# Debug journal

Notes distilled from maintainer debugging sessions and triage-bot runs on this repo (June–November 2026), written for whoever is triaging an issue next.

Every entry is an observation from a past investigation, not a statement about current main. The code moves. Use these as "look here first", confirm against the working tree before you put anything in a comment, and say what you actually confirmed rather than what this file says.

The file was compacted on 2026-11-05, from 730KB of per-issue detail down to the durable facts and pointers. If you need the full story behind an entry, the issue or PR it cites has it, and so does the last uncompacted version: `git show ea6ba38d:tools/debug-journal.md`.

## Replay the reporter's debug file

`predbat_debug.yaml` is a full state dump the harness replays against the current tree:

```bash
cd coverage
./run_all --debug_file <scratch>/predbat_debug.yaml > <scratch>/replay.log 2>&1
./run_all --debug_file <scratch>/predbat_debug.yaml --redo > <scratch>/replay-redo.log 2>&1
```

- Grep the log first for the non-default config block (`- <item> = <value> (default <value>)`). Output: `coverage/plan_orig.html`, `plan_final.json`.
- Without `--redo` you replay the dump's own rates, load model and Octopus slots. `--redo` recomputes them. A dump from an install with `debug_enable` off — the normal setting — carries empty `pv_forecast_minute_step`/`load_minutes_step` arrays (the end-of-cycle free-memory path clears them), so `KeyError: 0` near `pv_forecast_minute_step` is a needs-`--redo` tell, not an old-dump one: current v9.6.x reporter dumps crash without it too. (GH#5860, GH#4766)
- A replay cannot reproduce live ML-forecast choices, so a mismatch in marginal ~10p slots is inconclusive (GH#5213); grep the reporter's log for `Best export window` / `Best charge window`.
- The triage bot runs tests through `tools/triage_test.sh <test>` and forward replays through `python3 tools/triage_replay.py`; for a plain dump replay it uses a temporary `TEST_REGISTRY` entry calling `run_single_debug(..., redo=True)`, which also re-derives `set_rate_thresholds()`/`rate_scan_window()` (a dump stores end state, GH#5221).
- `Replay input:` log lines (PR #5427, 2026-10-12) rebuild a cycle's inputs from the log alone (formats pinned in `tests/test_log_replay_inputs.py`). The forward replay's parser (`tests/replay_forward.py`, PR #5363) makes `log_replay_*` a contract; unknown lines are skipped silently. A repeated identical line means the value changed, or (PR #5591, merged 2026-11-10) the first run of a new day — the signature includes `midnight_utc`, so each line logs once a day at most.
- Reading a dump directly (GH#5509): rates and windows use absolute minutes of the dump day, `predict_*_best` minutes from now, and the `*_today` arrays are minutes-ago convention (index 0 = now, larger = further in the past; recovering `minutes_now` from them works). `export_window_best[].target` is not the `export_limits_best[]` level; decode with `export_mode_of()`/`export_target_of()`.
- **Forward replay** (PR #5363): `./run_all --debug_file X.yaml --replay_log predbat.log` steps through the log's later runs, re-planning where live did and comparing plans (flags in `docs/developing.md`). For a plan that went wrong after the yaml was taken (GH#5423) or kept changing (GH#4865); `--override name=value` for what-ifs. Needs a log running past the yaml, and a yaml after any restart or `apps.yaml` change; concatenate rotated logs oldest first. Most reporters take the yaml when they file, at the end of the log, which leaves nothing to replay (GH#6150): ask for a History-view snapshot from the start of the period instead. `tools/triage_replay.py` checks this before running (exit 3).
- **Forward replay modes.** Exact (default) takes the logged SoC each run, and with `Replay input:` lines matched live plans line for line over whole days (Oct 2026); `--replay_simulate` steps the battery itself, to try a fix. The summary counts export windows only: use `--replay_chart`, and diff `predict base/best` lines against the replay's own `predbat.log` for costs.

Loader failures before Predbat code runs:

- `could not determine a constructor for the tag '!secret'`: `DebugYamlLoader` has no `!secret` constructor (GH#5748); sed captured args to dummies in a copy.
- numpy dtype `SystemError: bad argument to internal function` (v9.1.0+ dumps, GH#5205): fixed in PR #5892 (2026-11-01) — new dumps carry plain numbers, and the loader constructor replays the tagged old ones.
- `found unhashable key` from `io_slot_log_gate` (v9.3.8, GH#5569): fixed in PR #5575 (2026-10-17).
- Without `apps/predbat` on `sys.path` a load dies at the first `!!python/object` tag it cannot import. A newer dump on an older tree fails with `No module named 'control_monitor'` (GH#5719); null `control_monitor:`/`control_ledger:` in a copy.

Normal lines, not the bug: `Prediction kernel stale binary ... - using Python engine` (plan still correct) and `Config item ... is below the minimum ... - clamping to ...`.

## Debug yaml can contain real secrets

Read dumps locally and never quote a raw block publicly unchecked.

- Pre-v8.55.0 dumps can carry `args_from_apps_yaml` with resolved secrets (GH#4765); masked at source since PR #4910, so no reason to tell a current reporter to rotate.
- `mask_secret_args()`/`is_secret_key()` match `_key`/`password`/`secret`/`token` in top-level keys. `annual.py`'s `scrub_secrets()` is recursive and masks differently (GH#4770).
- `debug_history_enable` defaults True and snapshots ~3-hourly into `predbat_debug_history.tgz`, independent of `switch.predbat_debug_enable`.
- Snapshot retention is ~45 h: pruned by both count (`debug_history_count`, default 15) and age (`debug_history_interval`, default 3 h), and a force-capture just after a scheduled one doesn't double-retain. An evidence-request deadline is capture time + ~45 h, not a neat 48 h boundary.
- The Plan→History Debug column's snapshot download is served by Predbat's own web server (`/debug_history_download?id=`), so "I can't get files out of the Docker container" can still be met in a browser. And for "what did Predbat command during the window", ask for HA recorder history of the exact window, not the newest snapshot's ledger — the ledger keeps the latest confirmed value per entity, so window-start writes hide behind window-end restores. (GH#5852, verified 2026-10-29)
- Logs are redacted at write time (`LogRedaction`, `log_secrets.py`).
- `!secret` resolves only via the private `SecretYamlLoader`. Bare `yaml.load(...)` hits in the tree are ruamel, not PyYAML.
- Issue line numbers may resolve against a PR branch, not main. If `gh api .../pulls/<n>/comments` is denied, use `gh pr view --json`.

## Check configuration before code

Pull the non-default list first: `combine_export_slots`, `metric_min_improvement_export`/`_plan`, `best_soc_keep`, `metric_battery_value_scaling`, `metric_battery_value_export_scaling`, `metric_battery_cycle`, `metric_cloud_enable`, `load_scaling*`. "Configuration" is a legitimate outcome.

- Replay one setting change at a time and compare decisions, not the metric (an emptier final battery always looks cheaper). `best_soc_keep: 0.0` and `metric_battery_value_export_scaling: 0.8` are defaults.
- Read `optimise_all_windows()` end to end before calling a pass dead. The commented-out swap call is not the live one, which runs last (GH#4478).
- Near-parity export tariffs (GH#4840): leftover SoC is credited at `battery_value_rate()` (replacement cost), a ~1% margin, so `metric_battery_value_scaling` below ~0.987 flips exports. `metric_cloud_enable: False` predicts zero import.
- `battery_value_rate()`'s four inputs are built at different fetch stages (PR #5872, merged): `rate_max_base` (raw tariff), `rate_export_max_forward`/`rate_export_min_base` (post-replicate, pre-session, pre-override), `rate_min_forward` (post-replicate + IOG overlay, pre-session — built in `fetch_sensor_data()`, no longer in `rate_scan()`); `rate_export_min` stays session-inclusive by design. On a "stored-energy credit misbehaves" report, check the build point first. Traps: code installing a rate table outside fetch (a test `reset_rates()`, a replay harness) must reset `rate_min_forward` itself or a stale leftover silently prices the replacement cost; replaying an OLD debug dump restores its session-inclusive `rate_min_forward` and lacks `rate_export_min_base`, reproducing the old behaviour — run `--redo` to see the fix. (verified 2026-11-08)
- Charge-to-export "loss" (GH#5069): naive arithmetic omits the end SoC credit and displaced peak house load.
- Non-GBP tariffs (GH#3683, open 2026-11-05): `metric_min_improvement*` gates compare unconverted against the minor unit, with pence defaults, so plans churn. Scale them by the unit ratio.
- Money-losing plans: grep `Previous plan best metric is ... and new plan best metric is ...`. Positive deltas under `metric_min_improvement_plan` mean retention (GH#5616); negative deltas every cycle mean lock-in on stale windows, which lowering the gate cannot help (`should_replace_plan()`, GH#5686).
- Levels-pass exports that paid only in the PV10/PV90 blend, which `metric_min_improvement_export` could not remove and the write-backs restored (GH#3376/#5633, GH#5969): fixed in PR #5977 (2026-11-05, `export_gate_metric()`). Per-5-minute charging came in PR #5874 (2026-10-31).
- `best_soc_keep` is only a soft `metric_keep` penalty, never a window or reserve (GH#4961). `manual_soc_keep` and alert keeps (default 100 per alert) force `keep_minute_scaling >= 10` weighted by import rate, so are inert in 0p windows (GH#5162). Fixed in PR #6140 (2026-11-12): with a manual/alert floor active the keep penalty's import rate, and with a `manual_soc_max` ceiling its export rate, are floored at `KEEP_TARGET_MIN_RATE` in both engines — at a 0p/negative rate the target now still costs something, while plain `best_soc_keep` stays rate-weighted; a 30-minute slot still underprices the miss by ~5/kWh (the docs point at a manual charge slot). Only `set_reserve_enable` plus `reserve` is a hard floor.
- A "Predbat didn't charge before an Axle/saving-session event" report is usually config, not the optimiser. Check in order: `rate_low_threshold` set manually (a manual threshold caps the charge even ahead of a session; 0 = auto), `combine_charge_slots` on, `set_export_freeze_only` on (the export pass then only tries idle/freeze rungs, so nothing profitable to pre-charge for; #3994 open). Then the arithmetic (GH#5901, 2026-11-01): event revenue is bounded by discharge power × event length, so a pre-event top-up only adds post-event buffer worth about `battery_value_rate()` minus the refill price; an *additive* event boost (Axle, PR #4520) can never move a min-rate scan, so "no arb afterwards" may just mean base export is below the cheapest refill. No event-aware pre-charge config exists in `CONFIG_ITEMS`; the only hook is Axle's `binary_sensor.<prefix>_axle_event`.
- `HoldChrg` (within 1% of the limit, `set_discharge_during_charge` default True) is not `FrzChrg` (`is_freeze_charge()`).
- No charge-start hysteresis (GH#2513): the hold band needs `inv_target_soc_percent < 100.0`, so a 100% target is re-commanded every cycle.

`get_arg()`/validation traps that look like a feature silently off:

- `key:` (null) defeats the default for direct `get_arg()` callers (component args fixed since PR #5188, 2026-09-24). A quoted `'1'`/`'y'` coerces to False.
- Float-default truncation, e.g. `solcast_poll_hours: 4.8` read as 4 (GH#4925), was fixed in PR #4938 (2026-10-08).
- An enable-gated CONFIG_ITEM still returns its declared default while gated off (`get_ha_config()`).
- Unknown apps.yaml keys are ignored silently (GH#4999, open). `allowed:` is enforced only for string and integer types.
- Sensor-typed items reject numeric scalars (`not of type 'sensor'`); use list form (GH#2172).

## Test-order pollution (GH#5079)

- Since PR #5102 each registry test gets its own `create_predbat()`. Module- and class-level state can still leak (`PLOT_ENABLED`, `LogRedaction`'s lock).
- From `coverage/`: `./run_shuffle --hunt --quick` bisects to a (culprit, victim) repro. Also `--bisect <seed>`, `--campaign N`, and `./run_all --shuffle [--shuffle-seed N]`.
- Victims cluster in `model`/`kernel_parity` (tight assertions). Before fixing, check the culprit really touches the victim's state.
- `run_pre_commit` runs the quick suite only after the hooks pass, so a log ending at the hooks is not a green suite.

## The shared clock is rewound for ~0.8s every hour

`calculate_yesterday()` sets `midnight_utc` back a day and `minutes_now = 0` on the shared `PredBat` (`# Fake to yesterday state` / `# Save state`), unlocked, while other threads read it live. Present on main 2026-11-05.

- Off-thread readers are hit: manual overrides (GH#4900, fixed with `manual_time_origin()`) and component PV buckets (GH#4804). `ComponentBase` derives its clock from `now_utc` since 2026-09-13/14; `PredBat` mixins such as `Octopus` still read the fake.
- Code inside the fake must pass the real `minutes_now` to history indexing (GH#5004).
- Suspected, unverified (code-read 2026-10): `decode_octopus_slot()`, `dispatch_billed_off_peak()` and zero-kWh slot synthesis misread it (GH#4946). These affect History only.
- On a "shifted by one day" report, check this first. New off-thread code should derive time from `now_utc`.

## Per-integration notes

Grep for the named symbol rather than trusting a line number. Each area lists durable facts and "look here first" pointers, one per bullet.

### Fox (`fox.py`)

- Cloud errno 42015/44096 = setting unsupported by the device (`FOX_SETTINGS_UNSUPPORTED_ERRNO`); it is marked unavailable and never polled or written again. WorkMode is a select, ExportLimit a number. Since PR #5840 (2026-10-30) the three unsupported-setting lines log at Info (the same errno from a non-setting endpoint still warns); a Warn form in an attached log just dates it to pre-#5840.
- `soc_max` 4x too big when `batteryList` holds four `bmu` entries with one serial (AIO ESS, EVO 10-5-H): fixed in PR #5629 (2026-10-24). Unverified: whether `batteryDesignCapacity` totals a multi-pack stack.
- Fox device/detail `capacity` is an integer field, so fractional-kW models read low (`H1-3.7-E-G2-WL` read 3 kW, GH#5938): until PR #6081 (2026-11-10) only ".5"-suffixed deviceTypes were corrected (PR #4527). Both `-inverter_capacity` and `-battery_rate_max` funnel through `capacity_watts()` — the rate is min-capped with the truncated capacity and stored back destructively — and with `fox_automatic` on, apps.yaml's `inverter_limit`/`battery_rate_max` are re-bound to those sensors, so literal numbers there are inert. A dump's `sensor.predbat_fox_<sn>_info` attributes (`inverterCapacity`/`deviceType`) prove the truncation without raw-API access; read older logs as "fixed in PR #6081".
- `fox_automatic: true` re-`set_arg`s `soc_max` every cycle and it is not in `CONFIG_API_OVERRIDE`, so apps.yaml cannot override it; escape hatch `fox_automatic: false`.
- With the Mode Scheduler deleted, `compute_schedule()` shows the charge window from the legacy `forceChargeTime` read, which Predbat cannot clear (`set_battery_charging_time()` has no production callers; GH#4939, re-checked 2026-11-05).
- A Fox Cloud `didn't complete got X` is a genuine failure, but the cloud verify read is slow: old value at 3s, new one after ~18s.
- Reserve never reads back from the device (GH#5821, open), so "Current reserve is X%, already at target" is Predbat echoing its own write. Fox accepts `minSocOnGrid: 100` yet still discharges: declared ranges are acceptance, not enforcement.
- Device MaxSoc is published (`number.<prefix>_fox_<sn>_setting_maxsoc`, writable) but never bound to the planner (GH#5395, open); `automatic_config()` binds only `soc_max`/`reserve`/`battery_min_soc`/`export_limit`.
- ForceCharge overshooting its target (`fdSoc: 100` on ForceCharge groups): fixed in PR #5623 (2026-10-24).
- FoxESS HA/modbus path (`FoxESS`, not `FoxCloud`): the stock template binds `reserve:` to `number.foxess_min_soc_on_grid`; at 100%, `min_soc_on_grid` stops grid-connected discharge. `FoxESS` is `has_idle_time: False`, so `idle time is ...` programs nothing (GH#4961).
- Hold drain-block (GH#5704, verified 2026-10-23): `execute.py`'s hold-above-target branch called `adjust_charge_immediate(..., freeze=True)` on non-planner holds, so `charge_freeze_service` selected `"Back-up"`, which supplies no house load and pinned the battery. Fixed above the reserve in PR #5998 (2026-11-07): an inverter without a target SoC now stops the charge while SoC is above the hold reserve and freezes only once it reaches it. Below the reserve the freeze still applies; removing `charge_freeze_service` remains the workaround there.
- `ForceDischarge` in a `Fetch scheduler V1 returned` list does not prove a discharge window was written.
- Tests: `./run_all --test fox_api --test fox_oauth`

### Solis (`solis.py`)

- CID 636 (`SOLIS_CID_STORAGE_MODE`, Modbus 43110) is a bit mask. On "4B and above" firmware (`is_tou_v2_mode()`: CID 6798 reads 43605) per-slot registers (43707) alone drive timed charging and TOU bit 1 is refused, so CID 636 verify warnings are that refused bit, not a failed write (GH#4707).
- Do not infer V1/V2 from one read-back (GH#4774); keep the post-write `read_cid()` cache overwrite, which lets change detection retry. V2 writes the mode with slot 1, V1 at the window boundary (`claim_window_mode_assertion()`, once per window).
- A CID 636 report with no `setting storage mode to` lines came from the HA select handler `set_storage_mode_value()`, not `write_time_windows_if_changed()`.
- PV-only detection: `_reports_no_battery()` and `SOLIS_GRID_TIED_MACHINE_PATTERN` (`^S\d+-GR\dP`); Cloud alternates `batteryType` `'0'`/`'0.0'`, so match by value (`_reads_zero()`).
- Discovery beats apps.yaml (`overwrite=True`, grep `auto-discovery wins for this setting`) for `charge_limit`, `export_limit`, `battery_rate_max`, `battery_scaling`; only opt-out `solis_automatic: false`.
- Slot current cap (`slot_current_limits()`): CID 7224/7226 as read, else `SOLIS_SLOT_CURRENT_DEFAULT_AMPS` (60), lowered only by `--probe-ceiling` (GH#5068). The planner does not see the clamp; set `inverter_limit_discharge`.
- Verify echoes: the slot-current entity republishes the clamped cache at live voltage (`didn't complete got 3094.0` every cycle) and CID 5965's slot-SOC readback tracks live SOC (GH#4184); grep `CID 5967 ... is set to` for what reached the inverter.
- Still live (2026-11-05): `write_time_windows()` defaults a never-read slot current to the cap, so no write is attempted; seed `cached_values` in fixtures.
- Parallel pair (GH#5556): the master's V2 slot current governs the group while 7224/7226 are per-inverter, so a pair under-delivers — fixed in PR #5909 (2026-11-07): the master's slot current is now written for the whole group (`solis_parallel_slaves`).
- API: `B0115` (datalogger offline) and `R0000` (200/day allowance gone) are never retried (`SOLIS_API_CODES_NO_RETRY`); `automatic_config()` retries every cycle; `_with_retry()` catches only `SolisAPIError`.
- Unclassified outage codes (seen live in GH#5556's cloud outage: `B0072`, `B0673`) fall through `SOLIS_API_CODES_NO_RETRY` and get no datalogger cooldown; B0673 carries B0600's message text, so classify by code, not text (verified 2026-11-06).
- Still live (GH#5093, open): `SolisAPI.run()` folds all inverters into one `poll_success`, so one unreachable unit holds startup in backoff (to 128 min); list working SNs in `solis_inverter_sn`.
- Still live (GH#5190, open): `int()`/`float()` accept `_`, so `"1234567890_00"` passes `parse_cid_int()` and `get_arg()` coercion; start here on "absurdly huge value, fallback never fires".
- Holds (PR #5265): `reserve` is CID 157, a floor only while CID 636 bit 4 (`SOLIS_BIT_BACKUP_MODE`) is set, so the bit is always set. Non-slot events wait for the next `run()`, beyond the 2s verify.
- Older-log signatures: `export limit 0.48kW` (CID 499 100x small, PR #5625, 2026-10-24); `poll failed for <SN>: '<SN>'` (`KeyError` repr, PR #5733, 2026-10-24); `battery_scaling read as 0.0` every cycle, plan unaffected (warns once since PR #5841, 2026-10-29).
- `H M` types (`GS_fb00`, most cloud subtypes) rewrite time entities every cycle by design (#1529): first suspect for "hammers my Solis with writes".
- Test trap: `number_event_handler()` takes the SN from `parts[0]` of the entity id; use underscore-free mock SNs (`SN0EXPORT1`).
- `charge_discharge_time_windows[sn]` is startup-decoded once (`decode_time_windows*()` fire only on the first cycle) and is plan-driven afterwards; slot entities go stale if the startup decode fails, and everything else converges through `write_time_windows_if_changed()`. When adding a `seconds % 300`/`% 3600`-gated block inside `run()`, check the pre-existing `run(first=False)` tests at 300/600/3600 — they exercise it silently. (PR #5864, merged 2026-10-30)
- Demo / read-only handover: `Warn: Solis handover unconfirmed` latches while `set_read_only` is on and clears only through `run_cycle()`'s control section (`solis_control_enable` on, read-only off; monitor-only installs take the ordinary reset). Per-step budget is 60 s without a completed step, 300 s per inverter, each written CID able to pay the 5 s verify settle; `Schedule cleanup rejected for CID ...` is a refused write, and both `was not confirmed` and `cancelled before confirmation` mean timed out. A Demo entry costs ~8+4N Solis API requests (N slots) of the ~200/day allowance — check for slow or retrying Solis reads before assuming the inverter refused. (PR #5863, merged 2026-10-30; #4774)
- First question on a Solis hold-enforcement report: which route is the install on — the FB00 entity path (see *Solis Modbus*), Predbat's own Solis Cloud component (CID 636, sets the Battery Reserve bit unconditionally, freeze slots = `Self-Use - No Grid Charging` with 1% hold hysteresis), or a third-party select (Pho3niX90 solis_modbus `work_mode`: meaning-equivalent options, so supporting it needs a code-side name map, not config). A user-side HA automation keyed to `predbat.status` transitions can defeat any hold — it fires exactly during the hold; landed `backup_soc` writes with the physical mode still Self-Use mean landed writes ≠ enforced hold. (GH#5852, verified 2026-10-29)
- `has_reserve_soc: false` types (all Ginlong custom types; `templates/solis_local.yaml` ships `solis_rc` since PR #5881, merged 2026-11-07): a user-wired `reserve:` entity is display-only — read once into `reserve_percent_current` in `refresh_config()`, then replaced with a Predbat dummy, so `get_arg("reserve")` and `adjust_reserve()` land on the dummy, never the user's entity. Reserve functions are disabled fleet-wide (first such inverter) and the plan's floor is `reserve_min = max(set_reserve_min, battery_min_soc)`. A template pairing `has_reserve_soc: false` with a real `reserve:` entity looks like wiring but isn't; align `battery_min_soc`/`set_reserve_min` instead (the ginlong FB00 docs step-6 pattern). (verified 2026-11-08)
- Tests: `./run_all --test solis`

### Solis Modbus (`GS`, `GS_fb00` in `inverter.py`)

- The Energy Storage Control Switch (Modbus 43110, `energy_control_switch`) is written by `alt_charge_discharge_enable()`, gated on `has_solis_energy_control`; `GS` reaches it via `mimic_target_soc()` (35/33).
- `GS_fb00` (PR #5258): `write_solis_energy_control()` runs from `adjust_charge_immediate()` (49 charge/idle, 17 freeze/hold) or `adjust_export_immediate()` (64 freeze export, 49 export); a third writer would flip the switch twice a cycle. Before PR #5256 (2026-09-26) a switch left at 1 held charge slots at 0 W.
- With `energy_control_switch` unset, `write_solis_energy_control()` writes nothing and `warn_missing` fires only on a real charge cycle (`warn_missing=(target_soc > 0 and not freeze)`), so freeze/hold cycles degrade silently while reserve writes report success; an S6-style separate work-mode select is not a valid target — Predbat writes the FB00 option names verbatim (GH#5834, re-checked 2026-11-06).
- Bit 4 (Battery Reserve) makes `backup_mode_soc` (43024) a discharge floor. A SolisCloud session leaves the switch at 1 (`ENUM_SELF_USE_NO_GRID_CHARGING`) outside a slot. FB00 plugin names differ (`SOLAX_SOLIS_MODES_FB00`: Self-Use is 33).
- `set_current_from_power()` re-asserts `timed_*_current` on every rate call (PR #4437); `inv_charge_discharge_with_rate` zeroes only the power register. A 2600 W plan rate is `battery_rate_max_raw`'s fallback (GH#4198 family). Open: #3914, #3868 (HV battery amp conversion).
- On GS a hold is **mimic-owned**, never part of the rate intent: every hold path reaches hardware only through `mimic_target_soc()` (switch + `timed_charge_current`), and `apply_inverter_rates()` → `set_current_from_power()` re-asserts the full rate the same run ~0.2 s after the hold write — "bursts of full-rate charging during Hold/Freeze charging". The apply docstring's hold protection covers intent-expressed 0-rate holds only; decide intent-expressed vs mimic-owned before fixing. GS also logs `Note: Inverter does not support charge freeze - disabled` yet reports `Freeze charging` status, because `is_freeze_charge()` keys on limit==reserve independent of `set_charge_freeze`. (GH#5972, verified 2026-11-12)
- Test trap: a bare `Inverter(..., inverter_type: ["GS"])` mock does not seed `timed_charge_current`/`timed_discharge_current`/`energy_control_switch` args, so writes warn "No entity_id for timed_charge_current" and silently no-op — seed those args (plus `battery_voltage`/`soc_percent`) by hand before probing hold writes. (GH#5972)
- Modbus-path types (`GS`, `GS_fb00`, `SX4`, Sofar) have no component: control args come only from the template, and `create_missing_arg()` only dummies, so a missed `charge_limit` logs `No entity_id for charge_limit` on every target change (GH#5129).
- solax_modbus mode tables (`SOLAX_SOLIS_MODES`/`_NEW`) only compute 33/35, which mean different things in each; write the table-derived name, never a number. Feed-in priority is cloud-component only.
- The hold lever is window-scoped (GH#5152, open): only `set_current_from_power()`'s `timed_*_current`; `battery_discharge_current` is never driven.
- `energy_control_switch` mechanically requires a select exposing the exact `SOLAX_SOLIS_MODES_FB00` option names (`Backup/Reserve - No Grid Charging`, `Backup/Reserve`, `Feed-in priority - No Grid Charging`); any other domain falls through to a generic `set_value` a switch cannot take. ### Battery capacity estimation (`inverter.py` `find_battery_size()`)

- The estimator applies `battery_loss × inverter_loss` to every sample, right only for an AC-side `battery_power`; DC-side it under-reads ~4% at defaults (GH#5831, open, code-read 2026-10-29). Suspected, unverified: GivTCP's `battery_power` is DC-side.
- The 0.65–1.20 plausibility band anchors on `nominal_capacity`, which `refresh_config()` re-reads from the `soc_max` arg every cycle, so an integration that binds a wrong capacity there rejects every real charge (`capacity_too_high`) and the size never self-corrects. The `self.nominal_capacity = self.soc_max` fallback inside `battery_size_tracking()` is cycle-local and never a lasting anchor — the next `refresh_config()` overwrites it before the next `find_battery_size()` — and only the pre-fallback value is persisted as `soc_max_nominal`. Sunsynk fixed this in PR #6007 (2026-11-06) by binding `soc_max_fallback` and taking the estimator's power from `battery_size_power`; DEYE still binds `soc_max` from its own capacity (installer-typed `battCapacity` first), so a mistyped Deye capacity still pins the band (follow-up, not hardware-verified).
- The 80–100%-of-nominal clamp (#3974, #3940) means `battery_scaling_auto` tracks only degradation below `battery_scaling`; a measured capacity above nominal cannot take effect.
- Tests: `./run_all --test find_battery_size`

### SoC sources (`inverter.py` `soc_percent`/`soc_kw` args)

- `soc_percent` wins everywhere; `soc_kw` is a fallback only when it is absent (live SoC, `find_battery_size()`, `find_charge_curve()` all branch on key presence), so with both set the kWh sensor is inert.

### Balancer (`utils.py` `balance_inverters()`)

- "Balancing holds the wrong battery / the house imports while a peer sits near its reserve" — check the snapshot first: `build_inverter_snapshot()` (execute.py) is where units cross, and `balance_inverters()` trusts the key names it is fed (GH#5835). ### Load ML (`load_ml_component.py`, `load_predictor.py`)

- The 2-hourly retrain is a curriculum of passes (`ml_curriculum_step_days`/`ml_curriculum_max_passes`, hardcoded), a 16–40 minute CPU spike every 2 h (GH#3896, GH#5213). `threads` reaches only the C++ kernel and nothing caps BLAS threads, so NumPy may use every core.
- On "CPU regressed after upgrade", reconstruct from the log when fine-tunes ran under each version; a version window under 2 h proves nothing (GH#5213).
- `load_ml_retrain_interval_hours` (PR #5433, 2026-10-12; default 2, max 48) is age-based, not clock-aware. Past `ml_max_model_age_hours = 48`, `is_valid()` returns `"stale"` and ML predictions fall back to empty.
- `load_ml_enable`, `load_ml_source` and the retrain interval are component/apps.yaml args, not CONFIG_ITEMS.
- `is_valid()` can say "active" for a never-trained model (`model_initialized` is set before the first epoch), and an aborted curriculum leaves fresh stamps that suppress the staleness retrain (GH#5075; fix in open PR #5112).
- `PREDICT_HORIZON` is 48 h (576 steps) and the plan's load beyond it is exactly 0, as `load_forecast_only` skips the historical forecast (GH#5336, open); "over 48h" in `Generated N predictions` is hardcoded text.
- Each fine-tune can move the published 48 h total by double digits (GH#5561, open): bracket `Training successful` with the adjacent `Generated N predictions (total X kWh ...)` totals. The ML forecast replaces the load forecast with no blend; a quiet log is not evidence of health.
- Load exclusion knobs (`car_charging_energy`, `iboost_energy_subtract`, future `heat_pump_energy` #5445) reach ML-source users only if `load_ml_component.py`'s data prep subtracts the same: car already did, iBoost since PR #5829 (2026-10-29).
- Saved ML rows are prepped at fetch time and restored verbatim, so a data-prep change reaches only fresh minutes until old rows age out; `Database iBoost subtraction mismatch ... discarding` after an upgrade or switch flip is #5829's gate.
- "The LoadML trace shows large spikes and deep flat sections that do not reflect actual load" has two candidate mechanisms: rate history that reads as one flat value across many days comes from the `rates` sensor's `results` attribute backfill (the merge fills only minutes that backfill left empty — GH#6147, path from #3368), and long-range rollout error `mae_kwh` cannot see starts at `_normalize_features()`' z-scores meeting ReLU death. August's GH#4673 trace reports match both; that issue's npz replay proved the model accurate with correctly supplied inputs, so suspect inputs before retrain variance. Discriminator: `pattern_mae_kwh` vs `rollout_mae_kwh` on the `load_ml_stats` sensor (PR #4678), measured while the trace misbehaves. (verified 2026-11-13)

### Component health (`components.py`, `component_base.py`)

- `count_errors` is a lifetime counter. `api_started` means `run()` returned truthy once (Gateway does so while unconfigured). `is_alive()` is the real health check (60-minute staleness).
- A component's device-writing methods are listed by `ComponentBase.write_methods()` via the `@writes` marker; all integration components carry markers, but overriding a marked method without re-marking it silently unmarks it (PR #5920) — on a "Predbat wrote when it should not have" report, check the report against the actual code, not only the listing.
- `record_status()` writes raw text as the HA state, and HA rejects states over 255 characters. A test of `update_status()` sees only the last `record_status()` message.
- Each component has its own thread and loop, so blocking compute stalls only that component and `run_timeout` never fires. Slow shutdown (all log Stopped and "Predbat terminated", the process lingers): find the `run()` that cannot return, load_ml first (GH#5075; PR #5112 open).
- Since PR #5963 each component owns a clock (`monotonic()`/`wall_time()`/`await sleep()` on `ComponentBase`): elapsed-time windows (staleness, retry backoff, dedup) are stamped on the component clock; anything leaving the component — payload timestamps, JWT/epoch comparisons — stays on the wall clock. A stamp initialised to 0 needs an explicit zero-guard: a just-booted host's small monotonic value makes "never sent" read as "just sent".
- `align_minute: True` on a `COMPONENT_LIST` entry runs the component loop at minute boundary +1 s, skipping boundaries a slow run() overruns; run()'s `seconds` steps in whole minutes, so interval checks inside the run must be relative deltas on `seconds`. Sigenergy, Solax and Teslemetry set it; a new minute-edge component adds the flag and updates the registry pin test (`test_registry_align_minute_reaches_the_component`). Without it, acting on a minute-resolution edge is up to a minute+ late by design — check the flag before debugging the component's own window logic. (PR #5976)
- On timeout, `start()` cancels the task without setting `api_stop`, and the next tick may start a second run.
- `Components.start()` waits up to 10 minutes per component, serially: restart delay ÷ 10 minutes = dead-component count (GH#5580; GH#5134, open).
- A `run()` exception skips the rest of that cycle and retries on backoff (first cycle: `api_started` stays unset), so report what was skipped, not a "crash" (GH#5584). `json.JSONDecodeError` slips past `aiohttp.ClientError` handlers.
- A component whose fetch fails **gracefully** — logs and returns success, keeping previous/empty data — never triggers `ComponentBase.start()`'s backoff, so a one-shot `if first: automatic_config()` against the empty data is a permanent silent miss (Octopus: KT-CT-1199 → None → previous account data → `tariffs == {}` → `run()` returns True). On an "automatic config never ran / ran once against empty data" report, check what each change-detection guard does on the **empty→populated** side and enumerate all its call sites. Octopus's is fixed: `automatic_config()` records the tariff keys it ran with and the fetch reconfigures when they differ, downloading the rates the same cycle (PR #6080, 2026-11-09). Other components are unaudited. (GH#5994, verified 2026-11-13)
- A component's hardware fault is invisible outside its own log plus its realtime sensor unless the component calls `self.base.record_status()` itself (`solax.py` calls it nowhere; the working precedent is `gateway.py`'s error path) — and the `had_errors` branch in `update_pred()` skips `record_status()` entirely, so the "obvious" error path freezes `predbat.status` on its last value instead of showing an error. `non_fatal_error_occurred()` only sets the flag. (GH#5996, verified 2026-11-13)
- An every-cycle `Warn: <component>: failed to report discovery for the catalogue: <AttributeError>` where the traceback text comes from inside `build_discovery()`: the guard over malformed payloads covers `except (KeyError, IndexError, TypeError, ValueError)`, but a read of the data container sitting *outside* that try in the same method (a `data.get(...)` loop after a strptime `pass`) raises AttributeError uncaught, and `refresh_discovery()` swallows it — the observable is the warn plus a catalogue record frozen at its last-filed state. temperature.py shipped this shape; whether a live fetch can hand `build_discovery()` a truthy non-dict is unconfirmed. (GH#5936, verified 2026-11-10)
- Stamping liveness on cache-only cycles hides a dead component, so override `is_alive()` (enphase, Kraken; GH#5582); an empty signed-in account should return True without stamping, as False costs 10 minutes per restart.

- `rate_replicate(use_future=True)` fills live import/export, so the `*_base` tables, compare recognition (`is_live_published()`) and the IOG strip value include forecast fills (PR #5738).
- AgilePredict: `GET https://prices.fly.dev/api/{REGION}/?days=N&high_low=false` (REGION in `ABCDEFGHJKLMNP`, N ≤ 14; `&export=true` for export) returns one region object of half-hour `{date_time, agile_pred}` entries from the current half hour; mixed timezones across DST; cached ~180 min. The post-April-2026 unit-rate discount is applied **before** the unit-rate cap, and the cap is 95.23p (5% VAT makes it 100p) — confirmed against 9 Nov 2026 prices (PR #6100).

- Tests: `./run_all --test futurerate`

### Plan: charging and holding

- **Battery charges or freezes when it shouldn't** — rule the plan out first. A planned freeze is a charge window whose limit equals the reserve %. On an all-loss tariff, holding full is correct. (GH#4890)
- **Battery pinned at 100% while the house imports at peak** — `Completed run status Demand` every cycle, zero `Inverter N count register writes` and a flat SoC mean something outside Predbat refused the discharge; check the integration's reserve/min-SoC binding. (GH#4961)
- **`Hold charging target X%-Y%` while importing at peak, or a peak-price charge window** — the high-price gate (`best_price_charge_level`) guards only windows whose limit is still 0. Without `set_reserve_hold`+`set_reserve_enable` (or `inv_has_timed_pause`) "Hold charging" is an armed-window fallback; `not yet in charge freeze, holding target SoC at 100%` is a deliberate pre-window write. The suffix is SoC–target, not start–end. (GH#2716)
- **Plan shows `HoldChrg -> N%` / "charging to N%" while the slot charges higher, or a "Planned Charge" row whose SoC never rises** — a plan row's "target" is the predicted end SoC when the window cannot reach its limit (`clip_charge_slots()` keeps the limit at `soc_max`), and the label is a knife-edge: `HoldChrg` is shown only when the modelled SoC stays at/above the limit over the whole window, so a window whose target is already at/below the SoC (a reserve-hold that charges nothing) falls back to the generic "Planned Charge" with its hardcoded rising arrow. Check intent via the dump's `best_charge_limit` vs `status_detail`'s target before calling the limit logic broken. Open 2026-11-05. (GH#4445, GH#5889, GH#5902)
- **Weather alert active and the battery sits at its current SoC while importing ("my keep is ignored")** — the alert keep (default 100) is a floor the optimiser defends, not a hold (see "Check configuration before code"). (GH#3200)
- **"Why does Predbat discharge to the house during cheap hours?"** — a model gap: every minute outside a charge or export window is ECO in `predict()`; only EV slots (`car_charging_from_battery: false`) and iBoost (`iboost_prevent_discharge`) hold the battery there. (GH#5122)
- **Reserve raised to keep the battery full (`set_reserve_min` 100) and it never charges — `Filtered charge windows []`** — the charge scan needs levels strictly above the reserve, so a reserve ≥ `soc_max` (or `best_soc_max` below it) leaves only "off"; a fix must also cap `reserve_percent`, as a limit at the reserve is a kernel freeze. (GH#4766)
- **Plan shows a flat hold at the reserve but the battery drains past it (Sigenergy to 0%)** — `has_reserve_soc: False` keeps the floor model-only (`Note: Inverter does not support reserve - disabling reserve functions`); see the *Sigenergy* notes. (GH#5358)
- **First cheap window charges to 0% / the charge target lands later than the cheap band** — a metric tie: the SoC scan adopts on a non-strict `<=`, and with `metric_battery_cycle` at 0 a charged kWh scores as its stored credit; neither `metric_min_improvement` nor `metric_battery_cycle` fixes it. Open 2026-11-05. (GH#5069)
- **Overnight charge stops at "just enough", or starts late and stops short, or stops short when a free electricity session sits later in the horizon** — the first two are pruned pv10/pv90 hedge slots, fixed in PRs #5721/#5735 (2026-10-24/25; `debug_enable` logs `Prune dead` / `Prune kept hedge` / `Prune trade-off` per slot; with 0p export stored kWh earn `metric_battery_value_export_scaling` 0.8, so 100% is not the optimum); the session case is by design — it bridges to the 0p session, whose 0p is baked into the dump's `rate_import` on replay (deleting `octopus_free_slots` does nothing). (GH#5719)
- **The plan seems stuck and won't adopt a clearly better replan** — `should_replace_plan()` compares pre-clip snapshots and a retained incumbent keeps a stale one; gates and units are under "Check configuration before code". (GH#4736, GH#5261)
- **Charge and hold writes alternate every 5 minutes while the target is steady** — SoC flips 1% across the target: the `execute.py` hold gate `soc_percent >= inv_target_soc_percent` has no tolerance, and the `- 1.0` hysteresis nested inside it is dead (2026-11-05). (GH#5083, open)
- **Low power charging does nothing or still charges at full rate, a dawn-split window's dark half shows "rate zero", or the low-power rate changes several times within one window** — all by design: `find_charge_rate()` uses max rate when the window's average remaining PV forecast is at least `low_power_pv_threshold_w` (150 W, the same threshold driving the dawn split), re-runs every cycle filtered only by `rate_tolerances()`' 5%; a dark half showing "rate zero" is frozen at the reserve (`FrzChrg`) so no rate is computed. Treat requests as enhancements. (GH#4577, GH#4975, GH#3311, GH#5241, GH#5536, GH#2628)
- **"Predbat won't charge when the battery is cold"** — `find_battery_temperature_cap()` treats curve values as capacity-per-hour fractions of `soc_max`; a `0.00` step is a genuine 0 kW cap (the docs' own GivEnergy Gen2 example sets `0: 0.00`), so with a charge-current-triggered BMS heater that is a causal loop: no planned current → heater never fires → cells stay cold → cap stays 0. Without `battery_temperature_history` one constant temperature spans the horizon, and `predict_battery_temperature()` repeats 24 h-old deltas, blind to heater runs and charge self-heating; no heater concept exists, and one would have to be stepped inside `predict()` and mirrored in the kernel. (GH#5919, verified 2026-11-10)
- **Two charge windows meet at 00:00 inside one continuous cheap period** — `calc_dawn()`'s light latch resets at midnight; since PR #5709 (2026-10-23) `find_charge_window()` splits only at dawn. (GH#5205)
- **Turning `debug_enable` on changes the plan** — deliberate: `kernel_supported()` refuses under `debug_enable`, and Python honours the coarse `enable_fast_mode_levels` step while the kernel runs at 5 minutes, so near-ties can flip. (GH#5408, GH#4453)
- **Control SOC only: status `Demand` during the inverter's own charge window, the running charge's target churns or drops to the reserve, or an AC-coupled inverter charges to 100%** — `isCharging` used to be set only inside `execute.py`'s `if self.set_charge_window` block, so a charge the inverter ran itself counted as no charge (no planner keep, `inverter_soc_reset` wrote 100%, freeze-export-during-demand paused it); fixed 2026-11-06. The near-tie fragmentation tie-break that adopted those plans works as designed. (GH#5991, GH#5987)
- **"Why does the plan use these charge windows" in Monitor / Control SOC only** — with `set_charge_window` off, `calculate_plan()` clones `self.charge_window`, which the executor fills from the first enabled inverter's own programmed windows (repeated daily to the forecast horizon). So the planner optimises targets over the inverter's windows and the tariff's never appear, and a mixed fleet follows only that first inverter. Start here on a Control-SOC-only window report, not at the rate tables. (PR #6001 review, verified 2026-11-14)
- **`best_keep {}kWh` / `keep {}kWh` in a plan log is a penalty, not a planned level** — `metric_keep` prices the deficit below `best_soc_keep` at the minute's import rate × `best_soc_keep_weight` × duration, so on a two-tier tariff it can dominate the metric against a real plan cost of hundreds of pence; read "best_keep 1546kWh" as keep-dominated. Judge fills by replaying the captured instant with keep/weight variants, not by the log figure. (GH#5987, verified 2026-11-13)
- **A near-tie plan flip adopts the cleaner plan and the branch has no cost check** — `should_replace_plan()`'s fragmentation branch takes any `improvement >= 0` with fewer segments, while its docstring and the "cost-neutral improvement but less fragmented" log line claim cost-neutrality; `plan_fragmentation()` counts each night's charge window above the reserve as own segment, so it reaches charge plans, not just the export staircase. The `plan_tiebreak` suite's "cleaner but costlier plan is rejected" case passes no cost args (the boost cases do) — a cost-gated fix test needs real `cost_prev`/`cost_new`, and passing them fails the branch today. (GH#5991, verified 2026-11-13)
- **Predbat exceeded the site's import ceiling** — the planner has no import clamp: `import_limit` is only a discovery rating (sunsynk/fox/deye). Draft PR #5486 (diagnostics) open. (GH#5490)

### Plan: exporting

- **Exports happen at the wrong time** — `plan.py`'s export pass order, `combine_export_slots`, `metric_min_improvement_export`.
- **"Random" exports that lose money on a flat export tariff** — see GH#4840 under "Check configuration before code".
- **Exports at the export peak then imports all evening ("never sells above my buy price")** — sell is weighed against the refill price, not the concurrent import price; `best_soc_keep` handles the tail and `best_soc_min` binds only in export windows. Exports run at full power, so window length is the stop line; a row's limit % is the SoC reached. (GH#5509, GH#5566, GH#5579)
- **`Best export window @ 0p` on a non-zero export tariff** — a stale discharge window read back from the inverter (`update_status()` pre-fills `average = 0`), used verbatim under `calculate_best_export: false`. A `discharge_rate` + reserve write after a charge window is the routine restore, not an export. (GH#5036)
- **"Charging and exporting in the same slot" in the plan html** — two windows in one 30-minute row; `output.py` splits the State cell deliberately. (GH#4987)
- **Loss-making forced export kept plan after plan; `Prune kept hedge export slot` / `Reverted change to d window N`** — fixed in PR #5977 (2026-11-05); see "Check configuration before code". Prune pairs read (without slot) vs (with slot), lower is better; `export_threshold_penalty` is charged per plan interval of export still to come (PR #5874). Reporters swap pv10/pv90 labels in prose — check the `base10`/`base90` series before accepting a scenario attribution (PV90 runs later than nominal). The dead-slot branch ("Prune dead") still drops on nominal-identical-plus-no-SoC-move alone without consulting the blended metric — the residual trap when pv90 planning values a nominal-dead slot. (GH#5969, verified 2026-11-12)
- **An evening export drains to the same level whatever the load risk** — pv10 scored target exports at `best_soc_min`; since PR #5736 (2026-10-25) it floors at the nominal run's end SoC.
- **An export window is in the plan but moves nothing** — limits in the sentinel band (99.3/99.5/99.7) mean "Hold exporting" in both engines, and 99.0 is the freeze sentinel (GH#4914; whether a 99% floor still emits it is unverified). A freeze-export window zeroes an overlapping charge candidate (`remove_intersecting_windows()`). Change both engines together (`test_kernel_parity.py`).
- **Every ordinary export window vanishes when a saving session or Axle event is in the horizon** — the threshold latched at 99; fixed in PR #5163 (2026-10-09, v9.3.7). A dump's `rate_export_cost_threshold` is rewritten from the plan's own level, so it is not the operating threshold. (GH#5221)
- **Predbat plans exports the site may not make (DNO or installer restriction)** — on Teslemetry see `update_battery_export_permitted()`. Elsewhere `export_limit: 0` (zeroes solar export) and `battery_rate_max_discharge: 0` (stops self-consumption) both mis-model it. (GH#5710)
- **An evening export drains to the reserve hours before the cheap band, and raising `metric_min_improvement_export` doesn't stop it** — depth, not whether: `optimise_export()` compares each full-power start against the window's export-off baseline, never the next-shallower candidate, so a metric that keeps improving downward always selects the deepest start (window length is the only depth lever); raised far enough the gate instead rejects the whole export, which the plan write-backs re-adopt. Open enhancement (GH#5860, verified 2026-10-29).
- **Exports deeply at the peak, then the evening load imports at a higher price** — compute the nominal spread first: `export_peak × (1 − discharge_loss) − import_peak`. Negative → suspect the fixed #5566 mechanism (PV90 chose export depth on a losing nominal case; fixed, `load_scaling90` now defaults 0.9). Positive → the plan is behaving as designed: export at the peak, buy the small evening load back at day rate, refill cheap overnight — answer with the arithmetic and the levers (`best_soc_keep`, `best_soc_keep_weight`, `metric_battery_cycle`). The `Calculate Best options` log line prints the effective loss/cycle config. (GH#5866)
- **Do not compare the plan table's two "(w/loss)" columns** — they are different units: Import-(w/loss) = raw / `battery_loss` / `inverter_loss` + `metric_battery_cycle` (the cost to re-buy and store a kWh at that rate); Export-(w/loss) = raw × `battery_loss_discharge` × `inverter_loss` − `metric_battery_cycle` (earnings per stored kWh). "Export w/loss 32 < Import w/loss 40, so holding wins" compares sell vs re-buy; the comparator for holding an already-charged battery is the raw import through the discharge chain, or the overnight refill once demand is met. The loss chains cancel when both paths discharge the battery, so the raw export-vs-import spread is the trade for the displaced part, and the sim models both chains — there is no export-revenue bypass. When export < import the optimiser trims rather than forbids (read the `Export windows filtered [... @ N%]` percent — a SoC floor, not a price), and `metric_min_improvement_export` ignores `best_soc_keep` by design. (GH#5999, verified 2026-11-13)
- **The export icon or `binary_sensor.predbat_exporting` says off while the battery exports** — `isExporting` is not set by the demand-freeze `[Freeze exporting]` block; read the status text. PR #5131 open. (GH#5125)

(GH#5933; per-mode detail GH#5947)

### Inverter control and writes

- **Export start time rewritten to "now" every cycle of a running export** (`Adjust force export to True, change times from 20:55:00 - ... to 21:00:00 - ...`) — the overlap guard after `Include original export start` in `execute_plan()` counted an empty charge window, or one starting as the export ends, as an overlap. Fixed in PR #6005 (2026-11-06), verified with the GE Cloud budget harness.
- **Inverter setting not applied** — follow `execute.py` into the component's reconcile loop, and check `read_only`.
- **Battery charges to 100% at start, on a mode change or on `set_read_only` (Victron `SK`, any `has_charge_enable_time: False` profile)** — `reset_inverter()` writes `adjust_battery_target(100.0, False)`, a real order where that register is a floor, on any `reset_inverter: True` config change including startup, even in Read-Only.
- **`Note: Inverter does not support charge/discharge freeze - disabled` despite the flag; `has_service_api`/`has_rest_api` changes nothing** — capability flags are `INVERTER_DEF` values in the `inverter:` block (a custom type copies `GE`); `has_service_api` does not exist and `has_rest_api` is never read. Services come from the six `*_service` keys. (GH#1406, GH#5066, GH#5203)
- **`write_and_poll_switch: No entity_id for scheduled_charge_enable ... to write` / `write_and_poll_option: No entity_id for inverter_mode`, only a red `with Errors reported`** — presence flags with no bound entity; custom types inherit GE's `has_charge_enable_time: True` / `has_ge_inverter_mode`, so check the `inverter:` block first. (GH#5539)
- **Reserve ratchets up and never returns (`Increasing set_reserve_min from X% to battery_min_soc of Y%`)** — a one-way raise in `Inverter.__init__`; bound to a live entity (Solar Assistant Growatt SPH template) it pins the highest value read. (GH#4013, GH#5232)
- **"Predbat always sets the reserve to X%" where X = charge target + 1** — the hold-on-reserve path (`Hold charging as SoC ... is above target SoC` before `Current Reserve is ... new target is X%`). Changing `set_reserve_min`/`set_reserve_enable` drops the reserve to the device floor for a cycle. Blame drift only with ledger evidence. (GH#5660)
- **Hundreds of `Trying to write N to X didn't complete got M` overnight** — check the plan had a window: idle cycles rewrite rates to max and `write_and_poll_value()` has no failure dedup, so a refused register (SolarEdge preserve-charge) repeats every cycle. False alarms: see *HA write/verify*. SolarEdge `Connection to inverter ID N failed` is the HA integration. (GH#5073, GH#5324)
- **Every charge/export window runs ~N minutes late** — the inverter's clock; compensate manually (`inverter_clock_skew_*`). `check_clock_skew()` warns hourly at ≥5 minutes from v9.0.2. (GH#4927)
- **GivEnergy-mode discharge times appear in the inverter portal only once the window starts** — as coded: `adjust_force_export()` nulls start/end when `inv_has_ge_inverter_mode and not force_export`. The 30 s `Sleeping (workaround)` settle can delay full rate ~10 minutes. (GH#2649, GH#4180)
- **Charge or discharge rate pinned far below the hardware's** — check the component's auto-config rate binding first (GE Cloud: the `charge_rate` entity's `max`; Fox: a duplicated `batteryList`, or the truncated `capacity` field; Solis: its notes); compare `battery_rate_max_raw`/`soc_max` in the dump with the nameplate. The only raise lever is `battery_rate_max_scaling[_discharge]` (modelled rates only); `inverter_limit_override` is another cap, never a raise, and CONFIG_API_OVERRIDE/manual-API overrides do not reach a component's `set_arg` binding. (GH#4908, GH#4919, GH#4940, GH#5938)
- **Low power computes the right rate but a service-driven inverter still charges at full power** — with `output_charge_control: "power"` there is no dummy `charge_rate`, so `{power}` is `battery_rate_max_raw` (GH#3311, GH#5252 open); with a helper entity it lags a cycle. (GH#5182, GH#5252)
- **Monitor mode is not read-only** — the mode select sets only the windows/SoC flags; `set_read_only` is a separate switch, so with `set_freeze_export_during_demand` on a plan-free Monitor mode still writes a pause-charge plus rate-0. A control-mode pause is also not released by switching to Control SoC only/Monitor: the release runs only where `reset_rates` triggers. (GH#5856, verified 2026-10-29)
- **Inverter service calls stopped, or re-sent every cycle** — `Calling service` with no effect is an HA rejection (`was not accepted`); repeated `Skipped service ... as it was previously called` is payload dedup keyed by domain alone (`hash_index = domain`), so two inverters on one domain re-call every cycle. A rejected call is dropped from the dedup and reissued next cycle; an accepted call that died downstream (Modbus drop, gateway republish) was recorded as done — skipped for the rest of the window while `control_failures` grows, and `control_monitor` warns without re-applying. The hash is recorded only after every call the template made was accepted (`call_service_template()`), so it never recovers from a device that accepts then reverts (see the Solar Assistant bullet), and it keys the last accepted call per domain — an identical stop accepted in another state (the idle cycle's re-send, the previous window's stop) can silence an opposite-side transition stop. It is computed from the `data` argument, not the sent payload, so template calls with different resolved payloads can still collide. Grep the template for `repeat:`/`always:` — those re-send regardless. (GH#5021, GH#5627, GH#5888, open; dedup shape code-read 2026-11-12)
- **Solar Assistant: charge windows are planned but the battery ignores them / drains through them (SA Growatt SPH)** — the work-mode select is the operative control and SA firmware clears the TOU slot registers 0.4–0.9 s after a mode write (mirrors #2654): slot values alone control nothing, so re-arming or monitoring the slot selects never catches it. SA republishes the cleared slots as `00:00`/`23:59` with enable off, and the read path accepts that pair as a live full-day charge window (`start == end` is the only disable test), with `Include original charge start` adopting the 00:00 start. A fix must re-send/verify the mode, not the slots; `repeat: true` is improvement-not-cure — a mode re-send wipes the slots again. Start from the dump's `control_ledger.events` and `predbat.control_failures`; a window-end "Load first" + enable-off can be Predbat's own teardown. (GH#5951, verified 2026-11-03)
- **Solis: no charge or export since a pod restart, `Failed to verify CID 636 storage mode ... read back` (2 lower), errors naming `cid 103`** — a timed-out CID 6798 read left a TOU V2 inverter treated as V1; fixed in PR #5864 (2026-10-30). See the *Solis* notes.
- **Sigenergy: MQTT `published` but commands do nothing, or `code=1201 Access restriction for /openapi/system`** — the publish line proves nothing; run `sigenergy.py --command-test --command-mode idle`, and see the *Sigenergy* notes.

### Rates, costs and savings

- **`cost_today` steps up after each half hour of an Intelligent car charge and falls back 15–60 minutes later** — `today_cost()` re-prices a running dispatch before `completedDispatches` lists it; `octopus_held_update()` bridges it (`OCTOPUS_DISPATCH_HOLD_MINUTES`). See the *Octopus* notes; test `octopus_dispatch_hold`. (GH#5520)
- **The half hour under a running Intelligent dispatch stays at the peak rate while the car charges** — `started_dispatches` is read but never priced (completed/planned only); the `Octopus: Dispatch timeline car N @ ...` log line proves whether the entity listed it. See the *Octopus* notes. (GH#5773)
- **Rates read zero, or `Warn: Octopus: No Octopus data in sensor ... attribute 'rates' / 'raw_today' / 'prices'`** — `fetch_octopus_rates()` reads only `rates`/`raw_today`/`prices` (plus `raw_tomorrow` for non-Octopus entities); else use a template sensor. Keys: `rate`, `value_inc_vat`, `start`/`end` (×100, so EUR shows as cents), `value`, `price`/`from`/`till`. (GH#5676)
- **Plan-card summary cost one digit short ("£3.2")** — fixed in PR #5796 (2026-10-28).
- **The day rate is classed as low (low-rate sensors stuck on) while a saving session or Axle event is in the forecast** — fixed in PR #5163 (2026-10-09, v9.3.7) by `rate_minmax_excluding_saving()`; `rate_max`/`rate_average` stay event-boosted. (GH#5050, GH#5237)
- **"Plan has continual charge slots to 100%/HoldChrg through the peak" on a tariff whose export max beats the import max** — with `rate_low_threshold: 0` (auto), `set_rate_thresholds()` widens the import threshold to `rate_max + 0.1` when the export max beats the import max (also when alerts or manual SoC keeps exist): the `Low import rate windows [...]` filter becomes a no-op and buy-at-any-price/sell-at-the-peak arbitrage is what the optimiser rationally plans. Fingerprint: `Rate thresholds ... import <rate_max+0.1>` with every 5-minute slot in the low list. Workarounds: a non-zero `rate_low_threshold`, `set_export_freeze`, or more keep/`metric_battery_cycle`. (GH#5990, re-verified 2026-11-13)
- **Import cost far above the bill on a 3-phase site with per-phase sensors** — `minute_data_import_export()`/`minute_data_load()` sum phases instead of netting, double counting cross-phase offsets in today-so-far cost (plan unaffected). (GH#5746, GH#5835, GH#4856)
- **`cost_yesterday` / the History view uses today's rates for yesterday on a dynamic tariff** — `rate_replicate()` back-fills negative minutes with today's same-time rate, which `calculate_yesterday()` shifts back 24 h; the live plan is unaffected. (GH#5194, GH#3267, open)
- **`cost_yesterday` / `savings_yesterday_*` show the wrong day after a clock change** — `calculate_yesterday()` read `minutes_back = minutes_now + 1` while `minute_data()` keys by elapsed minutes, so lookups were ±60 off on a change day; yesterday's and today's figures are now read from the real start of the day (PR #6084, merged 2026-11-10). Keep the mechanism for reading older logs. (GH#5760)
- **An old History day still shows "(import, export not billed yet)"** — billing stops re-reading a local day once it is `BILLING_SETTLE_DAYS` (5) old, however incomplete (`still incomplete after 5 days, so it won't be read again`), so a half hour missing then never arrives; `_parse_node()` also drops a half hour whose bucket kWh do not sum to the metered kWh, or whose energy has no price yet (that one is re-read). With an export meter, a row whose import leg is billed and export leg is not is flagged `billing_pending_export` and shows as "import, export not billed yet" — on a settled day that mark never clears, and `missing_slots`/`export_pending_slots` deliberately count the two kinds apart. `history_billing_mark` is a per-leg [count, newest-key] over the whole cache, so one late slot rebuilds every History view, not just that day's. (GH#6009/#5926, verified 2026-11-14)
- **"I can only override one plan slot at a time"** — by design (one `POST /rate_override` and a reload each). Batch: `rates_import_override`/`rates_export_override` in apps.yaml, or the manual API. (GH#5289)

### Sensors, history and load data

- **Plan tab blank / no plan shown in HA** — `predbat.cost_today` is missing from HA recorder history (recorder configuration). See test `faq_recorder_config` and `docs/faq.md`. (GH#3936)
- **Energy totals jump, or a day counts a huge figure** — look for a counter dip then recovery: `minute_data()` drops only upward steps above `MAX_INCREMENT` (1.2 kWh/min), so a gentle recovery after a held dip counts in full. Applies to any `*_today` binding. (GH#5388, GH#5356)
- **The plan is too optimistic about solar on an AC-coupled site whose load reads ~0 in daylight** — derived load is already net of PV and `get_diff()` subtracts PV again; no generic netting option. Calibration side: *Solcast*. (GH#5552, open)
- **SoC reads too high, never falls, or is frozen** — check the sensor behind `soc_kw` (a "charge today" sensor ratchets); `battery_soc:` is not a config key. `Inverter N SoC:` fixed while power moves is a frozen entity (often mixed GivTCP prefixes). `soc_max` bound to "kWh remaining" shows as `nominal_capacity` on `predbat_soc_max_calculated` moving with charge. A sensor that vanishes after a restart may have its only publish inside a recovered-history branch (GH#5222). See *SoC sources*. (GH#4884, GH#5522, GH#5650)
- **`Warn: Found N periods of zero load with power data, filling using power integration`** — since PR #5921 (2026-11-07) `load_counter_quantum()` works out the counter's coarseness and splits each flat stretch between the counter's step and the power, so the fill conserves the counter's totals (older logs, pre-fix, read low-load history ~2x high on coarse counters, GH#5855). The warn now fires only when a run was actually filled and carries the counter quantum — "load sensor steps 0.0000 kWh" means a fine counter where every plateau ≥ a gap is being treated as lost readings. A flat run touching the oldest minute is never detected (it cannot close in the scan), so the oldest minutes stay raw by design. `load_power_fill_enable: false` turns the fill off. (GH#3623, GH#5204; re-verified 2026-11-10)
- **load_today climbs by kWh per hour on v9.4.1, or `Filled N gaps in load_today ... from predbat.load_energy_h0 history`** — feedback on Predbat's own `load_energy_h0`, fixed in PR #5656 (2026-10-20). Read any sensor Predbat also publishes with `interpolate=False`: `minute_data` extrapolates past a fresh newest record. (GH#5652)
- **"Plan History" shows 0.01–0.02 in the PV (or load) column overnight instead of the empty-slot glyph** — that is the recorded `*_today` sensor still ticking (a uniform ~20 W-equivalent slope on some Sunsynk units), replayed by `calculate_yesterday()` through `step_data_history()`; the History view is recorded data, not the forecast plan columns. The glyph is shown only for an exact 0 after dp2, so anything ≥ ~0.005 kWh/slot renders as a number; and the PV tooltip says "from the Solcast forecast" even in History, which is the confusion to acknowledge in the reply. (GH#5904, 2026-11-01)
- **A live export or charge window stops mid-slot after `Dynamic load last period 9.60kW, status high`** — `load_last_period` came from a coarse counter (Solis' whole-kWh `homeLoadTotalEnergy`); since PR #5851 (2026-10-29) "high" must be confirmed by `load_power` (fail-open: a sensor that is down reads None and the counter stands, so dynamic load is never switched off by a dead sensor). (GH#5851)

## Traps when investigating

### Versions, logs and attachments

- **Version drift.** Compare the log's version with `git tag --contains <sha>` (fetch tags first); many reports are fixed on main, and `v9.0.1` is `v8.55.1`. Treat "worked on 9.x, broke on 9.y" as a version question: `git show vX:<file>` before accepting a regression (GH#5390).
- **Tracebacks showing `/config/hass.py`, `/config/predbat.py`** — the HA add-on runtime layout: the add-on downloads the latest release zip and copies `apps/predbat/*` and `apps/predbat/config/*` flattened into `/config`, then runs `cd /config && python3 hass.py`, so line numbers match the released tag, not main. The download is gated on `/config/apps.yaml` being absent, so reinstalling the add-on does not refresh stale runtime files. (add-on repo re-read 2026-11-08, GH#5869)
- **`ValueError: bad marshal data (invalid reference)` from `_compile_bytecode` at aiohttp import** — corrupt compiled bytecode in the add-on's locally built container (no prebuilt image, `config.yaml` has no `image:` key; deps pip-installed at build): the crash is before any Predbat code, so classify `configuration` (precedent #3910) and look for a persistent disk cause (suspected, not verified remotely). (GH#5869)
- **A `predbat.log` spans versions and restarts** (appended across upgrades and downgrades, GH#5178). `version X currently running` prints every cycle, so count restarts by `Loading apps.yaml` → `Predbat: Startup predbat`. A restart without `Predbat terminating` was an outside kill, whose trigger is only in the add-on log (GH#3969) — the add-on wrapper's own line is `Shutdown, sleeping 20 seconds before restarting` (GH#5886; the wrapper is not in this repo).
- **`Best charge window` is the prefilled incumbent, not the optimised plan**, which is in the later `Raw/Filtered charge windows` lines. In a repeated pair in one tick the later line is the recompute (GH#5434, GH#5344).
- **Prove an attached debug yaml is the reporter's own** (compare `soc_kw` and serials/account ids at its capture minute with their log); once proven, it beats the issue prose (GH#5335).
- **Attachments disagree in time and identity.** Numbered logs (`predbat.1.log`, `.2.log`) are overlapping snapshots, not rotation order (check head and tail timestamps); debug-history snapshots are ~3-hourly; `predbat_debug.yaml` is download-time state (GH#5344). A new attachment URL can 404 for 10+ minutes (GH#5503); two attached dumps can be byte-identical — a "two dumps" corpus may be one snapshot (GH#5943). Ring snapshots are `debug/predbat_debug_<id>.yaml.txt` (GitHub rejects bare `.yaml` and `.tar`), and the per-cycle `create_debug_yaml()` dump still needs renaming; the HA Companion app's webview ignores `Content-Disposition: attachment` (GH#4720).
- **Evidence hosted on Google Drive cannot be fetched by tooling** (npz model files and the like on issue links): the URLs need interactive Google sign-in — ask for a GitHub-hosted attachment, or reason from the log and dump. (GH#4673)
- **A reporter's screenshot when `curl` is denied** — WebFetch the `user-attachments/assets/<id>` URL (GitHub 302s to a signed S3 URL expiring in ~5 minutes), WebFetch *that* within the window, then Read the saved `tool-results` file that fetch wrote: the Read is what renders the picture, as the text reply is just "raw JPEG binary". `user-attachments/files/<id>` downloads with plain `curl -L`, so a ">10 MB, unfetchable" conclusion is about the WebFetch route only. (verified 2026-11-07, GH#6016)
- **HA entity-history CSV exports cannot prove write provenance.** In one export every `context_event_type=call_service` row shared a single context id across 7 hours (impossible), and a provably-external flip carried full call_service context. Attribute by value + timestamp cross-referenced against `predbat.log`'s `Wrote X to Y successfully`/`Calling service` lines, never the context columns. (GH#5951, verified 2026-11-03)
- **Warnings.** Routine `Warn:` lines are the cause only if their timing matches the report. HA core's `Referenced entities ... are missing or not currently available` is only in the HA core log (GH#5420).
- **Log severity is the message prefix, read by two different consumers** — the console prints a quiet line only when its prefix starts with error/warn/info, while `classify_log_line()` (utils.py) is substring, so a line containing "warn"/"error" anywhere lands in the web Warnings tab whatever its prefix; word log messages accordingly, and de-noise a repeating warn by switching it to an Info prefix once the condition is known-persistent (PR #5841's pattern, verified 2026-11-06).
- **Hardware behaviour needs the hardware.** A unit test shows what the code does, not what the inverter did; say the maintainer must confirm.
- **A flat SoC is not necessarily a stall.** On a large pack one percent can be ~10 minutes at 2 kW (GH#4784).
- **Check that the report's premise exists.** Reports have cited AI-invented settings (GH#4918), features only on unmerged PRs (GH#4917), history `git log -S` disproves (GH#5022) and false "expert gated" claims (GH#5237). Grep `config.py`/`APPS_SCHEMA`, read each item's `enable:`, and check a proposal's symbols are on main (GH#5063).

### Replays and debug dumps

- **Copy `manifest.yaml` into a new worktree before running anything.** It is gitignored; without it `check_install()` downloads the release over tracked files and exits (`Predbat files are not installed correctly, trying to download them`). Recover: `git checkout -- .`, `git clean -fd apps/predbat`.
- **A/B across versions by checking out the old tag in place** and running `./run_all --debug_file <dump> --redo` on both (`git worktree add` is denied under triage permissions). First confirm the tag diff is inert for that config and the replay matches the live log (GH#5719).
- **Replay-probe pitfalls.** The dump's window list holds both days in one minute-of-day frame, so filter with `1140 <= start < 1440`. `Prediction.__init__` copies SoC, rates and ~200 other attributes from `base`, so set them first or rebuild it (GH#5616, PR #5756).
- **Dump-restored inverters are raw `__dict__` copies** (`read_debug_yaml()`), so an object restored from a dump written before your attribute existed simply lacks it — new per-inverter state must tolerate missing attributes (`getattr(..., False)`, as `build_inverter_snapshot()` does). Related: `charge_rate_now`/`discharge_rate_now` exist only after the first `update_status()`, and are floored to `battery_rate_min` immediately after the capture, so "is the rate actually 0" must capture the raw read first — a nonzero `inverter_battery_rate_min` defeats the balancer's `== 0` held-gate (the oscillation family, GH#5927). (verified 2026-11-10)
- **`self.predict_soc` after a trial run holds the nominal scenario** (nominal runs last in `run_prediction_metric()`); its keys stop at `forecast_minutes − 5` (PR #5735).
- **Ad-hoc replay under the triage permission mode.** Env-var prefixes break the allowlist: add a temporary probe to `run_debug_cases()`, gated on a marker file, and revert it. Plan pass lines go to `coverage/predbat.log`, not the test log (GH#5633).
- **Golden plans move with load scaling.** Regenerate `coverage/cases/*.expected.json` from `*.actual.json` and `random_results.json` via `./run_random`; `debug_cases` stops at the first failing case. First prove the shift by restoring the old behaviour.
- **A forward replay drifts from live** on logs without `Replay input:` lines (forecasts stay as the yaml had them), and where a restart or a mid-run car plug-in made live re-plan twice in one run. Multi-inverter SoC is the sum of each inverter's SoC line (GH#5423).
- **Simulated SoC RMS cannot tune battery settings**: a changed loss or rate changes the plan too. Measure efficiency from the log instead.
- **`Will recompute the plan as it is invalid` is logged on every recompute**; only `Recompute, previous plan is invalid...` means it was. A recomputing run's first `Best export window` is the fresh list, not the plan in force; the 8-hourly config refresh adds an extra run.
- **The goldens compare only the four window/limit arrays** (`charge_limit_best`, `charge_window_best`, `export_window_best`, `export_limits_best` passed through `export_limit_sort_key()`); `plan_final.json` is human output, never diffed — a PR that only adds fields or attributes to the plan JSON needs no golden regeneration. A replay's `plan_final.json` mirrors the live publish path (`run_single_debug` passes `show_scenarios=True`), so replayed plans carry the live scenario fields. (verified 2026-11-08)
- **The dump's rate tables sit back-to-back with no separator** (`rate_import`, `rate_import_base`, `rate_import_no_io`, `rate_import_pre_saving`, `rate_import_replicated` ...): a line-range read across an unanchored end mixes tables and can produce a completely wrong rate reading — grep the exact line bounds of each `^rate_` key before extracting. (GH#5902, verified 2026-11-01)
- **The per-candidate export metric table needs no instrumentation.** Via a `TEST_REGISTRY` entry calling `run_single_debug(..., debug=True, redo=True)` the `Try optimising export window(s) N` lines land in `coverage/predbat.log`, each carrying a window→[metric, cost] map across export lengths plus the export-off baseline entry — enough to settle "which export start scored what". A `--redo` replay re-segments cheap bands, so compare marginal deltas, not absolute metrics, against the reporter's replay table. (GH#5860)
- **On a money-losing-plan ticket, read the dump's `plan_preclip` first** — it is the retention gate's own artifact, stored per-minute in the dump; compare it against the published `export_window_best` before trusting any replay. And `--redo` overwrites dump-probe edits of `high_export_rates` (the redo path re-runs `rate_scan_window()` into it): replay no-export by flipping the dump's top-level `calculate_best_export`/`set_export_window` lines and emptying `export_window:` instead. (GH#5943, verified 2026-11-03)
- **A dump carries two config sources; only one is live.** The flat sorted args (`best_soc_keep: 4.0` style, below the rate tables) is what a replay actually reads — edit those to test what-ifs; the `value:` fields in the CONFIG_ITEMS section feed only the "changed items" printout, which keeps listing the pre-edit value after a hand edit (verified 2026-11-05: an args edit moved the metric 701.05→696.41 while the changed-items list still printed the old value). (GH#5987)
- **`predbat.plan_html` inside the dump's `dashboard_values` carries the full projected plan table** — its Totals column over time is the model's own cumulative-money trajectory, enough to settle "does the model think this wins" without running a replay. (`dashboard_values` is not on the dump exclude list.) (GH#5999, verified 2026-11-13)

### Tests and the C++ kernel

- **Do not rebuild the kernel binaries while triaging**: the `.so` files are committed and CI-built. A `scan_soc_range` count of 0 over a full plan means the kernel served it (GH#5408). After a `.cpp` edit delete the local `prediction_kernel_lib.so`; a loadable build is not rebuilt.
- **New kernel context arrays need `ContextStore` copies.** `pk_context_create` copies per-step arrays because the ctypes buffers are freed; a missing `ContextStore` vector/`assign`/`.data()` dangles silently, giving wrong values, not a crash (2026-10-18).
- **Kernel and Python can choose equal-scoring but different plans.** The kernel ignores the levels pass's `step=30` fast mode; `enable_fast_mode_levels: False` does not disable it, as `optimise_levels_pass` sets `fast_mode` per region (2026-10-20).
- **The kernel returns its scalar results already rounded to 4dp** (PR #6112; described in docs/developing.md's parity notes) — differences above 4dp between kernel and Python are expected, not a parity bug.
- **Export instructions are `(mode, target, power)` tuples since the split, with a permanent legacy decode of bare numbers** (`export_target_of()` of a bare value is `int(limit)`, None for freeze/idle; sentinels: exactly 99.0 freeze, ≥100 idle). Unit tests usually feed bare floats, so a regression confined to the tuple path passes the suite — pin both forms. (GH#5997)
- **`--test <name>` resolves through `TEST_REGISTRY`, not file names** (`dynamic_load_car` is in `test_dynamic_load.py`); a wrong name gives a green run with zero new assertions (GH#5407). The fourth tuple field is the slow flag.
- **The suite aborts at the first failure.** A raising test aborts the run (the registry loop `test_failed = func(my_predbat)` has no try/except), and some module runners (e.g. `run_kraken_tests()`) return at their first failing `test_*`, so one FAIL proves nothing about later tests; rename them to `xtest_` one at a time (PR #5641).
- **CI got slow: read the step timings before the tests.** `gh run view <id> --json jobs` gives per-step times, and the log's `PASSED in` lines rank the tests. In Nov 2026, 4m20s of a 14.5 min job was pip compiling numpy from source: `python-version: 3.x` had moved to a Python that the pinned numpy had no wheel for. check-yaml spent 48s on the `coverage/cases` dumps. A YAML parse or dump in a test runs at about 1s per MB even with libyaml, so look for one repeated in a loop (`read_debug_yaml`, `create_debug_yaml`, `load_scenarios`). `inspect.stack()` reads source for every frame; walk `sys._getframe()` instead (2026-11-09).
- **A test that reaches a vendor API passes anyway.** Fake credentials get a fast 401 that the component handles. When the call fails without a reply, the component retries with real sleeps: `deye_api` went from 1.8s to 28s, and `ge_cloud` ran for minutes. `tests/network_guard.py` now fails any test that makes a non-loopback DNS lookup or connect. Its message names the code line and the test line, and the event-loop `getaddrinfo` hook gets past aiohttp's executor thread, which loses the stack (2026-11-09).
- **Skips can count as passes.** `run_nordpool_test()` returns False (pass) on a download failure (the fixture is committed, PR #5799), and CI plus `coverage/setup.csh` install only `requirements.txt`, so `if have_<pkg>:` gates run only their skip path (GH#5715).
- **A passing test proves nothing when the fixture encodes the bug.** Seen: flat-rate fixtures, identical inverters, zero-iteration loops, `_mk_get_ctx`'s `json_body or {}`; a log-grep "not called" check is vacuous if the method is a silent stub, so use a calls counter (GH#5718). `TestHAInterface.get_state` returns `""`, not `default`, for a missing attribute (PR #5131); window asserts must check `start < end` (PR #4943); for address-reuse guards assert the object is pinned (`gc.get_referrers()`), as `tests/test_secrets.py` does (GH#5171).
- **MagicMock bases wake up host hooks.** A MagicMock `self.base` passes `getattr(base, hook, None) is not None`, so a new hook needs `base.<hook> = None` in those doubles (PR #5819).
- **Stub and constructor shapes.** `Execute.__new__` stubs lack base methods (GH#4965). `ComponentBase.__init__` aliases the live shared `base.args`; prefer `Cls.__new__` plus explicit `base`/`log`/`prefix`/`args` (unaudited for actual mis-renders, PR #5211). A mock that skips `ComponentBase.__init__` must set `self.base` (None is enough) once the component reports discovery: without it `report_discovery()`'s `getattr(self.base, "components", None)` raises AttributeError, swallowed by `refresh_discovery()`'s catch-all into an every-cycle "failed to report discovery" warn that poisons a last-log-line assertion (tests/test_temperature.py, PR #5936).
- **`self.base.set_read_only` is `True` until the first `update_pred()`**; read `get_arg("set_read_only")`. The charger mixin and wallbox were fixed in PRs #5793/#5798; `gecloud.py` and `gateway.py` still read the attribute first (checked 2026-11-05).
- **`run_execute_test()` scenarios inherit fleet state from the previous scenario.** `total_inverters = len(my_predbat.inverters)` is whatever the last scenario left (mixed-fleet tests silently assume 2), the `reserve=` kwarg is fleet-total kWh divided by that count, and `assert_soc_target` can pass through the reserve-driven reset-to-100 fallthrough rather than the target split — work out the member count, the per-inverter reserve and which branch writes the target; per-inverter split targets are only asserted in the `check=True` rig. (PR #5906 review, 2026-11-02)
- **Car-slot dicts handed to Predbat are mutated in place; the deep copy in `calculate_yesterday()` is a backup, not a shield.** It deep-copies at entry and replaces the list at the end, so during the reconstruction external owners of the slot dicts still saw their contents written; the two in-place writers are `yesterday_reconstruct_car_slots()` (with `car_energy_reported_load` on) and `dynamic_load_car_check()`. The random-scenario harness shared its slot dicts between runs until PR #5946 (2026-11-05) added the per-slot-dict copy — anything else replaying scenario objects needs the same. (GH#5946)
- If PR #5953 lands as drafted, car-slot consumption splits in two — `in_car_slot()` (point membership at the minute, first match wins) for ungrouped cars and `car_slot_average()` (overlap average over `[minute, minute+step)`, summing all overlapping slots) for cars in `shared_power_groups` — so a car-slot semantics change must land in both Python sites plus the C++ kernel, and `test_kernel_parity` would not exercise the shared-power path (its coverage there is a paired-engine scalar test). (PR #5953, open 2026-11-03)

### Clocks and time

- **`midnight_utc` and `now_utc` are local time**, in `ComponentBase` and `now_utc_exact` too. Use `.astimezone(timezone.utc)` before a `Z` suffix or an API window, and test with a BST date (GH#5572, GH#5693). `time_abs_str()` prints local time (GH#5036).
- **Build test dates from Predbat's clock**: anchor to `my_predbat.midnight_utc` and pin both clocks (PR #4877, PR #4998). Storage-cache expiry is the exception (real clock). `ComponentBase.midnight_utc` is a property re-reading `base.now_utc`, so a component fixture built with `__new__` plus a MagicMock base can replace the clock after construction (PR #5843 review).
- **The quick suite fails 00:00–01:00 local in summer on main** (2026-11-05): the teslemetry weekday test raises and aborts the run, and `test_solax.py`'s month test fails with an empty detail (grep `**** ERROR:`). Check the clock first.
- **`minutes_now = 0` hides time-of-day bugs.** History-index code needs a test at non-zero `minutes_now` (GH#4732). A pin-guard test is vacuous when the pin equals the residue (`FIXTURE_MINUTES_NOW`).
- **`timedelta.seconds` wraps into [0, 86399].** Use `abs((a - b).total_seconds())`; the button-press site was fixed in PR #5697 (GH#5694). Sites whose cache cleanup caps age below 24 h are fine.
- **Naive-tz sweeps after `strptime_aware()`.** It raises on missing tzinfo, so a `%z` site's naive handling is dead, and a bare-statement `.replace(tzinfo=...)` is a no-op. Watch for orphaned F401 imports (GH#5695).
- **CI's `python-version: 3.x` resolves to different CPythons per runner**; check `Successfully set up CPython` in the job log (PR #5653). The AST guard `offset_strptime_calls()` misses attribute and `BinOp` formats (2026-11-05).
- **`HAHistory` lags up to 2 minutes, and smoothing back-fills the gap**, so moving a marker to now loses the tail; count only the uncounted delta (`car_manual_soc_track()`, PR #5752).

### Reading the code

- **`self.base.args` holds Predbat's own dummy entity ids.** `create_entity()` ids pass `is_entity_id()`; use `user_configured_entity()` (PR #4745). Since PR #5126 Inverter objects persist and `refresh_config()` re-reads config every cycle (GH#5099).
- **`inverter_source_active()` is fleet-wide**, and `rest_data` has gone (since #4864). `create_missing_arg()` pads with `None`.
- **`re:` arg values are full-matched `^...$`** (`resolve_arg_re()`, GH#5677); when the pattern has capture groups the value is replaced by group 1 — why templates wrap patterns as `re:( ... )`. On a list or dict arg the outer call's `matched` comes back `True` unconditionally (failed items become `None` + a warn), so indexing `[0]` on a list arg is a vacuous match check in tests. (GH#5931, verified 2026-11-10)
- **Sign conventions.** `grid_power` is negative on import (`grid_power_invert` exists for meters that disagree); `battery_power` is positive while discharging. Find out which convention a sign report assumes (GH#4797).
- **Throwaway event loops in component events.** `select_event`/`switch_event` presses run under `asyncio.run` on a fresh loop, which breaks a persistent `aiohttp.ClientSession` or `asyncio.Lock`; hand the work over with `run_coroutine_threadsafe` (fixed for Hanchu in PR #5684).
- **Two loops over one slot.** A `TypeError` against `None` deep in the plan often means two loops over one slot drifted apart (PR #4943).

### Reviewing PRs

- **A clean auto-merge can still be a semantic conflict.** Run the full `run_pre_commit` (PR #4645).
- **Check base staleness first.** The fix may already be on main, and resolving a test conflict can delete main's test (PR #4756).
- **Stacked-PR squashes.** A `(#M)` squash suffix on PR N's head commit means its diff spans both PRs (PR #4186). A stacked PR — one whose base is another PR's branch — also shows state MERGED the moment the squash lands on that base branch, with a `mergeCommit` oid nowhere in main's history and nothing on the default branch; check `git merge-base --is-ancestor <mergeCommit> origin/main` before trusting "merged", and review the consuming PR's diff as the whole stack. (PRs #5591/#5363, 2026-11-10)
- **A review's `commit_id` (REST `commit.oid`) is the head at submission and never updates.** To judge whether an approval covers the current head, compare it to the PR's head: REST `/pulls/<n>/reviews` (fields `user.login`/`state`/`commit_id`) suffices without GraphQL, for which some triage permission modes deny `gh api graphql`. A later CHANGES_REQUESTED/DISMISSED by the same author supersedes an earlier APPROVED, so filter `state == "APPROVED"` with `commit.oid == headRefOid`; bot reviews post as state COMMENTED and satisfy no approval gate. (PR #5942, 2026-11-02)
- **Fork PRs can carry pasted truncation banners.** Grep the head tree for `truncated output` and `Total output lines`, confirming with `grep`, not Read, which adds its own banners (PR #5766).
- **CI runs the quick suite in the `pre-commit` job**, so "tests didn't run locally" does not mean untested; check the touched modules' slow flags (PR #5346).
- **Docstring coverage (interrogate) and flake8 are enforced nowhere** (re-checked 2026-11-10) — CLAUDE.md's Code Quality section does say "100% coverage required (interrogate)", which is what misleads reviewers: missing docstrings, including in test files, are not an enforceable finding. (PR #5810)
- **GitNexus is indexed from main.** On a PR branch read `detect_changes()` as "which files", not "which symbols" (PR #5143).
- **Re-running `/pr-review` on an unchanged head duplicates the review.** Post a follow-up with `comments: []` instead (PR #5645).

### GitHub and tooling

- **`gh issue list --search` without `--repo` searches all of GitHub.** Always pass `--repo springfall2008/batpred`, and distrust an empty result: fetch the exact title, typos included (GH#4705, GH#4973), and search bare `#N in:body` and the reporter's own issues (GH#5420).
- **`gh api` permission rules match literal prefixes.** Put flags after the endpoint. Events come back oldest-first, ascending within a page, so `gh api --paginate repos/<owner>/<repo>/issues/<n>/events` piped to a filter and `tail -n 1` is the most recent — the owner-gate workflow reads the last actor of a label exactly that way. The `comments: 0` in a review-creation response is unreliable (PR #5759, PR #5143).
- **jq on `--json comments`.** Use `--jq '.comments | length'`; plain `length` counts the wrapper's keys (GH#5349).
- **Triage permission-mode routes.** Read a branch doc with `git fetch` plus `git show <branch>:<path>` (GH#5291). For another repo use WebFetch, after checking its default branch (GH#5417). Plain `git` from the repo directory only: `-C` and `cd` outside the working dirs are refused as well.
- **When `git fetch` is itself denied, verify the tip over HTTP** — `WebFetch https://api.github.com/repos/<owner>/<repo>/commits/main` returns the real remote sha without `gh`, so compare it with local `git log`/`git describe --tags` and report the sync as done-by-verification, not skipped. A locally cached `origin/main` from an earlier fetch still serves range checks. (verified 2026-11-07)
- **Kraken (EDF/E.ON) issues have no component label.** Do not guess `Octopus`.
- **Merge box shows `owner-gate` "Expected — Waiting for status to be reported" though the API says it passed.** A `GITHUB_TOKEN` check run is filed into the *oldest* Actions check suite on the commit, which the merge box never reads, however green `gh pr checks` and the GraphQL rollup look (`mergeStateStatus` still `BLOCKED`, seen #6001/#6007/#5989/#5920). Fixed 2026-11-06 (PR #6008): the gate posts an `owner-approval` **commit status**, which belongs to no suite, and the job is deliberately named `owner gate evaluator` — different from the required status name — so its own green tick cannot satisfy the requirement. Read the verdict from `/commits/<sha>/statuses` (the newest status per context counts, so a stale pending beside a newer success only exists while a correcting run finishes); a PR needs one more gate event (an auto-merge toggle) to get a status after the swap. The required `pre-commit` context is produced by the `code-quality` workflow's `pre-commit` job, which runs the owner-gate tests as a pre-commit hook on that workflow or its test file — not a workflow of that name, and not the TEST_REGISTRY suite. An admin merge, or a new head commit, gets a stuck PR out.
- **Every `labeled` event fires the owner-gate workflow, including the bot's own labels** — so a bot-labelled (BOT_REVIEW/BOT_TRIAGED) PR carries extra owner-gate runs and a pending `owner-approval` status until the owner approves. Expected, not a gate regression. (PR #5940, 2026-11-02; workflow reworked 2026-11-06+)
- **`/commits/<sha>/check-runs` defaults to `filter=latest`, hiding duplicate runs of one check name** — pass `filter=all` (optionally `&check_name=`) before concluding a commit carries one run. Check runs live on the sha, not the PR: a force-pushed-away head returns none from `pulls/<n>/commits`, so locate it via a review's `commit_id` or `actions/runs?head_sha=<sha>`. (PR #6004 review, verified 2026-11-06)
- **Repo rulesets are readable without admin.** `gh api repos/springfall2008/batpred/rulesets` (then `/rulesets/<id>`) answers the actual required checks/statuses and branch policy with the triage-bot token — use it before trusting a PR or issue description of the gating requirements. (PR #5978, verified 2026-11-04)

## What belongs here, and what does not

The journal is for what a future triage run would otherwise have to rediscover. Test every entry with one question: would it save time on a **different** issue?

- **Keep: techniques and traps.** How to replay a dump (`--redo`), test-order pollution, stale kernel binaries, the macOS local-network block. These apply to every investigation.
- **Keep, tightly: durable facts about a device or API.** One line, no story. "GivEnergy stores rates as a whole percent of capacity, rounded down" is about the hardware, not about the issue that found it.
- **Keep, short and dated: findings that explain a class of report.** "Car not charging because X" is useful when the same symptom comes back. Give the issue or PR number and the date, say how it was verified, and word it as "look here first", so the reader confirms it against the code.
- **Drop: per-issue narrative.** What was tried, what the fix was, why the alternatives were rejected. That belongs in the PR and the issue, where it stays tied to the code it describes. In the journal it goes stale as the code moves.
- **Drop: file paths and line numbers.** They drift with every merge, and a citation pointing at unrelated code misleads more than no citation. The area heading already names the module, so point at a function, a config item or a log line instead: those survive a refactor, and a reader can grep for them. Naming a file is fine when the file is the subject rather than a location: `apps.yaml`, a template, a test to run, or "`execute.py` has no AlphaESS case".

Write each entry in the same shape: the **symptom** (the log line verbatim, or what the reporter sees), the **fact or mechanism** behind it, and **where to start looking** (a function or config item). Then add the issue or PR number, and the date if it is a bug.

Entries go stale, so retire them:

- When the code an entry describes has changed, correct or delete the entry. Do not leave it marked as stale.
- Once a fix for a bug entry has shipped, cut it down to what a reader holding an older log needs ("fixed in PR #N") and drop the story. After about six weeks, delete it unless the mechanism is still a trap.
- Prefer sharpening an existing entry over adding a second one.

Keep it small. Every triage, review and journal-update run reads this file end to end, and at 730KB it cost them most of their turns. One fact per bullet, a few hundred characters at most. If an area's notes grow past about 3KB, consolidate them rather than adding more.

## Adding to this file

When an investigation turns up something that passes the test above, add a bullet under the right heading: the area under "Per-integration notes", or the topic under "Symptom → first place to look". Keep it short, name a function or config item rather than a file or line, and cite the issue number so the next reader can check the original.

If you are running under the triage bot you cannot edit this file directly — the clone is `reset --hard` before every flow, so the edit would not survive. Write the finding as a single markdown file in the queue directory named in your system prompt instead; the `/journal-update` flow folds the queue in once a day, re-checking each candidate against current `main` first, and opens a PR for a maintainer to merge.

Whichever route you take, the bar is the same and it is not "interesting": record what you **verified**, say how you verified it, and keep anything you merely suspect explicitly marked as suspected. A wrong entry here is worse than a missing one — every later run trusts this file, so a confident mistake ends up in a comment posted to a real reporter. Correcting or deleting a stale entry counts as much as adding one.
