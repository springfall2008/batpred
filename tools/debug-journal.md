# Debug journal

Notes distilled from maintainer debugging sessions and triage-bot runs on this repo (June–November 2026), written for whoever is triaging an issue next.

Every entry is an observation from a past investigation, not a statement about current main. The code moves. Use these as "look here first", confirm against the working tree before you put anything in a comment, and say what you actually confirmed rather than what this file says.

The file was compacted on 2026-11-05, from 730KB of per-issue detail down to the durable facts and pointers. If you need the full story behind an entry, the issue or PR it cites has it, and so does the last uncompacted version: `git show ea6ba38d:tools/debug-journal.md`.

## Replay the reporter's debug file

`predbat_debug.yaml` is a full state dump the harness replays against the current tree:

```bash
cd coverage
csh ./run_all --debug_file <scratch>/predbat_debug.yaml > <scratch>/replay.log 2>&1
csh ./run_all --debug_file <scratch>/predbat_debug.yaml --redo > <scratch>/replay-redo.log 2>&1
```

- `run_all` is a **csh script with no shebang** (`source setup.csh`, `rm predbat.log`, `python3 ../apps/predbat/unit_test.py $*`), so a bare `./run_all` under bash or `sh` dies with `OSError: [Errno 8] Exec format error`; invoke it as `csh ./run_all`. It also needs `coverage/` as the working directory, so a wrapper should set `cwd` rather than rely on `cd`.
- Grep the log first for the non-default config block (`- <item> = <value> (default <value>)`). Output: `coverage/plan_orig.html` (the plan as the dump stored it), `plan_final.json` (main's recalculated plan, one row per slot) and `<yaml>.actual.json` beside the input. Both are overwritten per run, so copy them out between dumps. The two "Wrote plan ... metric" figures can differ hugely (seen -79.86 vs -20.07) — read the per-slot rows, not that pair, as an old-versus-new score.
- Without `--redo` you replay the dump's own rates, load model and Octopus slots. `--redo` recomputes them. A dump from an install with `debug_enable` off — the normal setting — carries empty `pv_forecast_minute_step`/`load_minutes_step` arrays (the end-of-cycle free-memory path clears them), so `KeyError: 0` near `pv_forecast_minute_step` is a needs-`--redo` tell, not an old-dump one: current v9.6.x reporter dumps crash without it too. (GH#5860, GH#4766) A v8.x-era dump stores the same four dicts empty as well, but the series they derive from (`load_minutes`, `pv_forecast_minute`/`10`) are in it, so a faithful replay rebuilds them with `step_data_history` instead — the harness only does that on the redo path (`reset_load_model = redo`), and `--redo` also recomputes rates, load and Octopus slots. (verified 2026-11-14 on #4124's dump)
- A replay cannot reproduce live ML-forecast choices, so a mismatch in marginal ~10p slots is inconclusive (GH#5213); grep the reporter's log for `Best export window` / `Best charge window`.
- The triage bot runs tests through `tools/triage_test.sh <test>` and forward replays through `python3 tools/triage_replay.py`; for a plain dump replay it uses a temporary `TEST_REGISTRY` entry calling `run_single_debug(..., redo=True)`, which also re-derives `set_rate_thresholds()`/`rate_scan_window()` (a dump stores end state, GH#5221).
- `Replay input:` log lines (PR #5427, 2026-10-12) rebuild a cycle's inputs from the log alone (formats pinned in `tests/test_log_replay_inputs.py`). The forward replay's parser (`tests/replay_forward.py`, PR #5363) makes `log_replay_*` a contract; unknown lines are skipped silently. A repeated identical line means the value changed, or (PR #5591, merged 2026-11-10) the first run of a new day — the signature includes `midnight_utc`, so each line logs once a day at most.
- Reading a dump directly (GH#5509): rates and windows use absolute minutes of the dump day, `predict_*_best` minutes from now, and the `*_today` arrays are minutes-ago convention (index 0 = now, larger = further in the past; recovering `minutes_now` from them works). `export_window_best[].target` is not the `export_limits_best[]` level; decode with `export_mode_of()`/`export_target_of()`.
- **Forward replay** (PR #5363): `./run_all --debug_file X.yaml --replay_log predbat.log` steps through the log's later runs, re-planning where live did and comparing plans (flags in `docs/developing.md`). For a plan that went wrong after the yaml was taken (GH#5423) or kept changing (GH#4865); `--override name=value` for what-ifs. Needs a log running past the yaml, and a yaml after any restart or `apps.yaml` change; concatenate rotated logs oldest first. Most reporters take the yaml when they file, at the end of the log, which leaves nothing to replay (GH#6150): ask for a History-view snapshot from the start of the period instead. `tools/triage_replay.py` checks this before running (exit 3).
- **Forward replay modes.** Exact (default) takes the logged SoC each run, and with `Replay input:` lines matched live plans line for line over whole days (Oct 2026); `--replay_simulate` steps the battery itself, to try a fix. The summary counts export windows only: use `--replay_chart`, and diff `predict base/best` lines against the replay's own `predbat.log` for costs.

Loader failures before Predbat code runs:

- `could not determine a constructor for the tag '!secret'`: `DebugYamlLoader` has no `!secret` constructor (GH#5748); sed captured args to dummies in a copy.
- numpy dtype `SystemError: bad argument to internal function` (v9.1.0+ dumps, GH#5205): fixed in PR #5892 (2026-11-01) — new dumps carry plain numbers, and the loader constructor replays the tagged old ones.
- `found unhashable key` from `io_slot_log_gate` (v9.3.8, GH#5569): fixed in PR #5575 (2026-10-17).
- Without `apps/predbat` on `sys.path` a load dies at the first `!!python/object` tag it cannot import. A newer dump on an older tree fails with `No module named 'control_monitor'` (GH#5719); null `control_monitor:`/`control_ledger:` in a copy. Both have been left out of dumps since they joined `DEBUG_EXCLUDE_LIST` (Nov 2026).
- `DebugYamlLoader` is a safe loader (Nov 2026): dumps come from public issues, and the old unsafe one ran whatever a `!!python/object/apply` tag named. It rebuilds only what is in `DEBUG_YAML_OBJECT_CLASSES` (`MinuteArray`, plus the two control objects for older dumps), numeric `array.array`/numpy values and tuples. `could not determine a constructor for the tag 'tag:yaml.org,2002:python/object/apply:X'` means a dump carries a new call-style value: add a numeric-only constructor for it, never a generic one. `Warn: ... load as plain dicts: X` means a new `!!python/object` class: add it to `DEBUG_YAML_OBJECT_CLASSES`, or to `DEBUG_EXCLUDE_LIST` if a replay never reads it. The safe C loader (`CSafeLoader`) parses as fast as the unsafe `CLoader` (0.91 s on a 5 MB dump; the pure-Python loaders take ~5 s).

Normal lines, not the bug: `Prediction kernel stale binary ... - using Python engine` (plan still correct) and `Config item ... is below the minimum ... - clamping to ...`.

## Debug yaml can contain real secrets

Read dumps locally and never quote a raw block publicly unchecked.

- Pre-v8.55.0 dumps can carry `args_from_apps_yaml` with resolved secrets (GH#4765); masked at source since PR #4910, so no reason to tell a current reporter to rotate.
- `mask_secret_args()`/`is_secret_key()` match `_key`/`password`/`secret`/`token` in top-level keys. `annual.py`'s `scrub_secrets()` is recursive and masks differently (GH#4770).
- `debug_history_enable` defaults True and snapshots ~3-hourly into `predbat_debug_history.tgz`, independent of `switch.predbat_debug_enable`.
- Snapshot retention is ~45 h: pruned by both count (`debug_history_count`, default 15) and age (`debug_history_interval`, default 3 h), and a force-capture just after a scheduled one doesn't double-retain. An evidence-request deadline is capture time + ~45 h, not a neat 48 h boundary.
- The Plan→History Debug column's snapshot download is served by Predbat's own web server (`/debug_history_download?id=`), so "I can't get files out of the Docker container" can still be met in a browser. And for "what did Predbat command during the window", ask for HA recorder history of the exact window, not the newest snapshot's ledger — the ledger keeps the latest confirmed value per entity, so window-start writes hide behind window-end restores. (GH#5852, verified 2026-10-29)
- Logs are redacted at write time (`LogRedaction`, `log_secrets.py`).
- `!secret` resolves only via the private `SecretYamlLoader`. Bare `yaml.load(...)` hits in the tree are ruamel, not PyYAML.
- Issue line numbers may resolve against a PR branch, not main. If `gh api .../pulls/<n>/comments` is denied, use `gh pr view --json`.

## Check configuration before code

Pull the non-default list first: `combine_export_slots`, `metric_min_improvement_export`/`_plan`, `best_soc_keep`, `metric_battery_value_scaling`, `metric_battery_value_export_scaling`, `metric_battery_cycle`, `metric_cloud_enable`, `load_scaling*`. "Configuration" is a legitimate outcome.

- Replay one setting change at a time and compare decisions, not the metric (an emptier final battery always looks cheaper). `best_soc_keep: 0.0` and `metric_battery_value_export_scaling: 0.8` are defaults.
- Read `optimise_all_windows()` end to end before calling a pass dead. The commented-out swap call is not the live one, which runs last (GH#4478).
- Near-parity export tariffs (GH#4840): leftover SoC is credited at `battery_value_rate()` (replacement cost), a ~1% margin, so `metric_battery_value_scaling` below ~0.987 flips exports. `metric_cloud_enable: False` predicts zero import.
- `battery_value_rate()`'s four inputs are built at different fetch stages (PR #5872, merged): `rate_max_base` (raw tariff), `rate_export_max_forward`/`rate_export_min_base` (post-replicate, pre-session, pre-override), `rate_min_forward` (post-replicate + IOG overlay, pre-session — built in `fetch_sensor_data()`, no longer in `rate_scan()`); `rate_export_min` stays session-inclusive by design. On a "stored-energy credit misbehaves" report, check the build point first. Traps: code installing a rate table outside fetch (a test `reset_rates()`, a replay harness) must reset `rate_min_forward` itself or a stale leftover silently prices the replacement cost; replaying an OLD debug dump restores its session-inclusive `rate_min_forward` and lacks `rate_export_min_base`, reproducing the old behaviour — run `--redo` to see the fix. (verified 2026-11-08)
- Charge-to-export "loss" (GH#5069): naive arithmetic omits the end SoC credit and displaced peak house load.
- Non-GBP tariffs (GH#3683): `metric_min_improvement*` gates compare unconverted against the minor unit, with pence defaults, so plans churn. Fixed by apps.yaml `currency_scale` (PR #6156, 2026-11-12): `apply_currency_scale()` multiplies the min/max of every money item by it, so a CZK/DKK/NOK/SEK install stops hitting `Config item ... above the maximum ... clamping`. It only raises a cap, never the defaults; a value below 1, `nan` or `inf` is ignored with a warn. Trap: the `snapshots` unit on `debug_history_count` contains a `p` — pick money items by exact unit, never by substring.
- Money-losing plans: grep `Previous plan best metric is ... and new plan best metric is ...`. Positive deltas under `metric_min_improvement_plan` mean retention (GH#5616); negative deltas every cycle mean lock-in on stale windows, which lowering the gate cannot help (`should_replace_plan()`, GH#5686).
- Levels-pass exports that paid only in the PV10/PV90 blend, which `metric_min_improvement_export` could not remove and the write-backs restored (GH#3376/#5633, GH#5969): fixed in PR #5977 (2026-11-05, `export_gate_metric()`). Per-5-minute charging came in PR #5874 (2026-10-31).
- `best_soc_keep` is only a soft `metric_keep` penalty, never a window or reserve (GH#4961). `manual_soc_keep` and alert keeps (default 100 per alert) force `keep_minute_scaling >= 10` weighted by import rate, so are inert in 0p windows (GH#5162). Fixed in PR #6140 (2026-11-12): with a manual/alert floor active the keep penalty's import rate, and with a `manual_soc_max` ceiling its export rate, are floored at `KEEP_TARGET_MIN_RATE` in both engines — at a 0p/negative rate the target now still costs something, while plain `best_soc_keep` stays rate-weighted; a 30-minute slot still underprices the miss by ~5/kWh (the docs point at a manual charge slot). Only `set_reserve_enable` plus `reserve` is a hard floor.
- A "Predbat didn't charge before an Axle/saving-session event" report is usually config, not the optimiser. Check in order: `rate_low_threshold` set manually (a manual threshold caps the charge even ahead of a session; 0 = auto), `combine_charge_slots` on, `set_export_freeze_only` on (the export pass then only tries idle/freeze rungs, so nothing profitable to pre-charge for; #3994 open). Then the arithmetic (GH#5901, 2026-11-01): event revenue is bounded by discharge power × event length, so a pre-event top-up only adds post-event buffer worth about `battery_value_rate()` minus the refill price; an *additive* event boost (Axle, PR #4520) can never move a min-rate scan, so "no arb afterwards" may just mean base export is below the cheapest refill. No event-aware pre-charge config exists in `CONFIG_ITEMS`; the only hook is Axle's `binary_sensor.<prefix>_axle_event`.
- `HoldChrg` (within 1% of the limit, `set_discharge_during_charge` default True) is not `FrzChrg` (`is_freeze_charge()`).
- No charge-start hysteresis (GH#2513): the hold band needs `inv_target_soc_percent < 100.0`, so a 100% target is re-commanded every cycle.

`get_arg()`/validation traps that look like a feature silently off:

- `key:` (null) defeats the default for direct `get_arg()` callers (component args fixed since PR #5188, 2026-09-24). A quoted `'1'`/`'y'` coerces to False.
- Float-default truncation, e.g. `solcast_poll_hours: 4.8` read as 4 (GH#4925), was fixed in PR #4938 (2026-10-08).
- An enable-gated CONFIG_ITEM still returns its declared default while gated off (`get_ha_config()`).
- Unknown apps.yaml keys are ignored silently (GH#4999, open). `allowed:` is enforced only for string and integer types.
- Sensor-typed items reject numeric scalars (`not of type 'sensor'`); use list form (GH#2172).
- `get_arg()` consults `get_ha_config()` **before** the `self.args` lookup, and a value from that path comes back raw: `resolve_arg()`'s entity-id/sensor resolution (and `required_unit` conversion) runs only on the args path. Check which of the two supplied a value before expecting an entity id to have been resolved.
- `config_index` items are mutated on the shared `CONFIG_ITEMS` dicts: `load_user_config()` seeds each item's `default` from `args` and `expose_config()` writes `item["value"]`, which survives across calls. A test that re-runs `load_user_config()` must reset `value` (and restore `default`) first or the stale value shadows the fresh apps.yaml load — `test_fetch_config_options` Test 16 is the pattern. (PR #6098 review)

## Test-order pollution (GH#5079)

- Since PR #5102 each registry test gets its own `create_predbat()`. Module- and class-level state can still leak (`PLOT_ENABLED`, `LogRedaction`'s lock).
- From `coverage/`: `./run_shuffle --hunt --quick` bisects to a (culprit, victim) repro. Also `--bisect <seed>`, `--campaign N`, and `./run_all --shuffle [--shuffle-seed N]`.
- Victims cluster in `model`/`kernel_parity` (tight assertions). Before fixing, check the culprit really touches the victim's state.
- `run_pre_commit` runs the quick suite only after the hooks pass, so a log ending at the hooks is not a green suite.

## The shared clock is rewound for ~0.8s every hour

`calculate_yesterday()` sets `midnight_utc` back a day and `minutes_now = 0` on the shared `PredBat` (`# Fake to yesterday state` / `# Save state`), unlocked, while other threads read it live. Present on main 2026-11-05.

- Off-thread readers are hit: manual overrides (GH#4900, fixed with `manual_time_origin()`) and component PV buckets (GH#4804). `ComponentBase` derives its clock from `now_utc` since 2026-09-13/14; `PredBat` mixins such as `Octopus` still read the fake.
- Code inside the fake must pass the real `minutes_now` to history indexing (GH#5004).
- Suspected, unverified (code-read 2026-10): `decode_octopus_slot()`, `dispatch_billed_off_peak()` and zero-kWh slot synthesis misread it (GH#4946). These affect History only.
- On a "shifted by one day" report, check this first. New off-thread code should derive time from `now_utc`.

## Per-integration notes

Grep for the named symbol rather than trusting a line number. Each area lists durable facts and "look here first" pointers, one per bullet.

### Fox (`fox.py`)

- Cloud errno 42015/44096 = setting unsupported by the device (`FOX_SETTINGS_UNSUPPORTED_ERRNO`); it is marked unavailable and never polled or written again. WorkMode is a select, ExportLimit a number. Since PR #5840 (2026-10-30) the three unsupported-setting lines log at Info (the same errno from a non-setting endpoint still warns); a Warn form in an attached log just dates it to pre-#5840.
- `soc_max` 4x too big when `batteryList` holds four `bmu` entries with one serial (AIO ESS, EVO 10-5-H): fixed in PR #5629 (2026-10-24). Unverified: whether `batteryDesignCapacity` totals a multi-pack stack.
- Fox device/detail `capacity` is an integer field, so fractional-kW models read low (`H1-3.7-E-G2-WL` read 3 kW, GH#5938): until PR #6081 (2026-11-10) only ".5"-suffixed deviceTypes were corrected (PR #4527). Both `-inverter_capacity` and `-battery_rate_max` funnel through `capacity_watts()` — the rate is min-capped with the truncated capacity and stored back destructively — and with `fox_automatic` on, apps.yaml's `inverter_limit`/`battery_rate_max` are re-bound to those sensors, so literal numbers there are inert. A dump's `sensor.predbat_fox_<sn>_info` attributes (`inverterCapacity`/`deviceType`) prove the truncation without raw-API access; read older logs as "fixed in PR #6081".
- `fox_automatic: true` re-`set_arg`s `soc_max` every cycle and it is not in `CONFIG_API_OVERRIDE`, so apps.yaml cannot override it; escape hatch `fox_automatic: false`.
- With the Mode Scheduler deleted, `compute_schedule()` shows the charge window from the legacy `forceChargeTime` read, which Predbat cannot clear (`set_battery_charging_time()` has no production callers; GH#4939, re-checked 2026-11-05).
- A Fox Cloud `didn't complete got X` is a genuine failure, but the cloud verify read is slow: old value at 3s, new one after ~18s.
- Reserve never reads back from the device (GH#5821, open), so "Current reserve is X%, already at target" is Predbat echoing its own write. Fox accepts `minSocOnGrid: 100` yet still discharges: declared ranges are acceptance, not enforcement.
- Device MaxSoc is published (`number.<prefix>_fox_<sn>_setting_maxsoc`, writable) but never bound to the planner (GH#5395, open); `automatic_config()` binds only `soc_max`/`reserve`/`battery_min_soc`/`export_limit`.
- FoxESS HA/modbus path (`FoxESS`, not `FoxCloud`): the stock template binds `reserve:` to `number.foxess_min_soc_on_grid`; at 100%, `min_soc_on_grid` stops grid-connected discharge. `FoxESS` is `has_idle_time: False`, so `idle time is ...` programs nothing (GH#4961).
- Hold drain-block (GH#5704, verified 2026-10-23): `execute.py`'s hold-above-target branch called `adjust_charge_immediate(..., freeze=True)` on non-planner holds, so `charge_freeze_service` selected `"Back-up"`, which supplies no house load and pinned the battery. Fixed above the reserve in PR #5998 (2026-11-07): an inverter without a target SoC now stops the charge while SoC is above the hold reserve and freezes only once it reaches it. Below the reserve the freeze still applies; removing `charge_freeze_service` remains the workaround there.
- `ForceDischarge` in a `Fetch scheduler V1 returned` list does not prove a discharge window was written.
- Live telemetry is refreshed by an **age gate, not a timer**: `_needs_refresh("device_values", ...)` against `self.realtime_refresh_minutes`, on `ComponentBase.start()`'s fixed 60 s loop, so one request per inverter lands every interval plus run time (no early firing, no one-tick-short). `FOX_REFRESH_REALTIME` (5) is the default and `fox_poll_seconds` (60–1800, converted to whole minutes by `fox_poll_minutes()`) sets it since PR #6139 (2026-11-11); settings/production/static keep their own gates. A failed poll does not stamp `data_age` (which `_save_cache()`/`_load_cache()` persist), so it retries on the next tick and a reboot does not re-poll fresh data. On a "Fox data is up to 10 minutes stale" report, add the two ages: the datum is up to one interval old when read, then up to another plan interval old when the 5-minute cycle consumes it. (GH#6138)
- Test trap: `MockFoxAPIWithRequests` and its subclasses override `__init__` and never call `initialize()`, so any attribute `initialize()` sets is missing in every run()-based Fox test, and the runner reports it only as `ERROR: Fox API test failed with exception:` with an empty message. Seed new attributes in `MockFoxAPIWithRequests.__init__`; tests building `FoxAPI(...)` directly do go through the real `initialize()`. Red-run tip: stashing a source file the test imports a new symbol from fails on `ImportError`, which proves nothing about behaviour — revert only the changed logic line.
- Tests: `./run_all --test fox_api --test fox_oauth`

### Solis (`solis.py`)

- CID 636 (`SOLIS_CID_STORAGE_MODE`, Modbus 43110) is a bit mask. On "4B and above" firmware (`is_tou_v2_mode()`: CID 6798 reads 43605) per-slot registers (43707) alone drive timed charging and TOU bit 1 is refused, so CID 636 verify warnings are that refused bit, not a failed write (GH#4707). Do not infer V1/V2 from one read-back (GH#4774); keep the post-write `read_cid()` cache overwrite, which lets change detection retry. V2 writes the mode with slot 1, V1 at the window boundary (`claim_window_mode_assertion()`, once per window). A CID 636 report with no `setting storage mode to` lines came from the HA select handler `set_storage_mode_value()`, not `write_time_windows_if_changed()`.
- PV-only detection: `_reports_no_battery()` and `SOLIS_GRID_TIED_MACHINE_PATTERN` (`^S\d+-GR\dP`); Cloud alternates `batteryType` `'0'`/`'0.0'`, so match by value (`_reads_zero()`).
- Discovery beats apps.yaml (`overwrite=True`, grep `auto-discovery wins for this setting`) for `charge_limit`, `export_limit`, `battery_rate_max`, `battery_scaling`; only opt-out `solis_automatic: false`.
- Slot current cap (`slot_current_limits()`): CID 7224/7226 as read, else `SOLIS_SLOT_CURRENT_DEFAULT_AMPS` (60), lowered only by `--probe-ceiling` (GH#5068); the planner does not see the clamp, so set `inverter_limit_discharge`. `write_time_windows_if_changed()` defaults a never-read slot current to the cap, so no write is attempted — seed `cached_values` in fixtures. Verify echoes: the slot-current entity republishes the clamped cache at live voltage (`didn't complete got 3094.0` every cycle) and CID 5965's slot-SOC readback tracks live SOC (GH#4184); grep `CID 5967 ... is set to` for what reached the inverter.
- Parallel pair (GH#5556): the master's V2 slot current governs the group while 7224/7226 are per-inverter, so a pair under-delivered — fixed in PR #5909: the master's slot current is now written for the whole group (`solis_parallel_slaves`).
- API: `B0115` (datalogger offline) and `R0000` (200/day allowance gone) are never retried (`SOLIS_API_CODES_NO_RETRY`); `automatic_config()` retries every cycle; `_with_retry()` catches only `SolisAPIError`. Unclassified outage codes (`B0072`, `B0673` seen live) fall through and get no datalogger cooldown; B0673 carries B0600's message text, so classify by code, not text.
- Still live (GH#5093, open): `SolisAPI.run()` folds all inverters into one `poll_success`, so one unreachable unit holds startup in backoff (to 128 min); list working SNs in `solis_inverter_sn`. Still live (GH#5190, open): `int()`/`float()` accept `_`, so `"1234567890_00"` passes `parse_cid_int()` and `get_arg()` coercion — start here on "absurdly huge value, fallback never fires".
- Holds (PR #5265): `reserve` is CID 157, a floor only while CID 636 bit 4 (`SOLIS_BIT_BACKUP_MODE`) is set, so the bit is always set. Non-slot events wait for the next `run()`, beyond the 2 s verify. Older-log signatures: `export limit 0.48kW` (CID 499 100x small, PR #5625); `poll failed for <SN>: '<SN>'` (`KeyError` repr, PR #5733); `battery_scaling read as 0.0` every cycle, plan unaffected (warns once since PR #5841).
- `H M` types (`GS_fb00`, most cloud subtypes) rewrite time entities every cycle by design (#1529): first suspect for "hammers my Solis with writes". Test trap: `number_event_handler()` takes the SN from `parts[0]` of the entity id, so use underscore-free mock SNs (`SN0EXPORT1`).
- `charge_discharge_time_windows[sn]` is startup-decoded once (`decode_time_windows*()` fire only on the first cycle) and plan-driven afterwards; slot entities go stale if the startup decode fails, and everything else converges through `write_time_windows_if_changed()`. When adding a `seconds % 300`/`% 3600`-gated block inside `run()`, check the pre-existing `run(first=False)` tests at 300/600/3600 — they exercise it silently. (PR #5864)
- Demo / read-only handover: `Warn: Solis handover unconfirmed` latches while `set_read_only` is on and clears only through `run_cycle()`'s control section (`solis_control_enable` on, read-only off; monitor-only installs take the ordinary reset). Per-step budget is 60 s without a completed step, 300 s per inverter, each written CID able to pay the 5 s verify settle; `Schedule cleanup rejected for CID ...` is a refused write, and both `was not confirmed` and `cancelled before confirmation` mean timed out. A Demo entry costs ~8+4N API requests (N slots) of the ~200/day allowance — check for slow or retrying reads before assuming the inverter refused. (PR #5863)
- First question on a Solis hold-enforcement report: which route is the install on — the FB00 entity path (see *Solis Modbus*), Predbat's own Solis Cloud component (CID 636, sets the Battery Reserve bit unconditionally, freeze slots = `Self-Use - No Grid Charging` with 1% hold hysteresis), or a third-party select (Pho3niX90 solis_modbus `work_mode`: meaning-equivalent options, so supporting it needs a code-side name map, not config). A user-side HA automation keyed to `predbat.status` transitions can defeat any hold — it fires exactly during the hold; landed `backup_soc` writes with the physical mode still Self-Use mean landed writes ≠ enforced hold. (GH#5852)
- `has_reserve_soc: false` types (all Ginlong custom types; `templates/solis_local.yaml` ships `solis_rc` since PR #5881): a user-wired `reserve:` entity is display-only — read once into `reserve_percent_current` in `refresh_config()`, then replaced with a Predbat dummy, so `get_arg("reserve")` and `adjust_reserve()` land on the dummy, never the user's entity. (verified 2026-11-12)

### Solcast (`solcast.py`)

- `max_kwh` is 9999 on the Solcast direct and HA-sensor paths (set only for Forecast.Solar/Open-Meteo), so "Raw forecast exceeds the array ceiling" never fires for Solcast (GH#4730, open).
- **P90 (and P10) roughly doubles every fetch on the HA-solcast integration, resetting when the integration republishes, P50 sane throughout** — the HA state cache holds attribute containers by reference and `get_state(..., attribute=...)` hands back that same object, so `pv_calibration()`'s write-back of the scaled band (it exists so `detailedForecast` publishes calibrated values) rescaled the band it had already scaled. Fixed in PR #6055 (2026-11-09) by copying the entries in `fetch_pv_forecast()`; P50 never compounded because its calibrated value goes to the separate `pv_estimateCL` key. The general rule: copy a `get_state()` attribute container before handing it to code that mutates it, when the same unchanged sensor state will be fetched again. #6049's first triage blamed the integration's dampening — wrong.
- A PV log cannot settle what was fetched: the `Replay input: PV forecast changed` rows log `pv_forecast_minute/10/90`, the **post-calibration planner series**, not the raw attributes. A ~30-minute step pattern in them is Predbat's own read cadence (`SolarAPI.run()` re-fetches every `plan_interval_minutes`, default 30, and when data is >60 min old), never the provider's poll interval; an integration republish shows as a reset. `detailedForecast` is **kW per slot**, not kWh: per-slot values sum to 2× the sensor's kWh day total on 30-minute slots (4× on 15-minute, factor detected, #2544), so ×0.5 sanity-checks any pasted sensor state.
- `fetch_pv_forecast()` order: Forecast.Solar with `forecast_solar_open_meteo_first` → Forecast.Solar (backup on empty data only) → `open_meteo_forecast` → Solcast direct → HA sensors. So `open_meteo_forecast` means Solcast is never used, and `solcast_api_key` beats `pv_forecast_*` sensors.
- Solcast direct has no fallback (GH#5545, open): a failed call returns the stale cache, so data is never empty and the plan ages; a backup must key off `solcast_last_success_timestamp`.
- `sensor.<prefix>_pv_forecast_h0` state is calibrated; raw is the `now` attribute. Since PR #5121 calibration reads `..._pv_forecast_h0_uncalibrated`. `history_attribute(attributes=True)` drops points lacking the key unless `fallback_to_state=True`.
- `sensor.<prefix>_pv_forecast_raw` has one publisher, the Solcast component, and it always sets `relative_time` — a missing attribute (or entity) means "no forecast source configured", not a malformed value. Since PR #6014 the warn fires only for a present-but-unparseable value. (GH#6013)
- Open-Meteo applies ensemble P10/P90 as ratios to the deterministic P50, so a re-issued deterministic forecast can push `pv_estimate90` implausibly high, bounded only by `1.2 x kWp` (PR #5347 fixed calibration-less P10/P90).
- Dull-day calibration inflated by per-minute `dp2()` rounding: fixed in PR #5802 (GH#5690). On "small values misbehaving", grep `dp2(`/`dp4(` in accumulation loops first.
- **Calibration is a 28-day evidence store, not a 7-day window** (`pv_calibration.py`, PRs #6231/#6233): each day keeps the per-slot uncalibrated forecast and actual (clipping imputed) plus the day's peak, and `fit_pv_calibration()` derives a day factor and a half-hour shape, each shrunk toward 1 by its own day-to-day noise (`pv_calibration_shrink`/`pv_calibration_shrink_slot`, default 0.2) with a 3.5-day half-life, so an already-calibrated site is left nearly alone while a persistent system error survives. A 0-PV day is a down-day and is excluded; fewer than `PV_CALIBRATION_MIN_DAYS` (3) valid days gives `Not enough valid days of evidence for calibration`; an older log's `Not enough valid (non-down) days` dates it to pre-#6231. Each future day's total is still nudged to its raw figure by `days_use_scaling`. (GH#5552)
- The calibration evidence is stored under `pv_calibration_evidence` for `pv_calibration_history_days` (28) days, scanned daily (retried hourly after a failed history read), and saved with a 60-day expiry plus a daily resave so a backend's default TTL cannot drop it. A failed read is not an empty store: it is only treated as empty after failed loads spanning `PV_CALIBRATION_LOAD_WAIT_MINUTES`. (#6231, same shape as #6225)
- The P10/P90 band and the observed peak still come from the last 7 days (`PV_CALIBRATION_BAND_DAYS`), as before the evidence store. Tests: `pv_calibration`, `pv_calibration_clipping`, `pv_calibration_scan`, `pv_calibration_update`, `pv_calibration_day_scaling`.
- Open-Meteo has no `horizon` parameter; Predbat has only monthly `shading_factors` (`gti_hourly_to_period_kwh()`).
- Test traps: the solar mock matches the first key that is a URL substring (`api.open-meteo.com` is inside `ensemble-api...`); patch `solcast.history_attribute_to_minute_data`; `now_utc_exact` is wall-clock while `minutes_now`/`midnight_utc` are frozen (`patch_now_utc_exact()`).

### HA write/verify (`ha.py`, `inverter.py`)

- `get_state(refresh=True)` is a no-op in a normal add-on install (re-reads only when `not self.ha_key`), so verification reads the websocket cache.

### Hanchu Cloud (`hanchu.py`, `hanchu_const.py`)

- Added in PR #5305 (2026-10-20), largely unverified on hardware; #5664/#5665/#5667/#5668 are from one live-hardware reporter, so search them first.
- Power limits are **two separate layers**, and a "Predbat won't write more than 5000 W though my unit is 10 kW" report usually confuses them. (a) The planner's `battery_rate_max`/`inverter_limit`: user override (`hanchu_battery_rate_max`/`hanchu_inverter_limit`), then the `HANCHU_MODELS` rating for `devModel` (codes are not in size order), then the `ranges_for()` ceiling. (b) The write clamp on `CHG_PWR_LMT`/`DSCHG_PWR_LMT` in `ranges_for()`: max(the cloud menu's range, the highest value seen held), capped by the model rating — the rating never raises it, because a refused key turns every write into a partial accept resent each cycle, and there is **no apps.yaml override for this layer** (#6044, decision pending). A 10 kW unit whose menu says 0–5000 is written at most 5000 W until seen holding more; the "If the inverter is ever seen holding a higher limit" Info line names the value it adopted.
- `CHG_PWR_LMT` limits grid charging only, so freeze export is never requested. A hold caps `DTU_AC_CHG_SOC_LMT` at the current SoC (`_hold_grid_target()`).
- Floors and caps: `CHG_BAT_SOC_LMT` ≥ 50 (read, never written), `DTU_AC_CHG_SOC_LMT` ≥ 20, `DSCHG_BAT_SOC_LMT` ≤ 45, so a hold below 50% or a discharge target above 45% cannot be set. A hold is a 0 W charge slot.
- One batched `iotSet` per change; a partial accept is never cached; overlapping writes fail with error 300004. The one-hour rolling hold slot is deliberate.
- Predbat commits a window in stages (times, target, rates), pressing the write button after each. Writing on the first press sent a new slot with the previous cycle's `CHG_PWR_LMT`/`DTU_AC_CHG_SOC_LMT` (e.g. 4000 W / 100% from `inverter_soc_reset`), and `hanchu_min_write_interval` then held the hold values back ~95 s: a live grid charge at a hold's start. Presses are now debounced (`hanchu_write_debounce`, default 10 s); the rates arrive after the loop with no press, so any schedule change while a write is pending restarts the wait too, and the reconcile tick skips while one is pending. Look for two `iotSet`s a minute or more apart at a window start. (GH#6074)
- **A hold stops at ~target+1 or at the clamped grid-charge target+1, and which path decides changes the number** — core's reserve hold (execute.py's Hold charging branch, needing `set_reserve_enable` and `inverter_reserve_max` ≥ the window target) floors at target+1; Hanchu's `_discharging_to_target()` judges against the **clamped** `DTU_AC_CHG_SOC_LMT` (floor 20) plus the 1% margin, so a 10% target holds at 21% — deliberate (documented in #6127, pinned by `test_hanchu_control`). The component guard only decides when the reserve hold is not in play. (GH#6133)
- HC-HY-SL-*-G2 is missing from the `devModel` table, so it always takes the fallback.

### Growatt Cloud OpenAPI (`growatt.py`, `growatt_const.py`)

- Component merged in PR #5666 (2026-11-11) with command-line diagnostics (PR #6132, 2026-11-11): `python3 growatt.py --config <apps.yaml> [--serial <sn>]` reads the growatt_* settings (resolving `!secret`) and writes `growatt_snapshot_<sn>_<time>.json` — run it instead of guessing from live logs. `--write-test` judges only telemetry taken after the write and before the slot ends, and slots never cross UTC midnight, so a scenario within 5 minutes of midnight is skipped `INCONCLUSIVE` by design.
- Pre-merge review facts, re-read on main 2026-11-12: `etoUserToday` is read as grid import into `load_today`; SoC limits are a software gate (`_gate_reason()`), not a register write; an unused slot reads back as `00:00-00:00` at 0% (`GROWATT_UNUSED_SLOT`), and a local repeating window is written as one or two non-wrapping UTC slots split at UTC midnight (`local_window_to_utc_slots()`); stale telemetry is silent, and a write verdict is judged only on readings taken after the write and before the slot ends (Growatt uploads telemetry about every 5 min).
- **"Export windows only cover the house load, nothing reaches the grid" (live SPH 3600TL BL-UP, Nov 2026)** — two causes, both needed. (1) The OpenAPI `export_limit` read `{"exportLimitEnabled": 1, "percentage": 0}`, and writing `{1, 100}` did *not* open it: every export attempt stayed at house load until Growatt support set `exportLimitEnabled: 0`. (2) Even with it disabled, a negative-percentage `time_slot_charge_discharge` slot only let surplus out; the timed `duration_and_power_charge_discharge` `dischargeCommand` with a power exported at the full 3.68 kW. Growatt support: "to force battery export, you also need to specify the battery discharge power in the dispatch request". So exports are now that timed command, renewed every few minutes, and "open" means disabled. Other traps from the same tests: the timed command keeps running after `enable_control` 0 (stop it with `selfConsumptionCommand`); it reads back the duration *as sent*, not the time left, and the discharge as a negative percentage; `getDeviceData` is 1 request/min per device, so a test script polling it beside the engine is rate limited (105) every time - read the engine's own `getDeviceData` log lines instead; the device's own Grid First rate is the "Discharging Power" % on its app screen (8% ≈ 290 W looked like "export stopped working" but was a user setting). Dead ends: the Growatt test-host base URL behaves identically to the production one; the Grid First stop SoC (`dischargeCutOffSOC`) at 100% does block exports, but lowering it alone did not fix them.

The planner cannot produce a lower target (the export search packs at `calc_percent_limit(best_soc_min, ...)` and the clip pass only raises targets); the gateway firmware's own per-slot floors/cut-off are outside Predbat's reach (maintainer: firmware fix). (GH#5997, verified 2026-11-13)
- **`set_read_only` on a PredBat Hub: the hub is told read-only before the safe state is written** — the component's own 60 s loop publishes the read-only command as soon as the switch changes, while the safe state comes from `reset_inverter()` in the next `execute_plan()`, so the hub is already refusing the writes (`Trying to write ... didn't complete`, hub `writes_ok: 0`). PR #6187 holds the publish while `inverter_needs_reset_force == "set_read_only"`; the second half is still open: `reset_inverter()` clears the pending flags unconditionally and the `adjust_*` helpers discard `write_and_poll_value()`'s False, so nothing retries a failed handover write (`test_solis_handover` pins the clear-anyway behaviour). **The window is one 15-second cycle**, which is the general trap: `expose_config(event=True)` arms the flag and `update_time_loop`'s 15 s tick runs `update_pred()` → `execute_plan()` → `reset_inverter()`, which clears it once its writes return — so a component on its own loop (Gateway 60 s, and Solis reads the same flag) sees the force only if its cycle happens to fall inside that window, and no component-side gate on it can order itself against the reset. Closing it needs the reset side to wait for the component. The publish reads `get_arg("set_read_only")` while `_ev_control_read_only()` prefers the live attribute, so an Axle-forced read-only is never sent to the hub (separate issue, same function). (GH#6175)

### Octopus (`octopus.py`, `fetch.py`)

- **Intelligent Go / dispatches:** for "a cheap slot Octopus never offered", compare `rate_import_base` with `rate_import_no_io` at that minute in the dump: cheap in both = the integration's rate sensor; cheap only after `no_io` = `rate_add_io_slots()`. `io_adjusted` cannot tell them apart (GH#5012, GH#5663). `trim_started_dispatch()` moves a running dispatch's start to the poll time, so the tail re-prices as a short dispatch (GH#5702, open), and `dynamic_load()` under-subtracts car load (`Dynamic load adjust is setting load minimum`, GH#5762, open).
- **Slot cancellation:** with `octopus_intelligent_dynamic` on (default), `dynamic_load_car_check()` cancels the slots of a car in a dispatch but not seen charging and re-prices them outside 23:30–05:30 (`in a dispatch but not charging`); check `car_charging_now` history, as `eco`/`boost` never equals `charging` (GH#5335, GH#5390). Confirmation counts any car charging from 2 minutes into the half hour (PR #5725); sub-5-minute dispatches need a confirmed half hour (PR #5657). Without `car_charging_now`, a charge below 0.85 × `car_charging_threshold` (kWh/minute: `0.1` is 6 kW) cancels real dispatches (GH#5706, open).
- **Dispatch pricing persistence, and "cheap charging latched after a planned dispatch was withdrawn"** — completed dispatches stay off-peak only while the feed lists them and applied rates are not persisted (GH#2785), so `today_cost()` and History re-price the past (GH#5413); `octopus_held_dispatches()` (PR #5533) bridges the gap where an account never populates `completedDispatches` (GH#5544). `octopus_held_update()` latches on planned-list coverage of the half hour whether or not the car charged; `octopus_held_withdrawn()` releases it and asks for a replan, and the companion `octopus_dispatch_tail()` covers a `source charging-unlisted` slot for the half hour *after* a dispatch ends (the car's charging sensor lags the dispatch end) — both fixed in PR #5907 with #5983. On that report rule out, in order: Predbat's own held record, the integration rate sensor's own post-withdrawal prices (read `rate_import_no_io` in the dump), and the poll-trim tail (built-in component only; HA-integration entries are untrimmed). Tells: Predbat-held entries in `Octopus slots changed` carry a `%z` stamp and no kWh; the row is a `held: True`/`AT_HOME` slot whose `amount` rises every cycle by (5 min × charge-point kW)/60, because a held slot carries no kWh and decode synthesises it from minutes-to-now (a `charging-unlisted` slot's amount follows real car energy). `octopus_slots_held` names the held half hours and `octopus_slots_held_saved` carries them across a restart. Planned dispatches are never promoted, by design; keep the `abs()` in `decode_octopus_slot()`. **The release gates** (`octopus_held_withdrawn()`, first in **v9.7.8** — compare tags by content before reading an older log's silence as a gate change): it needs `octopus_intelligent_dynamic` on plus a definitive not-charging read, and nothing logs when gated out. No `car_charging_now` sensor reads None (blocked); a load-inference misread such as the house battery's own import latches "seen charged" permanently; and the car-config `charging_now [False, False]` prints `bool(state)`, so it cannot tell a definitive False from None. (GH#5884, GH#5957, GH#5962, GH#6130)
- **The withdrawal strip** (`octopus_strip_withdrawn_feed_rates()`): a minute at/after now outside the fixed 23:30–05:30 window loses the feed's discount (reset to `rate_max_base`, `io_adjusted` mark dropped) once its half hour was seen covered by a dispatch (`octopus_feed_covered`, Storage-persisted so a restart cannot bring it back) and no dispatch — planned, completed or held — covers it now. Nothing is stripped while any car reads charging, under the window billing rule, or (dynamic Off) in the half hour in progress; a discount no dispatch ever covered is left alone. Strips reset to `rate_max_base`, not the half hour's own tariff rate, so for a few cycles after a withdrawal a genuinely cheap window can read at peak. (GH#5663/#5984)
- **A car slot priced wrong for a newly added dispatch source** — which sources are billed at the tariff rather than a dispatch rate is encoded twice, and nothing fails loudly when the two drift: `dispatch_billed_off_peak()` early-returns False for `bump-charge`, `BOOST` and charger-schedule, while `load_octopus_slots()` derives its own `tariff_rate_slot` flag from the same set independently (the `tariff_rate` marker it stamps has exactly one reader, `reprice_charger_schedule_slots()`). A source added to one and not the other freezes the start minute's rate across the whole span — the pre-#6051 BOOST/`bump-charge` behaviour, and a multi-hour boost at a 0p free-session or off-peak start rate is the fingerprint. Sources pass through raw from `decode_octopus_slot()` (no case normalisation) as string literals, not constants. (PR #6051)
- One `fetch_sensor_data()` cycle decides a dispatch half hour's rate in a fixed order: `fetch_sensor_data_cars()` builds `octopus_slots` (and runs `octopus_held_dispatches()`), then `dynamic_load_car_check()` can add charging confirmation, then `octopus_held_update()` holds/releases (a release sets `update_pending`, so the 15 s loop re-runs and drops the half hour from the rates), and only then `rate_add_io_slots()` stamps the cheap rate from the slots built in step 1, rounded out to whole half hours. The car's live charging read can differ between the slot-building and hold steps. (PR #5983)
- **`... dispatch was withdrawn before the car charged in it ...` plus `... is under 5 minutes and car N has not been seen charging in it` for a dispatch Octopus really ran** — a dispatch that started and ended between plan cycles: the 15-second poll reads the cached planned list and charging evidence is only recorded once a dispatch is already known, so `octopus_held_withdrawn()` judges the half hour from the planned list alone (a completed dispatch overlapping it is never consulted) and `dispatch_too_short()` then refuses it. With an Ohme-sourced slot sensor the unlisted plug-in charge is never seen either: `octopus_charging_unlisted()` needs a `current_state` attribute of `SMART_CONTROL_IN_PROGRESS` on the slot entity, which Predbat's own Ohme slot sensor does not publish. (GH#6110, verified 2026-11-10)
- **Do not read `Octopus Intelligent: car charging in its dispatch, preferring battery charge in the run to ...` as evidence the car charged** — it prints whenever the car is in a dispatch that was not cancelled, with no charging evidence at all. Build the timeline from `car_charging_now` history. (GH#6110)
- **Cap and over-cap billing:** `has_six_hour_cap()` matches `IOG-SMB` only; `octopus_account_slots()` keeps one budget per account, not per car (PR #5639); `octopus_intelligent_charging` off still stamps (GH#5065). The cap is midday-to-midday, in the dispatch's own minutes, shared earliest-first, and a partly-fitting dispatch is split where the budget runs out rather than flipped to peak (PR #6023). Minutes beyond it are billed at `rate_max_base` and only once past: `octopus_over_cap_minutes()` re-counts over completed, held and planned slots, and `over_cap_premium()` adds `(rate_max_base − house rate) × energy` to `cost_today`/`cost_today_car`, never `cost_today_import`. Energy is the car sensor's measured figure when `car_charging_energy` has data, else the dispatch's own, so a zero-measured minute pays nothing and a *planned* over-cap dispatch shows no premium. (GH#6023)
- **Charger outside the CT clamp (`car_energy_reported_load: false`)**: `car_outside_clamp_energy()` is the meter view `today_cost()` and the History rows share — the clamp's export is consumed by the car before any import is counted, so that export credit disappears and car kWh shows in neither the import nor the load sensor while the meter bills it. (GH#6023)
- **API and auth:** polls every 30 min (account), 10 min (events), 2 min (dispatch); a changed GraphQL body is logged in full. Octopus is moving its public API from `api.octopus.energy` to `api.oegb-kraken.energy`; since PR #5799 (merged 2026-11-21) Predbat's own requests use the new domain through one constant in `const.py`, and a user-set rates/compare/annual URL naming the old domain is rewritten at fetch with a log line asking for apps.yaml to be updated, so existing configs keep working after the old domain is switched off. **Saving sessions stay on `api.backend.octopus.energy`** — `savingSessions` answers 400 on the new domain. Both domains are live with no redirect, so a bare curl of the old one still succeeds; that proves nothing about which Predbat uses. (GH#5786) A 200 carrying `errors` comes back as data (`null` = that part failed, `[]` = none) — guarded for dispatches, devices and `savingSessions.account` (PRs #5493/#5750), not for null `events`/`joinedEvents` in `get_saving_session_data()`. **`/api/ping` returns 500 and the status reads unhealthy while rates keep arriving** — `OctopusAPI.is_alive()` goes False once the token mint has been refused continuously for `OCTOPUS_MINT_UNHEALTHY_AFTER_SECONDS` (1 h), and `health_message()` then reads `sign-in rate limited by Octopus for Nh, retrying automatically` (or `blocked` for an edge/WAF refusal); public download endpoints need no token, so read the health message before calling the install down. (GH#6029)
- An entity-sourced dispatch overlay prices only the entity's `completed_dispatches`/`planned_dispatches`; `started_dispatches` feed only the dispatch-timeline render (umbrella #4516). The `Octopus: Dispatch timeline car N @ ...` line proves whether the entity listed the dispatch — a dump cannot, it stores Predbat's parsed slots. Route: entity attributes → `octopus_slots` → `rate_add_io_slots()`. (GH#5773)
- Leaving an Intelligent tariff freezes the devices (`async_update_intelligent_devices()` returns early; GH#5412 closed). `octopus_automatic: true` re-wires over a user's `octopus_intelligent_slot` every restart. Add-X% vs SoC targets: `intelligent_device_is_charger()` (PR #5822).
- **Saving and free sessions:** the args read event entities (`events` free, `joined_events`/`available_events` saving); both ship disabled (calendar twins lack attributes), so "the sensor does not exist" usually means enable it (GH#5370, GH#5707). Free electricity comes only from `customerFlexibilityCampaignEvents` (`last: 50`, no pagination, no fallback; `Found N ... via flexibility API` shows what it holds, GH#5614); saving sessions' `falling back to legacy query` means the campaign endpoint was empty. `eventType` alone splits Power Down from Happy Hour and the flexibility path drops it, so read `event.get("eventType") or event_type.get(eventId)` (PR #5727); the Happy Hour skip must follow the type-map build (three check sites, GH#5615). Saving-session value is credited to every minute with no baseline (GH#2090), but Octopus pays only above the baseline, so an already-exporting plan earns nothing (GH#5458).
- **A Power Down session that failed, or "Predbat didn't earn the token"** — Predbat prices a joined Power Down purely per kWh: the event's octopoints are converted to p/kWh on every minute of the window for import, and for export only when the export tariff is configured (the gate is `rate_export_max > 0`, the max of the export table). ### Kraken / EDF (`kraken.py`)

### Axle (`axle.py`)

- An export event boosts import as well as export, by design (PR #4520, like Octopus saving sessions; `docs/energy-rates.md`); `axle_pence_per_kwh` scales both and nothing disables only the import side. #5060 and #5175 are by-design answers.
- `load_axle_slot()` bounds only the event end (no `start_minutes >= 0` guard as in `load_free_slot()`), so a closed event writes dead keys at negative minutes (GH#5036, open); they are inert, as `rate_minmax()` and the window scans start at `minutes_now`.
- Event boosts run before user overrides (`apply_rate_overrides()`), so a full-horizon `rates_export_override` rewrites event minutes as `user` (GH#4277 family). Workaround: put the fixed schedule in `rates_export` as the base tariff.
- Forensics: `rate_*_replicated` marked `user` through the event window = boost ran, override clobbered it; no `saving` marks and no boost = it never ran. `rate_*_base` holds the tariff's own price. Saving sessions, free sessions and Axle events all share the `saving` tag, so the tag cannot tell which programme priced a minute; the other tags are `copy`/`future`/`offset` (replication), `manual`/`increment`/`user`. (GH#6171)

### History fetch / memory (`ha.py`)

- History is fetched in `HISTORY_CHUNK_DAYS` chunks with boundary dedup; the chunking also multiplies REST calls enough to trip the fatal API-error counter at startup (see "Too many API errors" under *Startup, config and apps.yaml*).
- `HAInterface.get_history()` takes the db path only under `db_enable`+`db_primary` (both default off) — and until 2026-11-09 it ignored `from_time` there: a caller passing a small `days` plus a `from_time` delta (the 2-minute `HAHistory.run()` refresh sends `days=1, from_time=<last epoch>`) got a `days`-capped window. Fixed by passing `from_time` through (it overrides `days` where the engine accepts it, commit bc685a95). An empty store used to be re-read over its whole tracked window every 2 minutes; since PR #6071 a read that worked and found nothing is cached with a check time (`history_checked`) and rechecked every 30 minutes from the check time less a 15-minute overlap (`HISTORY_REFRESH_OVERLAP_SECONDS`), while a failed read caches nothing and retries on the next refresh. Anything calling `get_history_wrapper()` without `tracked=False` joins that 2-minute refresh for good — `tracked=False` is the precedent for rarely-read entities (web pages, `history_recorded_events()`).
- The largest memory peak is ML load-predictor training, not the plan.
- Since PR #5837 (2026-10-29) `EntityHistory.prune()` keeps the last pre-cutoff record re-stamped at the cutoff, so a rarely-changing sensor's cached oldest record is an artificially-stamped anchor rather than a real change; suspected, unverified: a later cache merge can keep that re-stamped anchor contradicting a refetched record — one wrong minute at the window start (PR #5837 review; GH#5456).
- Tests: `./run_all --test history_chunking`

### Minute data (`utils.py`)

- `minute_data()`'s gap-fill writes `newest_state` beyond the data, which for `backwards=False` is the earliest sample's value, so deltas after the fill show a phantom step when the series ends lower than it started. Convert deltas per sensor before summing (PR #4756 review).
- **A daily counter that resets at local midnight reads no reset on a DST-shifted date** — the reset test uses the history stamp's own clock (`near_midnight = stamp.time() < 00:06 or > 23:58`) and HA history stamps are UTC, so under BST a local-midnight reset lands at ~23:00 UTC, outside the window. A drop under 1 kWh (carbon_today, iboost_today, a cheap day) then takes the small-dip path and `clean_incrementing_reverse()` flattens the day's early increments; a bigger drop still trips the `last_state - state >= 1` catch. Probe-verified 2026-11-09 on a three-record history. (GH#6083)
- `get_from_incrementing()` adds 24×60 to a negative index instead of returning nothing, so a plan-axis key that arithmetic takes below 0 reads a plausible value from another day (backwards) or the far end of the forecast (forwards). Guard the key where `minute - minutes_now` or a change-day day start can go negative — the load forecast's extended tail is guarded since #6084. `fetch.py`, `load_ml_component.py` and `predheat.py` each carry the same wrap. (GH#5760)
- Tests: `./run_all --test minute_data`

### Battery capacity estimation (`inverter.py` `find_battery_size()`)

- The estimator applies `battery_loss × inverter_loss` to every sample, right only for an AC-side `battery_power`; DC-side it under-reads ~4% at defaults (GH#5831, open, code-read 2026-10-29). Suspected, unverified: GivTCP's `battery_power` is DC-side.
- The 0.65–1.20 plausibility band anchors on `nominal_capacity`, which `refresh_config()` re-reads from the `soc_max` arg every cycle, so an integration that binds a wrong capacity there rejects every real charge (`capacity_too_high`) and the size never self-corrects. The `self.nominal_capacity = self.soc_max` fallback inside `battery_size_tracking()` is cycle-local and never a lasting anchor — the next `refresh_config()` overwrites it before the next `find_battery_size()` — and only the pre-fallback value is persisted as `soc_max_nominal`. Sunsynk fixed this in PR #6007 (2026-11-06) by binding `soc_max_fallback` and taking the estimator's power from `battery_size_power`; DEYE still binds `soc_max` from its own capacity (installer-typed `battCapacity` first), so a mistyped Deye capacity still pins the band (follow-up, not hardware-verified).
- `sensor.<prefix>_soc_max_calculated` is not always a measurement: `update_soc_max_calculated_sensor()` publishes the 7-day trimmed mean only when the history holds at least one non-None day, otherwise the `nominal_capacity` attribute (or `unknown` at 0), and `battery_size_tracking()` reads the state back only with a measurement or a nominal. On an install whose `soc_max` has since been unset (Sunsynk now binds `soc_max_fallback`), a restart could read the old configured size back as the "measured" mean — the "battery size stuck at an old configured number, and the sensor looks plausible" report. Since PR #6018 the unconfigured branch no longer writes the estimate back into `soc_max`, and a day that found nothing retries hourly (`last_attempt` attribute, `BATTERY_SIZE_RETRY_MINUTES` 60) so an overnight charge is used the same morning; old low measurements fade only as they age past the 7-day window.
- The 80–100%-of-nominal clamp (#3974, #3940) means `battery_scaling_auto` tracks only degradation below `battery_scaling`; a measured capacity above nominal cannot take effect.
- Tests: `./run_all --test find_battery_size`

### Balancer (`utils.py` `balance_inverters()`)

- "Balancing holds the wrong battery / the house imports while a peer sits near its reserve" — check the snapshot first: `build_inverter_snapshot()` (execute.py) is where units cross, and `balance_inverters()` trusts the key names it is fed (GH#5835). Its takeover rule reads the snapshot's `reserve_percent` key, filled from `inverter.reserve_percent_current` since PR #5836 (2026-10-29).
- Three similarly-named reserve attributes: `reserve_percent_current` = the live percent read, `reserve_current` = the kWh value derived from it, `reserve_percent` = Predbat's planning floor when `set_reserve_enable` is on. `adjust_reserve()` writes the device but never refreshes the `_current` attributes — they update only in `refresh_config()` — so the snapshot can read a stale reserve for up to one cycle after a mid-pass hold (verified 2026-11-06).
- Fixture trap: the execute-path balancer fixture stores a percent into `inverter.reserve_current` (the kWh field), so a unit conflation at the snapshot boundary is invisible to it until a real-Inverter test uses a non-default reserve (GH#5835/#5836).
- A peer claiming "charge" makes `balance_inverters()` zero every measured discharger, including a demand-mode discharge the executor itself planned — the all-demand/no-charging-peer case is protected by the executor's own demand claim only. Pinned by `test_executor_rate_survives_a_balance_hold`; on "inverter discharged but Predbat shows it at 0 W" start at the claims, not the power readings. Since PR #6194 (2026-11-14) cross-charge holds are latched while the fleet keeps discharging (a held unit's 0 W reading cannot un-hold it), a peer is counted at `min(claimed rate, learned ceiling)` so a derated unit is not assumed, and the pass publishes `sensor.<prefix>_balance_inverters` with each hold's reason and the learned ceilings.
- Was a bug (fixed in PR #5870, 2026-11-01): a register-less type's dummy `reserve` entity was seeded with the kWh reserve labelled `uom="%"`, and the `battery_min_soc` floor on the read-back masked it for packs ≤100 kWh — `reserve_percent_current` came out accidentally correct; >100 kWh packs read an overstated reserve. Test trap: an assertion on `reserve_percent_current` alone passes on that broken code — assert the dummy entity's own state **and** its uom. (GH#5850)

### Charge/discharge rate grid (`battery_rate_grid.py`, `battery_curve.py`, `inverter.py`)

- The plan's charge/discharge ceiling is a learned **rate grid**, not one curve: SoC percent (101 columns) × battery temperature rows, looked up per target minute by `rate_grid_curve()`/`rate_curves()` and applied in prediction, execute, output and the Curves page. `battery_rate_grid_update()` scans full-rate history runs (`find_rate_grid_samples`) and `fit_rate_grid()` fits the cells. A rate tapering near ~93% SoC is expected, not a fault. (#6212)
- The manual `battery_charge_power_curve`/`_discharge_power_curve` (or `_default`) and `battery_temperature_*_curve` make the base grid, the fallback and the prior for unmeasured cells. With `battery_rate_grid_auto` (default on) the learned grid is laid over it only once evidence covers `BATTERY_RATE_GRID_MIN_CELLS` (20) cells over `BATTERY_RATE_GRID_MIN_DAYS` (3) days; with it off the evidence is still gathered for the Curves page but the manual grid plans. (#6189)
- Evidence comes from history runs of at least `BATTERY_RATE_GRID_RUN_MINUTES` (15) at the written full rate — a minute counts only when **every** inverter was written at ≥95% of its own maximum — with the ramp ends dropped, cut into 5-minute segments, kept per day for `BATTERY_RATE_GRID_MAX_AGE_DAYS` (365) with a 90-day half-life, rescanned daily and retried hourly after a failed history read.
- A failed store read and an empty store both come back as None: the store is treated as empty (a new install) only after failed loads spanning `BATTERY_RATE_GRID_LOAD_WAIT_MINUTES` (10), so a storage outage cannot replace a year of evidence with one scan. It is saved with a ~395-day expiry and at least daily so a backend's 72 h default cannot drop it. (#6225)
- The learners run from `fetch_inverter_data()` on inverter 0 but read the **whole fleet's** history (`curve_fleet()`), because the plan models one summed battery. A site-total install marks the other inverters' `battery_power` as `0`; the old code dropped a falsy entry, failed to recognise the site total and fell back to inverter 0 alone, measuring the site's power against one inverter's rate — fixed in #6227 (`counted_in_site_total()`). When another inverter lacks a setting or its history, learning falls back to inverter 0 alone, except where `battery_power` is a site total, where it warns and refuses; binding a per-inverter sensor under a site total is the same mistake. (GH#6226)
- One grid serves the fleet and is applied per inverter at that inverter's own temperature; the fleet SoC model is still combined, so mixed-fleet deliverability is unchanged (GH#5442, GH#5508, GH#5628). The multi-inverter target split is `split_change_by_rate()` (PR #5906).
- `Info: Inverter N Cannot find battery discharge rate grid evidence, export_limit ... is below the discharge rate and there is no grid_power history to tell which exports it limited` — a discharge grid cannot be learned safely when the export limit caps the rate and nothing records grid power; wire `grid_power` or accept the manual curve.
- `battery_temperature_charge_curve`/`_discharge_curve` remain apps.yaml-only keys checked by `validate_curve()` in `fetch.py`, not CONFIG_ITEMS (grepping `config.py` misleads); `battery_charge_power_curve`/`_discharge_power_curve` and `battery_rate_grid_*` are CONFIG_ITEMS. (GH#5630)
- Tests: `./run_all --test battery_rate_grid --test battery_rate_grid_scan --test battery_rate_grid_update --test battery_curve_keys`

### Predheat (`predheat.py`)

- No control path: every outbound call is a read-only `return_response` service (`weather/get_forecasts`, and since #6042 `climate_scheduler/get_schedule`/`get_settings` and `workday/check_date`); `smart_thermostat` only pre-empts a setpoint rise in the simulation, and Predheat is its own object, so `plan.py` never sees a heat decision (GH#4848).
- `load_forecast: - predheat.heat_energy$external` feeds modelled heat to the plan as fixed load, on top of history and Load ML (`fetch_extra_load_forecast()` sums all sources); feature asks are usually wiring (GH#5483).
- Predheat settings resolve only inside the `predheat:` apps.yaml section (nested under `pred_bat:`, GH#5002): a `domain=None` read never reaches the section. `volume_temp` was silently ignored until PR #6038 switched it to `domain="predheat"` — on a "documented predheat setting does nothing" report, check the read's domain. The domain keyword binds to the OUTER read only: the nested fallback (`get_arg("next_volume_temp", ...)`, now inside `get_temperature_arg`) must keep no domain, because it is the read half of the persistence round trip (scheduled run → `expose_config("next_volume_temp", ...)` → next cycle's no-domain `get_ha_config` read). A symmetrical tidy-up makes every cycle restart from the current internal temperature with no error logged.
- Climate Scheduler (#6042, merged 2026-11-15) reads `climate_scheduler/get_schedule` (`schedule_mode` `all_days`/`5/2`/`individual`, node `time`/`temp`/`hvac_mode`) and `get_settings`, whose keys are exactly `"workdays"` and `"use_workday_integration"` (other settings there are camelCase, so don't infer casing). `DEFAULT_WORKDAYS` is Mon–Fri. HA's `workday/check_date` takes `check_date` (not `date`) and returns `{<entity id>: {"workday": bool}}`; `binary_sensor.workday_sensor` is the integration's own hardcode, not an HA convention.
- Predheat works in °C internally: entity temperatures are converted in from their unit since PR #5958 and results published in the user's unit, so a °F weather entity running the forecast away while energy stays 0 is a pre-#5958 log. An entity with no unit is read in HA's unit. (GH#5153)
- Thermostat bands: `hysteresis` (0.5 °C) is how far **below** target heating turns **on**, `hysteresis_off` (0.1 °C) how far **above** it turns off — code and docs agree since PRs #5767/#6032, so a report citing the old "counterintuitive" description dates itself. The COP key is `heating_cop`, with `heat_cop` still supported, default 0.9.
- Two routes to the fallback target (21.5 °C): an unset `heating_energy` meter pinned `minute_data_age` to 0 (PR #5867); `EntityHistory.prune_history()` dropped the state-in-force record, so an `unavailable` blip floored age to 0 for 24 h (PR #5837).
- Traps: `run_simulation(save="best")` publishes HA entities, so a parameter sweep overwrites the sensors; Predheat reads `datetime.now(local_tz)`, so build history mocks against wall-clock time.

### Load ML (`load_ml_component.py`, `load_predictor.py`)

- The 2-hourly retrain is a curriculum of passes (`ml_curriculum_step_days`/`ml_curriculum_max_passes`, hardcoded), a 16–40 minute CPU spike every 2 h (GH#3896, GH#5213). `threads` reaches only the C++ kernel and nothing caps BLAS threads, so NumPy may use every core.
- On "CPU regressed after upgrade", reconstruct from the log when fine-tunes ran under each version; a version window under 2 h proves nothing (GH#5213).
- `load_ml_retrain_interval_hours` (PR #5433, 2026-10-12; default 2, max 48) is age-based, not clock-aware. Past `ml_max_model_age_hours = 48`, `is_valid()` returns `"stale"` and ML predictions fall back to empty.
- `load_ml_enable`, `load_ml_source` and the retrain interval are component/apps.yaml args, not CONFIG_ITEMS.
- `is_valid()` can say "active" for a never-trained model (`model_initialized` is set before the first epoch), and an aborted curriculum leaves fresh stamps that suppress the staleness retrain (GH#5075; fix in open PR #5112).
- `PREDICT_HORIZON` is 48 h (576 steps) and the plan's load beyond it is exactly 0, as `load_forecast_only` skips the historical forecast (GH#5336, open); "over 48h" in `Generated N predictions` is hardcoded text.
- Each fine-tune can move the published 48 h total by double digits (GH#5561, open): bracket `Training successful` with the adjacent `Generated N predictions (total X kWh ...)` totals. The ML forecast replaces the load forecast with no blend; a quiet log is not evidence of health.
- Load exclusion knobs (`car_charging_energy`, `iboost_energy_subtract`, future `heat_pump_energy` #5445) reach ML-source users only if `load_ml_component.py`'s data prep subtracts the same: car already did, iBoost since PR #5829 (2026-10-29).
- Saved ML rows are prepped at fetch time and restored verbatim, so a data-prep change reaches only fresh minutes until old rows age out; `Database iBoost subtraction mismatch ... discarding` after an upgrade or switch flip is #5829's gate.
- "The LoadML trace shows large spikes and deep flat sections that do not reflect actual load" has two candidate mechanisms: rate history that reads as one flat value across many days comes from the `rates` sensor's `results` attribute backfill (the merge fills only minutes that backfill left empty — GH#6147, path from #3368), and long-range rollout error `mae_kwh` cannot see starts at `_normalize_features()`' z-scores meeting ReLU death. August's GH#4673 trace reports match both; that issue's npz replay proved the model accurate with correctly supplied inputs, so suspect inputs before retrain variance. Discriminator: `pattern_mae_kwh` vs `rollout_mae_kwh` on the `load_ml_stats` sensor (PR #4678), measured while the trace misbehaves. (verified 2026-11-13) Both are since fixed: the backfill by PR #6241 (`pad=False`, merged 2026-11-20), and the unbounded z-scores by `FEATURE_Z_LIMIT` (±5σ in `bound_normalised()`, applied in `_normalize_features()` *and* both `WindowedFeatures` row paths, since training batches never go through `_normalize_features()`), with `MODEL_VERSION` 11 discarding older models.
- **A LoadML forecast flat at one value (or jumping several-fold) around a saving session or Axle event, on an old model** — inspect the saved weights before the inputs: in #6147/#6208/#6259's models only 69%/27%/2% of the 256 second-layer units fired on any of 576 validation windows, and clipping their inputs revived none (one-step MAE slightly worse). Retraining from scratch on the same history gave 52–98%. So the damage lives in the weights and only a retrain clears it — that is why `MODEL_VERSION` was bumped rather than the limit applied to loaded models. Replaying those three histories: a +100p future spike moved single 5-minute steps by up to 16× without the limit and under 4× with it; two training runs per case could not tell the accuracy apart either way (runs of one setup differed up to 3.6×), so robustness, not accuracy, is the measured gain. The limit is saved with the model and `load()` discards one saved under a different limit. Raising the rate blocks' 1p minimum std to 5p was tried and rejected (little extra robustness; #6259's forecast went far too flat, MAE 0.028 vs 0.008). Trap for offline experiments: `_initialize_weights()` calls `np.random.seed(42)`, so every training run is identical unless that call is redirected — two "different seeds" silently give the same model. (GH#6147, GH#6208, GH#6259, verified 2026-11-20)
- **The LoadML forecast stays at the household's long-run level through a cold snap while real load climbs** — by construction, not a data fault: `predict()` blends the autoregressive rollout with a per-weekday daily pattern (`_compute_daily_pattern`, an unweighted mean over the saved history) down to `blend_floor = 0.5` at the 48-hour horizon, and a multi-month mean cannot move inside a snap. Training is one 5-minute step ahead with teacher-forced validation, so a good `val_mae` measures persistence on the same regime, not response to the weather ahead — expect the stats sensor to look healthy. Check the temperature source feeds the *forward* channels: Open-Meteo's `past_days=28` already returns ~7 days ahead as negative keys. (GH#6157)
- Replaying a LoadML npz pair offline: `ml_model.npz` holds no object arrays and **float64 weights** (Adam upcast them after float32 init) — cast nothing. `ml_history.npz` keeps only positive keys (minutes ago) and only 5-minute-aligned ones, so per-minute temp/rate keys collide into `minute//5` buckets on save. Future channels from a dump use **two key formats**: the temperature sensor's results attribute is quoted ISO with `+00:00`, while `predbat.rates`/`rates_export` are unquoted `...+0000`. Self-check a rebuild by matching `_ar_rollout_diagnostic`'s `pattern_mae` and the `prev_energy value` in `Starting autoregressive` against the log — both match exactly when the channels are right, while model-level numbers may still not reproduce (anchor/phase sensitivity, unresolved), so quote perturbation experiments as indicative. `Forward temperature/rate forecast ran out for N of 576 steps` fires only when a step is missing from temp **and both** rate channels, so its absence proves nothing about temperature. (GH#6157)

### Web, MCP and Chat (`web.py`, `web_mcp.py`, `chat.py`)

- **MCP OAuth (GH#4799/#5847):** the surface was rewritten by PR #5992 — `/oauth/register` mints public clients (no secret out), client-credentials works only with `mcp_secret` itself (that secret stays the all-scope legacy bearer), the JWT signing key is random and Storage-persisted, `tools/call` enforces `mcp:read`/`mcp:write`/`mcp:control`, and a default or empty `mcp_secret` is refused to start. ### Component health (`components.py`, `component_base.py`)

- `count_errors` is a lifetime counter. `api_started` means `run()` returned truthy once (Gateway does so while unconfigured). `is_alive()` is the real health check (60-minute staleness). A component's device-writing methods are listed by `ComponentBase.write_methods()` via the `@writes` marker; all integration components carry markers, but overriding a marked method without re-marking it silently unmarks it (PR #5920) — on a "Predbat wrote when it should not have" report, check the code, not only the listing.
- `record_status()` writes raw text as the HA state, and HA rejects states over 255 characters. A test of `update_status()` sees only the last `record_status()` message.
- Each component has its own thread and loop, so blocking compute stalls only that component and `run_timeout` never fires. Slow shutdown (all log Stopped and "Predbat terminated", the process lingers): find the `run()` that cannot return, load_ml first (GH#5075; PR #5112 open). `Components.start()` waits up to 10 minutes per component, serially, so restart delay ÷ 10 minutes = dead-component count (GH#5580; GH#5134, open).
- A `run()` exception skips the rest of that cycle and retries on backoff (first cycle: `api_started` stays unset), so report what was skipped, not a "crash" (GH#5584). `json.JSONDecodeError` slips past `aiohttp.ClientError` handlers. On timeout, `start()` cancels the task without setting `api_stop`, and the next tick may start a second run.
- Since PR #5963 each component owns a clock (`monotonic()`/`wall_time()`/`await sleep()` on `ComponentBase`): elapsed-time windows (staleness, retry backoff, dedup) are stamped on the component clock; anything leaving the component — payload timestamps, JWT/epoch comparisons — stays on the wall clock. A stamp initialised to 0 needs an explicit zero-guard: a just-booted host's small monotonic value makes "never sent" read as "just sent".
- `align_minute: True` on a `COMPONENT_LIST` entry runs the component loop at minute boundary +1 s, skipping boundaries a slow `run()` overruns; `run()`'s `seconds` steps in whole minutes, so interval checks inside it must be relative deltas on `seconds`. Sigenergy, Solax and Teslemetry set it; a new minute-edge component adds the flag and updates `test_registry_align_minute_reaches_the_component`. Without it, acting on a minute-resolution edge is up to a minute+ late by design — check the flag before debugging the component's own window logic. (PR #5976)
- A component whose fetch fails **gracefully** — logs and returns success, keeping previous/empty data — never triggers `ComponentBase.start()`'s backoff, so a one-shot `if first: automatic_config()` against the empty data is a permanent silent miss (Octopus: KT-CT-1199 → None → previous account data → `tariffs == {}` → `run()` returns True). On an "automatic config never ran / ran once against empty data" report, check what each change-detection guard does on the **empty→populated** side and enumerate all its call sites. Octopus's is fixed (`automatic_config()` records the tariff keys it ran with; the fetch reconfigures when they differ, downloading rates the same cycle, PR #6080). Other components are unaudited. (GH#5994)
- A component's hardware fault is invisible outside its own log plus its realtime sensor unless the component calls `self.base.record_status()` itself (`solax.py` calls it nowhere; the working precedent is `gateway.py`'s error path) — and the `had_errors` branch in `update_pred()` skips `record_status()` entirely, so the "obvious" error path freezes `predbat.status` on its last value instead of showing an error. `non_fatal_error_occurred()` only sets the flag. (GH#5996)
- An every-cycle `Warn: <component>: failed to report discovery for the catalogue: <AttributeError>` whose traceback comes from inside `build_discovery()`: the guard over malformed payloads covers `except (KeyError, IndexError, TypeError, ValueError)`, but a read of the data container *outside* that try (a `data.get(...)` loop after a strptime `pass`) raises AttributeError uncaught, and `refresh_discovery()` swallows it — the observable is the warn plus a catalogue record frozen at its last-filed state. temperature.py shipped this shape; whether a live fetch can hand `build_discovery()` a truthy non-dict is unconfirmed. (GH#5936)
- Stamping liveness on cache-only cycles hides a dead component, so override `is_alive()` (enphase, Kraken; GH#5582); an empty signed-in account should return True without stamping, as False costs 10 minutes per restart.

## Symptom → first place to look

What a report or log shows, and where to start. Where a symptom belongs to one integration, the bullet points at that area's notes above.

### Startup, config and apps.yaml

- **`Error: You have not set load_today or load_forecast in apps.yaml` then `Error: Exception raised ValueError` every cycle** — a bare `raise ValueError` in `fetch_sensor_data()` used to abort the cycle; since PR #6101 the cycle is skipped without a traceback while no load source is set. Cloud components set `load_today` at runtime, so during their startup delay check the Components panel. (GH#5092)
- **`Error: timer_tick caught exception: <X>`, status `Error: Exception raised <X>`, "stopped planning"** — an exception escaped `update_pred()`; find the raiser from the payload. `ReadTimeout` is not a `ConnectionError`, a hole in any `except ConnectionError` around a bounded request (PR #5801). (GH#5743)
- **`Failed to decode response <Response [404]>`, `Error: Too many API errors, stopping`, "stopped but running", `Cannot initialise Home Assistant Interface` (empty message), repeating `HAHistory: No HAInterface available`, or silence after a restart** — this was the `fatal_error` latch: a counter of consecutive REST failures with no time decay that stopped the interface at 10, reachable from one startup history fetch, because `HISTORY_CHUNK_DAYS` is 3 and the 30-day fetch is exactly 10 calls (GH#5948). **Fixed in PR #5449 (merged 2026-11-21):** the counter is now an outage timer (`HA_OUTAGE_LIMIT_SECONDS`, 15 minutes) — any contact with HA ends the outage, REST and the websocket keep separate timers so one working cannot hide the other, the websocket's ends only on authenticating, `initialize()` retries with backoff over the same period but fails at once on a 401/403 `ha_key` rejection, a mid-reply connection reset now counts as an outage instead of escaping, and Supervisor calls (`core=False`) no longer count. So "stopped after 10 errors" on a current log dates it to before #5449.
  Two amplifiers survive: `wait_api_started()` still never checks `fatal_error`, so each dead component burns its full 10-minute timeout serially, and the standalone fatal watcher still starts only after `initialize()` returns, so a mid-initialize fatal is unobserved and the web Restart button is a no-op. No-interface repeats follow `ComponentBase.start()`'s retry ladder (0/120/360 s, GH#5886), reprinted on every attempt since v9.6.4, so "one attempt then silence" is an older log; it usually recovers by itself, so "the other instance is fine" is no counter-evidence. #5134/#5354/#5437/#5948 still carry `fixed` labels but remain open; PR #5323 is open. (GH#5354, GH#5744, GH#5806)
- **predbat.log shows only `Loading secrets from ...` / `Loading apps.yaml` pairs every ~20 s, never `Predbat: Startup`** — apps.yaml failed to parse, usually an unknown tag (only `!secret` is registered). Since PR #5642 (2026-11-14) the parse error is logged to predbat.log with the offending tag and a `!secret` hint, so on a current log read that line; on an older one it only reached the add-on console. (GH#5530)
- **`Invalid value None in element predheat.heat_energy$external`, no `Predheat:` lines** — `predheat:` must sit inside `pred_bat:`; bundled sub-apps read via `self.args.get(domain, {})` and ignore a top-level section. (GH#5002)
- **A config item above its maximum stays capped, or an entity/slider accepts a value the engine reverts** — a `CONFIG_ITEMS`/`APPS_SCHEMA` `max` clamps every source including apps.yaml (`Warn: Config item ... clamping to ...`, GH#5070). Entities and the web slider advertise the static `min`/`max` but do not clamp writes; the entity-side Warn-clamp runs only at startup, after a config write and on the 8-hour `CONFIG_REFRESH_PERIOD` refresh, so an install can sit with entity state below its advertised min for hours. Runtime mutation is restart-safe: every restore path (`predbat_config.json`, saved settings, debug replay) applies `value` only. The clamp also catches items the engine writes back via `expose_config()`, so their declared max must cover the physical range: `next_volume_temp` restarted too cold every reload until PR #6173 raised max to 100, and `car_charging_manual_soc_kwh` (100 kWh), `iboost_today` (30) and `holiday_days_left` (28) are the same shape — fix the range, not the clamp. Engine-side reverts are `Inverter` self-heals (`battery_min_soc`) landing after the write; GivTCP publishes the reserve register's `min` as `min(hardware_min, battery_min_soc)`, and do not fold `reserve_device_bounds()`' device min into the one-way `set_reserve_min` raise (a fluctuating read re-ratchets it, #4013/#5232). (GH#5995/#6000)
- **"Predbat reports a GivEnergy error but I use Solis / Fox / GE Cloud"** — `inverter_type` is `GE` until component auto-config sets it (tell: `Warn: ... inverter_type is not set in apps.yaml`). Self-heals. (GH#4990)
- **`Error: Inverter N unable to read charge window time - no source is configured`, every cycle, then `timer_tick caught exception`** — deliberate with no `charge_start_time` arg and `inverter_source_active()` False (GH#5804). Read the dump's `inv_charge_time_format` before theorising: `HH:MM:SS` on a non-GivEnergy setup means the template's `inverter:` block never applied — a template merged with the block flattened to `pred_bat:` level leaves `inverter:` null, so the type materialises as a copy of the GE defaults and no charge-window args are self-created. Re-merge preserving indentation. The same raise is legitimate on a real type with `has_charge_enable_time` and no source — on Tesla, configure the Teslemetry component or `templates/tesla_powerwall.yaml`. (GH#5804, GH#6113)
- **`apps.yaml has N errors` naming a `*_today` accumulator "is not a valid type float", or `Warn: Validation of apps.yaml found ...` while the install runs normally** — validation is warn-and-continue: `validate_config()` logs one Warn per problem into its arg-errors dict and nothing on that path stops Predbat (the only consumers are status side effects). It reads live states, so an `unavailable` accumulator fails a few times a day (`transient_ok` covers only car charging items, GH#5421; a constant-valued placeholder was fixed in PR #5845, GH#5242). An unquoted all-digit value is the usual benign case — YAML loads an int, a `type: string` item warns, and readers that convert to text keep working — so quote it; and a *list* given where the schema says `string` passes item by item, so a schema test's negative case must use a mapping. (PR #6104 review, 2026-11-10)
- **`Validation ... is not a list, but requires N entries based on num_inverters` plus `Return bad int value [<list>]` every cycle** — the `entries: num_inverters` check disagrees with a `get_arg()` reader lacking `index=`; unindexed list reads default with `had_errors`. PR #5651 (2026-11-14) added `single_value_ok`, an opt-out declared only by `inverter_battery_rate_min` and `inverter_reserve_max`: for those two a single value passes `validate_config()`'s list check and `get_arg()` broadcasts it to every inverter; any other `entries: num_inverters` item still gets the check. (GH#5369)
- **`Validation of apps.yaml found configuration item 'X' element <entity> which cannot be modified` while everything works** — the writable-domain allowlist in `validate_config()` (`switch/select/input_number/number/time/input_datetime`; `input_select` missing) has drifted from the write paths, which accept more (`write_and_poll_option()` writes `input_select`, the change router covers `input_boolean`), so a helper domain the validator forgot is a false positive; a genuinely read-only entity is the real case. Red/green via a mirrored case in `test_validate_config.py`. (GH#5885)
- **An inverter drops out of the plan after an upgrade on a mixed fleet** — start at the vendor `automatic_config()`'s `set_arg_auto(..., overwrite=True)` writes (grep `auto-discovery wins`), not `execute.py`. Workaround: `givtcp_automatic: False`. (GH#5029, GH#5209)
- **An apps.yaml entry for a daily total (`load_today`/`import_today`/`export_today`/`pv_today`) is ignored or reverts under `<integration>_automatic`** — the totals are discovery-bound and `set_arg_auto(overwrite=False)` (user wins) is adopted unevenly: GivTCP for exactly the four plus `export_limit` (a template's hand-typed line stays authoritative until deleted), Sigenergy for `export_limit`/`battery_min_soc`, Hanchu for the four; GE Cloud binds several with plain `set_arg`; Solis still default-overwrites (`load_today`/`pv_today` escape via `solis_cloud_pv_load_ignore`, `import_today`/`export_today` have none). Read the component's `automatic_config()` first — the call shape decides. (GH#5873)
- **"Predbat entities that won't go away" / a "[Disabled] ..." entity after turning a feature off** — enable-gated config entities are never removed: disabling keeps the entity in HA with its last state and a `[Disabled]` friendly-name prefix (`load_user_config()`). Feature outputs (`iboost_best`, `binary_sensor.predbat_iboost_active`) publish regardless of the enable switch; the plan-card column and generated dashboard cards are what disappear. (GH#5922)
- **`Watched event: <entity> = {...} will trigger re-plan` repeating each integration refresh, each followed by a replan** — `watch_event()` sets `plan_valid = False` unconditionally and no trigger path compares old with new, so an `event.*` entity fires on every refire: its state is only the last firing time, while the payload sits in attributes that may not have changed. Fingerprint attributes for event entities and state for everything else; Predbat reads the Octopus event entities every cycle anyway, so removing them from `watch_list` loses nothing. (GH#6105, verified 2026-11-10)

### Plan: charging and holding

- **Battery charges, freezes or discharges when it shouldn't** — rule the plan out first. A planned freeze is a charge window whose limit equals the reserve %; on an all-loss tariff holding full is correct (GH#4890). An active weather alert's keep (default 100) is a *floor the optimiser defends*, not a hold, so "my keep is ignored" usually means the plan is holding at the current SoC instead (GH#3200). Every minute outside a charge or export window is ECO in `predict()` — only EV slots (`car_charging_from_battery: false`) and iBoost (`iboost_prevent_discharge`) hold the battery there, so "why discharge during cheap hours" is a model gap, not the plan (GH#5122).
- **Battery pinned at 100% while the house imports at peak** — `Completed run status Demand` every cycle, zero `Inverter N count register writes` and a flat SoC mean something outside Predbat refused the discharge; check the integration's reserve/min-SoC binding. (GH#4961)
- **`Hold charging target X%-Y%` while importing at peak, or a peak-price charge window** — the high-price gate (`best_price_charge_level`) guards only windows whose limit is still 0. Without `set_reserve_hold`+`set_reserve_enable` (or `inv_has_timed_pause`) "Hold charging" is an armed-window fallback; `not yet in charge freeze, holding target SoC at 100%` is a deliberate pre-window write. The suffix is SoC–target, not start–end. (GH#2716)
- **Plan shows `HoldChrg -> N%` / "charging to N%" while the slot charges higher, or a "Planned Charge" row whose SoC never rises** — a row's "target" is the predicted end SoC when the window cannot reach its limit (`clip_charge_slots()` keeps the limit at `soc_max`), and the label is a knife-edge: `HoldChrg` shows only when the modelled SoC stays at/above the limit over the whole window, so a window whose target is already at/below the SoC (a reserve-hold charging nothing) falls back to the generic "Planned Charge" with its hardcoded rising arrow. Check the dump's `best_charge_limit` against `status_detail`'s target before calling the limit logic broken. (GH#4445, GH#5889, GH#5902)
- **Reserve raised to keep the battery full (`set_reserve_min` 100) and it never charges — `Filtered charge windows []`** — the charge scan needs levels strictly above the reserve, so a reserve ≥ `soc_max` (or `best_soc_max` below it) leaves only "off"; a fix must also cap `reserve_percent`, as a limit at the reserve is a kernel freeze. (GH#4766) A flat hold at a reserve the battery then drains past (Sigenergy to 0%) is `has_reserve_soc: False` keeping the floor model-only — see the *Sigenergy* notes. (GH#5358)
- **First cheap window charges to 0% / the charge target lands later than the cheap band** — a metric tie: the SoC scan adopts on a non-strict `<=`, and with `metric_battery_cycle` at 0 a charged kWh scores as its stored credit; neither `metric_min_improvement` nor `metric_battery_cycle` fixes it. (GH#5069)
- **Overnight charge stops at "just enough", starts late and stops short, or stops short when a free session sits later in the horizon** — the first two are pruned pv10/pv90 hedge slots, fixed in PRs #5721/#5735 (`debug_enable` logs `Prune dead` / `Prune kept hedge` / `Prune trade-off` per slot; with 0p export stored kWh earn `metric_battery_value_export_scaling` 0.8, so 100% is not the optimum); the session case is by design — it bridges to the 0p session, whose 0p is baked into the dump's `rate_import` on replay (deleting `octopus_free_slots` does nothing). (GH#5719)
- **The plan seems stuck and won't adopt a clearly better replan** — `should_replace_plan()` compares pre-clip snapshots and a retained incumbent keeps a stale one; gates and units are under "Check configuration before code". (GH#4736, GH#5261)
- **`Will not recompute the plan, it is 5.0 minutes old and max age is 10 minutes` at a tariff boundary, so the previous plan runs on past it** — the gate is `plan_age_minutes + RUN_EVERY > calculate_plan_every` with a strict `>`, and both run times and plan stamps sit on the 5-minute grid, so ages land on exactly 5.0 or 10.0: at the default 10 the run after a recompute never replans, and a rate rollover is not a replan trigger at all. Workaround `calculate_plan_every: 5`. (GH#6102, verified 2026-11-10)
- **The battery keeps charging at a higher tariff inside one charge window although the plan's row shows a hold after the rise** — nothing splits a window at a rate change: `clip_charge_slots()` raises a charge's limit to full so adjacent windows can merge, and `discard_unused_charge_slots()` merges same-limit neighbours with no price check unless `set_charge_low_power` is on — so the post-rise hold is welded into the pre-rise charge and execution (charge while below target) keeps importing across the rise. The Chrg/HoldChrg row labelling knows the split; nothing sent to the inverter does. (GH#6108, verified 2026-11-10)
- **A near-tie plan flip adopts the cleaner plan and the branch has no cost check** — the fragmentation branch takes any `improvement >= 0` with fewer segments while its docstring and log line claim cost-neutrality; `plan_fragmentation()` counts each night's charge window above the reserve as a segment, so it reaches charge plans, not just the export staircase. The `plan_tiebreak` suite's "cleaner but costlier plan is rejected" case passes no cost args, and passing real `cost_prev`/`cost_new` fails the branch today. (GH#5991)
- **Charge and hold writes alternate every 5 minutes while the target is steady** — SoC flips 1% across the target: the `execute.py` hold gate `soc_percent >= inv_target_soc_percent` has no tolerance, and the `- 1.0` hysteresis nested inside it is dead. (GH#5083, open)
- **Low power charging does nothing, still charges at full rate, shows "rate zero" on a dawn-split window's dark half, or changes rate several times within one window** — all by design: `find_charge_rate()` uses max rate when the window's average remaining PV forecast is at least `low_power_pv_threshold_w` (150 W, the same threshold driving the dawn split), re-runs every cycle filtered only by `rate_tolerances()`' 5%; a dark half showing "rate zero" is frozen at the reserve (`FrzChrg`). Treat requests as enhancements. (GH#4577, GH#4975, GH#3311, GH#5241, GH#5536, GH#2628)
- **"Predbat won't charge when the battery is cold"** — `find_battery_temperature_cap()` treats curve values as capacity-per-hour fractions of `soc_max`; a `0.00` step is a genuine 0 kW cap (the docs' own Gen2 example sets `0: 0.00`), so with a charge-current-triggered BMS heater that is a causal loop: no planned current → heater never fires → cells stay cold → cap stays 0. Without `battery_temperature_history` one temperature spans the horizon and `predict_battery_temperature()` repeats 24 h-old deltas, blind to heater runs and charge self-heating; no heater concept exists, and one would have to be stepped in `predict()` and mirrored in the kernel. (GH#5919)
- **Every planned charge capped at a temperature curve's coldest step while the live battery reads warm** (e.g. 1.39 kWh into a 9.5 kWh pack for a 30-minute window), and `predbat.battery_temperature` pinned at one value across the horizon — the prediction never reads the live `battery_temperature`. `predict_battery_temperature()` anchors on `history[0]` and adds the 24-hours-ago delta per step, so the whole horizon is whatever the `battery_temperature_history` entity recorded: a sensor that exists and records 0 (a GivTCP stack BMS sensor can, for days) predicts 0 °C, and a sensor with no rows predicts the 20 °C default instead — the opposite failure, equally silent. Nothing sanity-checks the two args against each other, so a mis-set history sensor looks exactly like genuinely cold batteries. Check the history entity really has non-zero rows before believing a cold-weather report; every auto-configuring integration binds its own sensor, so a hand-set or vendor-template value is the usual source. (GH#6193, verified against the reporter's dumps; the anchoring is deliberately unchanged by PRs #6201/#6203)
- **Two charge windows meet at 00:00 inside one continuous cheap period** — `calc_dawn()`'s light latch resets at midnight; since PR #5709 `find_charge_window()` splits only at dawn. (GH#5205)
- **`calc_pv_light_dark()`/`calc_dawn()` answer "before dawn", not "is it dark now"** — within each calendar day the light flag is a one-way latch: everything from the first forecast bucket at or above `low_power_pv_threshold_w` (default 150 W) to midnight reads light, including after sunset. That is deliberate (it exists to find dawn and split a charge window, #4557/#4699), and there is no dusk detector anywhere, so any "it is dark, nothing can charge" consumer needs its own classification or it will treat all evening as daylight. The dict is stored on the PredBat instance by `fetch_pv_forecast_and_dawn`, but is empty with no PV forecast — which reads as "never dark" rather than "unknown". (GH#6181)
- **A charge window is armed (`set_window_minutes`, default 30) at the inverter's full rate and only throttles a minute in, with `set_charge_low_power` on** — measured ~60 s and ~0.1 kWh, so it cannot explain a window that "finishes early"; check that separately. The low-power rate is only *written* inside `execute_plan()`'s running-window branch — `find_charge_rate()` is called from `predict()` and from the plan's display path too, but those recompute it for the model and the page and write nothing. So every cycle outside a window leaves the rate unclaimed and the executor's default writes `battery_rate_max_charge`. The device then reports the throttled figure one cycle (plus the component's write pacing) after the window opens — on Hanchu, a ~45 s gap between the `charge_rate` write and the `iotSet` carrying it is that pacing, not ordering. Computing the rate before arming means first settling which number is authoritative: `predict_soc`'s implied rate and the executor's computed rate disagree for the same window (GH#5854). Applies to every inverter type, not just Hanchu. (GH#6190, verified 2026-11-14 against a live log and hardware)
- **Turning `debug_enable` on changes the plan** — deliberate: `kernel_supported()` refuses under `debug_enable`, and Python honours the coarse `enable_fast_mode_levels` step while the kernel runs at 5 minutes, so near-ties can flip. (GH#5408, GH#4453)
- **Control SOC only: status `Demand` during the inverter's own charge window, the running charge's target churns or drops to the reserve, or an AC-coupled inverter charges to 100%** — `isCharging` used to be set only inside `execute.py`'s `if self.set_charge_window` block, so a charge the inverter ran itself counted as no charge (no planner keep, `inverter_soc_reset` wrote 100%, freeze-export-during-demand paused it); fixed 2026-11-06. The near-tie tie-break that adopted those plans works as designed. (GH#5991, GH#5987)
- **"Why does the plan use these charge windows" in Monitor / Control SOC only** — with `set_charge_window` off, `calculate_plan()` clones `self.charge_window`, which the executor fills from the first enabled inverter's own programmed windows (repeated daily to the forecast horizon), so the planner optimises targets over the inverter's windows and the tariff's never appear; a mixed fleet follows only that first inverter. Start here, not at the rate tables. (PR #6001)
- **`best_keep {}kWh` / `keep {}kWh` in a plan log is a penalty, not a planned level** — `metric_keep` prices the deficit below `best_soc_keep` at the minute's import rate × `best_soc_keep_weight` × duration, so on a two-tier tariff it can dominate the metric against a real plan cost of hundreds of pence. Judge fills by replaying the captured instant with keep/weight variants, not by the log figure. (GH#5987)
- **Predbat exceeded the site's import ceiling** — the planner has no import clamp: `import_limit` is only a discovery rating (sunsynk/fox/deye). Draft PR #5486 (diagnostics) open. (GH#5490)

### Plan: exporting

- **Exports happen at the wrong time** — `plan.py`'s export pass order, `combine_export_slots`, `metric_min_improvement_export`. **"Random" exports that lose money on a flat export tariff** — see GH#4840 under "Check configuration before code".
- **"The battery charges to full before peak solar and then PV is clipped"** is an unwritten headroom preference, not a scheduled charge — Predbat schedules only *grid* charge windows, so the SoC rise through PV hours is the inverter putting DC surplus into the battery and cannot be deferred by the plan. Its only clipping levers are the export plan (`export_limits_best` `freeze` holds the battery while PV goes to grid, `target` discharges to a level), and nothing prices headroom against *forecast* PV above the inverter/export cap — that ask is GH#4865 (with #1206; #5460 is a dup). Replays of the reporter's dumps show ~10–19% headroom reserved with the residual clip knowingly accepted. Do not promise zero clipping when `export_limit` equals `inverter_limit`: once the battery is full, every kW above that figure plus house load is clipped whatever the plan does. (GH#6193, replayed 2026-11-14)
- **"Stop exporting below Xp" is a margin gate, not a price floor** — `metric_min_improvement`/`metric_min_improvement_export` require a window to beat *not* doing it by that many pence per interval (scaled by window length and export power), so a value near the price threshold only approximates a band and never means "no export below X"; the export gate also deliberately excludes `best_soc_keep`. Partial power already exists via `set_export_low_power` and `LOW_EXPORT_POWER_LEVELS` (0.7/0.5/0.3 rungs) — what is missing is a price-linked rule to pick the rung. (GH#6172)
- **Exports at the export peak then imports all evening ("never sells above my buy price")** — sell is weighed against the refill price, not the concurrent import price; `best_soc_keep` handles the tail and `best_soc_min` binds only in export windows. Exports run at full power, so window length is the stop line; a row's limit % is the SoC reached. To answer the report, compute the nominal spread first: `export_peak × (1 − discharge_loss) − import_peak`. Negative → suspect the fixed #5566 mechanism (PV90 chose export depth on a losing nominal case; `load_scaling90` now defaults 0.9). Positive → the plan is behaving as designed: export at the peak, buy the small evening load back at day rate, refill cheap overnight — answer with the arithmetic and the levers (`best_soc_keep`, `best_soc_keep_weight`, `metric_battery_cycle`); `Calculate Best options` prints the effective loss/cycle config. (GH#5509, GH#5566, GH#5579, GH#5866)
- **`Best export window @ 0p` on a non-zero export tariff** — a stale discharge window read back from the inverter (`update_status()` pre-fills `average = 0`), used verbatim under `calculate_best_export: false`. A `discharge_rate` + reserve write after a charge window is the routine restore, not an export. (GH#5036)
- **"Charging and exporting in the same slot" in the plan html** — two windows in one 30-minute row; `output.py` splits the State cell deliberately. (GH#4987)
- **Loss-making forced export kept plan after plan; `Prune kept hedge export slot` / `Reverted change to d window N`** — fixed in PR #5977; see "Check configuration before code". Prune pairs read (without slot) vs (with slot), lower is better; `export_threshold_penalty` is charged per plan interval of export still to come (PR #5874). Reporters swap pv10/pv90 labels in prose — check the `base10`/`base90` series before accepting a scenario attribution (PV90 runs later than nominal). The dead-slot branch ("Prune dead") still drops on nominal-identical-plus-no-SoC-move alone without consulting the blended metric — the residual trap when pv90 planning values a nominal-dead slot. (GH#5969)
- **An evening export drains to the same level whatever the load risk, or drains deeper into the cheap band than expected** — two separate controls. The pv10 scenario used to score target exports at `best_soc_min`; since PR #5736 it floors them at the nominal run's end SoC. And since PR #5874 (2026-10-31) `export_gate_share()`/`export_threshold_penalty()` charge `metric_min_improvement_export` per plan interval of export still to come, scaled by the option's power, and each option's score is compared against the export-off baseline — so every extra 5 minutes of a deeper start must earn its own share. On a pre-v9.6.4 log the old rule compared each start only with the export-off baseline, so a metric improving downward always chose the deepest. Raised far enough, the gate still rejects the whole export, which the plan write-backs re-adopt. (GH#5860, closed fixed in v9.6.4; re-checked on main 2026-11-21)
- **An export window is in the plan but moves nothing** — limits in the sentinel band (99.3/99.5/99.7) mean "Hold exporting" in both engines, and 99.0 is the freeze sentinel (GH#4914; whether a 99% floor still emits it is unverified). A freeze-export window zeroes an overlapping charge candidate (`remove_intersecting_windows()`). Change both engines together (`test_kernel_parity.py`).
- **A `FrzExp` slot / export limit 99.0 in a zero-PV period is not a fault** — freeze export runs the same ECO/Demand flow with charging suppressed (the freeze flag only scales the charge branch), so at PV 0 it computes identically to Demand and holds nothing Demand would not hold; the label is cosmetic. Dead freezes are removed by `prune_dead_plan_slots` (since #4491, first tag v8.48.1) rather than `clip_export_slots`/`clip_charge_slots`, so a dead slot in a plan is expected on anything older. (GH#4124)
- **A dump's `rate_export_cost_threshold` is rewritten from the plan's own level**, so it is not the operating threshold (GH#5221). On a pre-v9.3.7 log, every ordinary export window vanishing while a saving session or Axle event was in the horizon was that threshold latching at 99 (fixed in PR #5163).
- **Predbat plans exports the site may not make (DNO or installer restriction)** — on Teslemetry see `update_battery_export_permitted()`. Elsewhere `export_limit: 0` (zeroes solar export) and `battery_rate_max_discharge: 0` (stops self-consumption) both mis-model it. (GH#5710)
- **Do not compare the plan table's two "(w/loss)" columns** — they are different units: Import-(w/loss) = raw / `battery_loss` / `inverter_loss` + `metric_battery_cycle` (the cost to re-buy and store a kWh at that rate); Export-(w/loss) = raw × `battery_loss_discharge` × `inverter_loss` − `metric_battery_cycle` (earnings per stored kWh). "Export w/loss 32 < Import w/loss 40, so holding wins" compares sell vs re-buy; the comparator for holding an already-charged battery is the raw import through the discharge chain, or the overnight refill once demand is met. The loss chains cancel when both paths discharge the battery, so the raw export-vs-import spread is the trade for the displaced part, and the sim models both chains — there is no export-revenue bypass. When export < import the optimiser trims rather than forbids (the `Export windows filtered [... @ N%]` percent is a SoC floor, not a price), and `metric_min_improvement_export` ignores `best_soc_keep` by design. (GH#5999)
- **The export icon or `binary_sensor.predbat_exporting` says off while the battery exports** — `isExporting` is not set by the demand-freeze `[Freeze exporting]` block; read the status text. PR #5131 open. (GH#5125)

### Inverter control and writes

- **Export start time rewritten to "now" every cycle of a running export** (`Adjust force export to True, change times from 20:55:00 - ... to 21:00:00 - ...`) — the overlap guard after `Include original export start` in `execute_plan()` counted an empty charge window, or one starting as the export ends, as an overlap. Fixed in PR #6005.
- **Inverter setting not applied** — follow `execute.py` into the component's reconcile loop, and check `read_only`.
- **A parallel master/slave pair gets every control written twice, once per inverter object** — nothing suppresses writes to a non-first unit, and the two write helpers differ: numeric writes read back and skip (`No write needed`), while `write_and_poll_option` writes even when the entity already matches, so window/time entities get a service call every cycle. Silencing the slave's writes alone halves the delivered power (#5556) because the rate/target split hands the master only its share: the working shapes are one virtual inverter (Sunsynk) or suppress the slave *and* write the group total to the master (the Solis `solis_parallel_slaves` pattern, extended past slot current). (GH#6169)
- **"Predbat writes my timed charge/discharge entities although apps.yaml sets `set_charge_window: false`"** — that key and `set_discharge_window` are dead config (in neither `CONFIG_ITEMS` nor `APPS_SCHEMA`). Runtime gates come only from the mode select (Control SOC only = no ordinary window writes, Control charge = charge, Control charge & discharge = both). The `*_start_service`/stop/freeze paths are gated on `set_soc_enable` (on in all Control modes, off in Monitor), so **Control SOC only leaves the inverter's own windows alone and still drives a service/script-controlled one** — except a `set_read_only`/mode-change reset (`reset_inverter()`), which writes both sides whatever the mode. `has_time_window` is likewise `INVERTER_DEF`-only and unread. An install unaffected to v9.3.6 that sees writes after upgrading is the v9.3.7 change (#4738) that honours a real apps.yaml `time.*` mapping. (#6069, docs PR #6073)
- **A mapped charge or discharge time entity is written 00:00–00:00 with no window planned** — on `has_charge_enable_time: false`, Predbat's `scheduled_charge_enable` placeholder defaults to **on**, so `disable_charge_window()` takes its enable branch and calls `adjust_charge_window(midnight, midnight)`; the discharge twin is `adjust_force_export(False)`'s midnight disable for `has_discharge_enable_time: false`. On Predbat's own dummy that is bookkeeping, but on a real register-backed entity it closes a standing window (a SolaX mode-8 site loses house supply). Fires once per change into idle. (#6073, #6069)
- **Battery charges to 100% at start, on a mode change or on `set_read_only` (Victron `SK`, any `has_charge_enable_time: False` profile)** — `reset_inverter()` writes `adjust_battery_target(100.0, False)`, a real order where that register is a floor, on any `reset_inverter: True` config change including startup, even in Read-Only.
- **`Note: Inverter does not support charge/discharge freeze - disabled` despite the flag; `has_service_api`/`has_rest_api` changes nothing** — capability flags are `INVERTER_DEF` values in the `inverter:` block (a custom type copies `GE`); `has_service_api` does not exist and `has_rest_api` is never read. Services come from the six `*_service` keys. None of these keys is in `APPS_SCHEMA` or read by `get_arg()`, so the same flag at `pred_bat:` level is silently ignored — `templates/tesla_powerwall.yaml` ships exactly that inert `charge_control_immediate` (still inert 2026-11-19; PR #6114, open, would warn). (GH#1406, GH#5066, GH#5203, GH#6113)
- **`write_and_poll_switch: No entity_id for scheduled_charge_enable ... to write` / `write_and_poll_option: No entity_id for inverter_mode`, only a red `with Errors reported`** — presence flags with no bound entity; custom types inherit GE's `has_charge_enable_time: True` / `has_ge_inverter_mode`, so check the `inverter:` block first. (GH#5539)
- **Reserve ratchets up and never returns (`Increasing set_reserve_min from X% to battery_min_soc of Y%`)** — a one-way raise in `Inverter.refresh_config()`; bound to a live entity (the SA Growatt SPH template) it read back Predbat's own reserve write, and a hold writes the current SoC, so each hold pinned the floor higher for good (8%→97% in one night, then it blocked export). Fixed in PR #6137: a `battery_min_soc` naming any inverter's reserve entity is treated as unset, with a warn — but an already-raised `set_reserve_min` must be lowered by hand, and an older log still reads as the old bug. (GH#4013, GH#5232) Related: **"Predbat always sets the reserve to X%" where X = charge target + 1** is the hold-on-reserve path (`Hold charging as SoC ... is above target SoC` then `Current Reserve is ... new target is X%`); changing `set_reserve_min`/`set_reserve_enable` drops the reserve to the device floor for a cycle. (GH#5660)
- **Hundreds of `Trying to write N to X didn't complete got M` overnight** — check the plan had a window: idle cycles rewrite rates to max and `write_and_poll_value()` has no failure dedup, so a refused register (SolarEdge preserve-charge) repeats every cycle. False alarms: see *HA write/verify*. SolarEdge `Connection to inverter ID N failed` is the HA integration. (GH#5073, GH#5324)
- **Every charge/export window runs ~N minutes late** — the inverter's clock; compensate manually (`inverter_clock_skew_*`). `check_clock_skew()` warns hourly at ≥5 minutes from v9.0.2. (GH#4927)
- **GivEnergy-mode discharge times appear in the inverter portal only once the window starts** — as coded: `adjust_force_export()` nulls start/end when `inv_has_ge_inverter_mode and not force_export`. The 30 s `Sleeping (workaround)` settle can delay full rate ~10 minutes. (GH#2649, GH#4180)
- **Charge or discharge rate pinned far below the hardware's** — check the component's auto-config rate binding first (GE Cloud: the `charge_rate` entity's `max`; Fox: a duplicated `batteryList`, or the truncated `capacity` field; Solis: its notes); compare `battery_rate_max_raw`/`soc_max` in the dump with the nameplate. The only raise lever is `battery_rate_max_scaling[_discharge]` (modelled rates only); `inverter_limit_override` is another cap, never a raise, and it also caps **export**: `refresh_config()` mins it into charge and discharge, then `inverter_limit_export` defaults to the already-capped discharge, so without an explicit export limit the override silently limits export too — and the per-direction manual-API overrides are read before it, so they cannot raise above it (GH#6170). CONFIG_API_OVERRIDE/manual-API overrides do not reach a component's `set_arg` binding. (GH#4908, GH#4919, GH#4940, GH#5938)
- **Low power computes the right rate but a service-driven inverter still charges at full power, or `{power}` is one cycle behind the rate helper** — with `output_charge_control: "power"` there is no dummy `charge_rate`, so `{power}` is `battery_rate_max_raw`. Since PR #5149 the rates are written by `apply_rate_intent()` at the end of `execute_plan()`, while `adjust_charge_immediate()`/`adjust_export_immediate()` build `{power}` from the entity as it stood before that write, so the payload always carries the previous cycle's rate. `target_soc` and the times are current-cycle, `{power}` alone lags; templates cannot substitute the watt value (`{charge_rate}` resolves to the entity id). Fix queues the service calls until after the apply (PR #5373, open 2026-11-17). (GH#5182, GH#5252)
- **Monitor mode is not read-only** — the mode select sets only the windows/SoC flags; `set_read_only` is a separate switch, so with `set_freeze_export_during_demand` on a plan-free Monitor mode still writes a pause-charge plus rate-0. A control-mode pause is also not released by switching to Control SoC only/Monitor: the release runs only where `reset_rates` triggers. (GH#5856)
- **Inverter service calls stopped, or re-sent every cycle** — `Calling service` with no effect is an HA rejection (`was not accepted`); `Skipped service ... as it was previously called` is dedup keyed by domain alone (`hash_index = domain`), so two inverters on one domain re-call every cycle. A rejected call is dropped from the dedup and reissued next cycle; an accepted call that died downstream (Modbus drop, gateway republish) was recorded as done — skipped for the window while `control_failures` grows, and `control_monitor` warns without re-applying. The hash is recorded only after every template call was accepted (`call_service_template()`), so it never recovers from a device that accepts then reverts (see the Solar Assistant bullet); it keys the last accepted call per domain, so an identical stop accepted in another state can silence an opposite-side transition; it is computed from the `data` argument, so different resolved payloads can still collide; and a freeze call passes `target_soc` = the live SoC, so every 1% tick makes a new hash. (PR #6124) Grep the template for `repeat:`/`always:` — those re-send regardless. (GH#5021, GH#5627, GH#5888, open)
- **Solar Assistant: charge windows are planned but the battery ignores them / drains through them (SA Growatt SPH)** — the work-mode select is the operative control and SA firmware clears the TOU slot registers 0.4–0.9 s after a mode write (mirrors #2654), so slot values alone control nothing and re-arming or monitoring the slot selects never catches it. SA republishes the cleared slots as `00:00`/`23:59` with enable off, and the read path accepts that pair as a live full-day charge window (`start == end` is the only disable test), with `Include original charge start` adopting the 00:00 start. A fix must re-send/verify the mode, not the slots; `repeat: true` is improvement-not-cure. Start from the dump's `control_ledger.events` and `predbat.control_failures`; a window-end "Load first" + enable-off can be Predbat's own teardown. (GH#5951)
- **Solis: no charge or export since a pod restart, `Failed to verify CID 636 storage mode ... read back` (2 lower), errors naming `cid 103`** — a timed-out CID 6798 read left a TOU V2 inverter treated as V1; fixed in PR #5864. See the *Solis* notes. **Sigenergy: MQTT `published` but commands do nothing** — the publish line proves nothing; run `sigenergy.py --command-test --command-mode idle`, and see the *Sigenergy* notes.

### Rates, costs and savings

- **`cost_today` steps up after each half hour of an Intelligent car charge and falls back 15–60 minutes later** — `today_cost()` re-prices a running dispatch before `completedDispatches` lists it; `octopus_held_update()` bridges it (`OCTOPUS_DISPATCH_HOLD_MINUTES`). See the *Octopus* notes; test `octopus_dispatch_hold`. (GH#5520)
- **The half hour under a running Intelligent dispatch stays at the peak rate while the car charges** — `started_dispatches` is read but never priced (completed/planned only); the `Octopus: Dispatch timeline car N @ ...` log line proves whether the entity listed it. See the *Octopus* notes. (GH#5773)
- **Rates read zero, or `Warn: Octopus: No Octopus data in sensor ... attribute 'rates' / 'raw_today' / 'prices'`** — `fetch_octopus_rates()` reads only `rates`/`raw_today`/`prices` (plus `raw_tomorrow` for non-Octopus entities); else use a template sensor. Keys: `rate`, `value_inc_vat`, `start`/`end` (×100, so EUR shows as cents), `value`, `price`/`from`/`till`. (GH#5676)
- With a saving session or Axle event in the forecast, `rate_max`/`rate_average` stay event-boosted by design; `rate_minmax_excluding_saving()` keeps the low-rate classification clear of them, so a pre-v9.3.7 log with the day rate classed as low is that gap (fixed in PR #5163). (GH#5050, GH#5237)
- **"Plan has continual charge slots to 100%/HoldChrg through the peak" on a tariff whose export max beats the import max** — with `rate_low_threshold: 0` (auto), `set_rate_thresholds()` widens the import threshold to `rate_max + 0.1` when the export max beats the import max (also when alerts or manual SoC keeps exist): the `Low import rate windows [...]` filter becomes a no-op and buy-at-any-price/sell-at-the-peak arbitrage is what the optimiser rationally plans. Fingerprint: `Rate thresholds ... import <rate_max+0.1>` with every 5-minute slot in the low list. Workarounds: a non-zero `rate_low_threshold`, `set_export_freeze`, or more keep/`metric_battery_cycle`. (GH#5990, re-verified 2026-11-13)
- **Today's cost over-costs every car-charging slot by roughly car kWh × rate** — with `switch.predbat_car_energy_reported_load` off, `car_outside_clamp_energy()` (in `today_cost()` and the History rows) already prices the car from `car_charging_energy` at each minute's rate, so a smart-meter `import_today` that also sees the car counts it twice. This inverted the pre-#6023 advice to point `import_today` at a smart-meter daily total on an install whose charger sits outside the inverter's meter; check the switch position before blaming `today_cost()`. (GH#6149)
- **Guidance for one setting lives in three places** — the docs page, a code comment in the component's `automatic_config()`, and the template/regex. A behaviour change that flips which setup users should choose (#6023 above) has to be fixed or at least grepped in all three; #6149's docs-only fix left the Hanchu `automatic_config()` comment still recommending the smart-meter override. Same shape as the "apps.yaml entry ignored" story, which is per-integration and lives in `automatic_config()`.
- **Import cost far above the bill on a 3-phase site with per-phase sensors** — `minute_data_import_export()`/`minute_data_load()` sum phases instead of netting, double counting cross-phase offsets in today-so-far cost (plan unaffected). (GH#5746, GH#5835, GH#4856)
- **`cost_yesterday` / the History view uses today's rates for yesterday on a dynamic tariff** — `rate_replicate()` back-fills negative minutes with today's same-time rate, which `calculate_yesterday()` shifts back 24 h; the live plan is unaffected. (GH#5194, GH#3267, open)
- **`cost_yesterday` / `savings_yesterday_*` show the wrong day after a clock change** — `calculate_yesterday()` read `minutes_back = minutes_now + 1` while `minute_data()` keys by elapsed minutes, so lookups were ±60 off on a change day; yesterday's and today's figures are now read from the real start of the day (PR #6084, merged 2026-11-10). Keep the mechanism for reading older logs. (GH#5760)
- **An old History day still shows "(import, export not billed yet)"** — billing stops re-reading a local day once it is `BILLING_SETTLE_DAYS` (5) old, however incomplete (`still incomplete after 5 days, so it won't be read again`), so a half hour missing then never arrives; `_parse_node()` also drops a half hour whose bucket kWh do not sum to the metered kWh, or whose energy has no price yet (that one is re-read). With an export meter, a row whose import leg is billed and export leg is not is flagged `billing_pending_export` and shows as "import, export not billed yet" — on a settled day that mark never clears, and `missing_slots`/`export_pending_slots` deliberately count the two kinds apart. `history_billing_mark` is a per-leg [count, newest-key, cost, kWh and standing-charge totals] over the whole cache, so one late or re-priced slot rebuilds every History view, not just that day's. (GH#6009/#5926, verified 2026-11-14)
- **The Billed/Diff columns, and the Happy-Hour credit marks, silently vanish on `plan_interval_minutes: 15`** — `attach_billing()` returns before adding any billing field when the interval is not a multiple of 30, with no warning, and `docs/energy-rates.md` tells 15-minute-tariff users to set exactly that value. 30 and 60 work. Either the guard admits 15-minute rows (mapping each row onto billable half hours) or the docs must warn. (PR #6116 review, 2026-11-11)
- **History's Billed column shows a car-dispatch evening at Home Standard Rate, but the Octopus app shows EV Low Rate** — Kraken first publishes an IOG dispatch evening outside 23:30–05:30 under `Home Standard Rate`, then re-rates the same half-hours into `EV Low Rate` + `Home Low Rate` a day or so later. A complete day is now read again once per local day (per-leg, per-day `rechecked` in the saved cache) until it settles at `BILLING_SETTLE_DAYS`, so a re-price published after the day's re-read shows the next day. A failed re-read keeps the cached figures and counts as that day's re-read; the newer complete days it skipped are read at the next refresh (otherwise one failing day held back every newer re-read for the week — `could not read the ... billing for <day> ... again`). A cache saved without `rechecked` re-reads all complete days on the first refresh. Predbat's own cost is unaffected — check `predbat.rates` and `cost_today_car` first; to tell a stale cache from a real peak charge, query Kraken `measurements` and compare with `sensor.predbat_billing`'s `slots`. (GH#6252/#6274, PR #6275, verified 2026-11-20)
- **"I can only override one plan slot at a time"** — by design (one `POST /rate_override` and a reload each). Batch: `rates_import_override`/`rates_export_override` in apps.yaml, or the manual API. (GH#5289)

### Sensors, history and load data

- **`Warn: No history data found for X` (nothing after the colon) plus `Error: Failure to fetch history for X` every cycle, status `car_charging_energy entity has no data, falling back to car_charging_threshold heuristic`** — component entities are created by POSTing to `/api/states`, and Home Assistant's **recorder** can hold zero rows for them; the history REST API omits an entity exactly when the recorder has no rows in the window, so the repeat is a genuine live "no rows" answer, not a cached miss (`HAHistory` re-asks every 2 minutes). The FAQ's recommended recorder include list predates the charger components' `sensor.predbat_*` entities, so FAQ-followers record nothing for them and `car_charging_hold` silently degrades to the threshold heuristic. Tell: `get_history_wrapper()` raises a bare ValueError, so an empty exception message means HA answered `[]`. Any REST-published component sensor can hit this, not just Hypervolt's `car_charging_energy`. (GH#6142)
- **Plan tab blank / no plan shown in HA** — `predbat.cost_today` is missing from HA recorder history (recorder configuration). See test `faq_recorder_config` and `docs/faq.md`. (GH#3936)
- **Energy totals jump, or a day counts a huge figure** — look for a counter dip then recovery: `minute_data()` drops only upward steps above `MAX_INCREMENT` (1.2 kWh/min), so a gentle recovery after a held dip counts in full. Applies to any `*_today` binding. (GH#5388, GH#5356)
- **The plan is too optimistic about solar on an AC-coupled site whose load reads ~0 in daylight** — derived load is already net of PV and `get_diff()` subtracts PV again; no generic netting option. Calibration side: *Solcast*. (GH#5552, open)
- **SoC reads too high, never falls, or is frozen** — check the sensor behind `soc_kw` (a "charge today" sensor ratchets); `battery_soc:` is not a config key. `Inverter N SoC:` fixed while power moves is a frozen entity (often mixed GivTCP prefixes). `soc_max` bound to "kWh remaining" shows as `nominal_capacity` on `predbat_soc_max_calculated` moving with charge. A sensor that vanishes after a restart may have its only publish inside a recovered-history branch (GH#5222). See *SoC sources*. (GH#4884, GH#5522, GH#5650)
- **`Warn: Found N periods of zero load with power data, filling using power integration`** — since PR #5921 (2026-11-07) `load_counter_quantum()` works out the counter's coarseness and splits each flat stretch between the counter's step and the power, so the fill conserves the counter's totals (older logs, pre-fix, read low-load history ~2x high on coarse counters, GH#5855). The warn now fires only when a run was actually filled and carries the counter quantum — "load sensor steps 0.0000 kWh" means a fine counter where every plateau ≥ a gap is being treated as lost readings. A flat run touching the oldest minute is never detected (it cannot close in the scan), so the oldest minutes stay raw by design. `load_power_fill_enable: false` turns the fill off. (GH#3623, GH#5204; re-verified 2026-11-10)
- **load_today climbs by kWh per hour on v9.4.1, or `Filled N gaps in load_today ... from predbat.load_energy_h0 history`** — feedback on Predbat's own `load_energy_h0`, fixed in PR #5656 (2026-10-20). Read any sensor Predbat also publishes with `interpolate=False`: `minute_data` extrapolates past a fresh newest record. (GH#5652)
- **"Plan History" shows 0.01–0.02 in the PV (or load) column overnight instead of the empty-slot glyph** — that is the recorded `*_today` sensor still ticking (a uniform ~20 W-equivalent slope on some Sunsynk units), replayed by `calculate_yesterday()` through `step_data_history()`; the History view is recorded data, not the forecast plan columns. The glyph is shown only for an exact 0 after dp2, so anything ≥ ~0.005 kWh/slot renders as a number; and the PV tooltip says "from the Solcast forecast" even in History, which is the confusion to acknowledge in the reply. (GH#5904, 2026-11-01)
- **The Energy dashboard refuses a Predbat daily energy sensor, or shows a negative bar in the midnight hour** — HA accepts an energy sensor only with `state_class` `total` or `total_increasing`; `measurement` is rejected outright. Predbat's "today" counters reset at midnight, which `total_increasing` reads as a new meter cycle and `total` without `last_reset` counts as a negative change. The fleet is inconsistent: Deye (since PR #6053), GivTCP, Hypervolt and Predbat's own sensors are `total_increasing`, while the gateway and GE Cloud `*_today` attribute tables still ship plain `total` with no `last_reset` (re-checked 2026-11-16) — start from the component's attribute table or `publish_data` call. Not a learning bug: history learning reads recorded state through `minute_data`, so `state_class` never reaches the plan. (GH#6045)
- **HA's recorder logs `The unit of sensor.X (None) cannot be converted to the unit of previously compiled statistics (°C)`** — a numeric state with no `unit_of_measurement` meeting compiled metadata that has one; that entity's statistics are suppressed. An `unavailable`/`unknown` state cannot trigger it, and no current Predbat path produces it: the temperature sensor is the only writer of `sensor.<prefix>_temperature` and sets unit, device and state class on every publish. HA closed both prior reports (#126724, #155586) as benign, so a one-off points at HA and a recurrence means some other entity really is recording numeric states with no unit. (GH#6093, verified 2026-11-10)
- **A live export or charge window stops mid-slot after `Dynamic load last period 9.60kW, status high`** — `load_last_period` came from a coarse counter (Solis' whole-kWh `homeLoadTotalEnergy`); since PR #5851 (2026-10-29) "high" must be confirmed by `load_power` (fail-open: a sensor that is down reads None and the counter stands, so dynamic load is never switched off by a dead sensor). (GH#5851)

- **"I can't find or install HACS", or "my AppDaemon app stopped updating since the last HA release"** — HA 2026.11 built HACS in as the **Marketplace** (Settings → Marketplace, not the sidebar), so HACS cannot be installed on 2026.11+ and is removed on upgrade. (GH#1566, GH#5708, GH#5749)

## Traps when investigating

### Versions, logs and attachments

- **Version drift.** Compare the log's version with `git tag --contains <sha>` (fetch tags first); many reports are fixed on main, and `v9.0.1` is `v8.55.1`. Treat "worked on 9.x, broke on 9.y" as a version question: `git show vX:<file>` before accepting a regression (GH#5390).
- **A tester's `AttributeError: '<Class>' object has no attribute '<method>'` after copying PR files over a release** — maintainers ask testers to copy individual files from a PR's Files-changed page; a partial copy leaves a new file calling a method that only another PR file adds, and a force-push can leave the traceback on a superseded revision. Neither is a code bug: `git grep` the exact source line against the PR's old SHAs and its head, and `git diff --stat <release-tag> origin/main -- <files>` shows which files can be copied alone. (PR #6165/#6161, verified 2026-11-14)
- **An HA notification quoting `Source: custom_components/<integration>/__init__.py:<line>` pins a third-party integration's release**: fetch that file at each upstream tag and match the message's line number. On #6059 line 3026 matched solax-modbus `2026.10.02` while main was at 3064, and the matched release's code differed from main — read the matched release, not main.
- **Tracebacks showing `/config/hass.py`, `/config/predbat.py`** — the HA add-on runtime layout: the add-on downloads the latest release zip and copies `apps/predbat/*` and `apps/predbat/config/*` flattened into `/config`, then runs `cd /config && python3 hass.py`, so line numbers match the released tag, not main. The download is gated on `/config/apps.yaml` being absent, so reinstalling the add-on does not refresh stale runtime files. (GH#5869) A `ValueError: bad marshal data (invalid reference)` from `_compile_bytecode` at aiohttp import is corrupt compiled bytecode in the add-on's locally built container (no prebuilt image; deps pip-installed at build): the crash is before any Predbat code, so classify `configuration` (precedent #3910) and look for a persistent disk cause (suspected).
- **A `predbat.log` spans versions and restarts** (appended across upgrades and downgrades, GH#5178). `version X currently running` prints every cycle, so count restarts by `Loading apps.yaml` → `Predbat: Startup predbat`. A restart without `Predbat terminating` was an outside kill, whose trigger is only in the add-on log (GH#3969) — the wrapper's own line is `Shutdown, sleeping 20 seconds before restarting` (GH#5886; the wrapper is not in this repo).
- **`Best charge window` is the prefilled incumbent, not the optimised plan**, which is in the later `Raw/Filtered charge windows` lines. In a repeated pair in one tick the later line is the recompute (GH#5434, GH#5344).
- **Prove an attached debug yaml is the reporter's own** (compare `soc_kw` and serials/account ids at its capture minute with their log); once proven, it beats the issue prose (GH#5335). Attachments disagree in time and identity: numbered logs (`predbat.1.log`, `.2.log`) are overlapping snapshots, not rotation order (check head and tail timestamps); debug-history snapshots are ~3-hourly; `predbat_debug.yaml` is download-time state (GH#5344). A new attachment URL can 404 for 10+ minutes (GH#5503); two attached dumps can be byte-identical — a "two dumps" corpus may be one snapshot (GH#5943). Ring snapshots are `debug/predbat_debug_<id>.yaml.txt` (GitHub rejects bare `.yaml`/`.tar`), and the per-cycle `create_debug_yaml()` dump still needs renaming; the HA Companion app's webview ignores `Content-Disposition: attachment` (GH#4720).
- **Evidence hosted on Google Drive cannot be fetched by tooling** (npz model files and the like): the URLs need interactive Google sign-in — ask for a GitHub-hosted attachment, or reason from the log and dump. (GH#4673) **A reporter's screenshot when `curl` is denied**: WebFetch the `user-attachments/assets/<id>` URL (GitHub 302s to a signed S3 URL expiring in ~5 minutes), WebFetch *that* within the window, then Read the saved `tool-results` file that fetch wrote — the Read is what renders the picture, as the text reply is just "raw JPEG binary". `user-attachments/files/<id>` downloads with plain `curl -L`, so a ">10 MB, unfetchable" conclusion is about the WebFetch route only.
- **HA entity-history CSV exports cannot prove write provenance.** In one export every `context_event_type=call_service` row shared a single context id across 7 hours (impossible), and a provably-external flip carried full call_service context. Attribute by value + timestamp cross-referenced against `predbat.log`'s `Wrote X to Y successfully`/`Calling service` lines, never the context columns. (GH#5951)
- **Warnings.** Routine `Warn:` lines are the cause only if their timing matches the report. HA core's `Referenced entities ... are missing or not currently available` is only in the HA core log (GH#5420).
- **Log severity is the message prefix, read by two different consumers** — the console prints a quiet line only when its prefix starts with error/warn/info, while `classify_log_line()` (utils.py) is substring, so a line containing "warn"/"error" anywhere lands in the web Warnings tab whatever its prefix; word log messages accordingly, and de-noise a repeating warn by switching it to an Info prefix once the condition is known-persistent (PR #5841's pattern, verified 2026-11-06).
- **A quoted "Predbat did not react until ..." timestamp is usually the latest repeat of a per-cycle line.** `Car N is charging now outside its plan`, `Current SoC X% is less than Target SoC Y. Grid charging enabled`, `operation_mode = ...` and `Info: Completed run status <status>` re-log every 5-minute cycle for as long as the state holds, so grep for **every** occurrence of the quoted string and anchor the timeline on the first one before judging latency (on GH#6031 the first was 17 minutes before the quoted pair; real end-to-end latency was ~30–45 s). (verified 2026-11-07)
- **Hardware behaviour needs the hardware.** A unit test shows what the code does, not what the inverter did; say the maintainer must confirm.
- **A flat SoC is not necessarily a stall.** On a large pack one percent can be ~10 minutes at 2 kW (GH#4784).
- **Check that the report's premise exists.** Reports have cited AI-invented settings (GH#4918), features only on unmerged PRs (GH#4917), history `git log -S` disproves (GH#5022) and false "expert gated" claims (GH#5237). Grep `config.py`/`APPS_SCHEMA`, read each item's `enable:`, and check a proposal's symbols are on main (GH#5063).

### Replays and debug dumps

- **Copy `manifest.yaml` into a new worktree before running anything.** It is gitignored and *generated* by the self-update path from the release file list, never a source-controlled module list — a new module needs no entry, and a working-tree copy is whatever release was last downloaded over that tree (verified PR #6176). Without it `check_install()` downloads the release over tracked files and exits (`Predbat files are not installed correctly, trying to download them`). Recover: `git checkout -- .`, `git clean -fd apps/predbat`. **A/B across versions by checking out the old tag in place** (`git worktree add` is denied under triage permissions), then `./run_all --debug_file <dump> --redo` on both — first confirm the tag diff is inert for that config and the replay matches the live log (GH#5719).
- **Replay-probe pitfalls.** The dump's window list holds both days in one minute-of-day frame, so filter with `1140 <= start < 1440`. `Prediction.__init__` copies SoC, rates and ~200 other attributes from `base`, so set them first or rebuild it (GH#5616, PR #5756).
- **A dump's `now_utc:` line can carry a YAML anchor** — older writers dumped the whole dict at once, so `now_utc` and `plan_last_updated` (the same datetime when a plan was recomputed) alias: `now_utc: &id002 2024-12-13 08:00:00+00:00`, with `plan_last_updated: *id002` below (both committed `coverage/cases` dumps show it). Allow an optional `&idNNN` anchor (plus its space) after `key:` in any text regex, or parse with `yaml.safe_load`; never infer "not a dump" from a regex miss — check for `debug_schema_version`/`CONFIG_ITEMS` too. (PR #6168)
- **A log stamp and a dump's `now_utc` are different clocks** — log lines carry the host's naive local wall clock (`datetime.now()`), while `now_utc` is aware in Predbat's configured `timezone` (still named `now_utc`; `update_time()` converts into `local_tz`). When the two differ (UK host with `timezone: UTC`, or an HA host abroad) a "did anything run after this dump?" comparison is silently off by the difference. Compare the `minutes now` each run line records, or apply `now_utc`'s own offset; never compare raw strings. (PR #6168)
- **`pv_forecast_minute`/`10`/`90` are keyed by absolute minute of day; `..._step` by minutes from now.** `step_data_history(..., forward=True)` consumes them at `item[minute + minutes_now]`, so a replay helper that indexes the raw dict with `range(start - minutes_now, end - minutes_now)` samples a completely different time of day, and `.get(minute, 0.0)` makes it invisible — a "there must be no solar here" guard then passes whatever the scenario. Seen live in a PR's dark-slot guard (01:30–01:59 read where 22:30–22:59 was meant).

- `charge_rate_now`/`discharge_rate_now` exist only after the first `update_status()` and are floored to `battery_rate_min` immediately after the capture, so "is the rate actually 0" must capture the raw read first — a nonzero `inverter_battery_rate_min` defeats the balancer's `== 0` held-gate (the oscillation family, GH#5927).

Prove the shift by restoring the old behaviour first. ### Tests and the C++ kernel

- **Do not rebuild the kernel binaries while triaging**: the `.so` files are committed and CI-built. A `scan_soc_range` count of 0 over a full plan means the kernel served it (GH#5408). After a `.cpp` edit delete the local `prediction_kernel_lib.so`; a loadable build is not rebuilt. The verify script is `apps/predbat/verify_kernel_binary.py`, **not** in `tools/`, and the handshake that makes a stale `.so` fail loudly is the loader's `pk_parity_revision()` against `KERNEL_PARITY_REVISION` in `prediction_kernel.py` (a mismatch falls back to the Python engine, which is a normal log line, not a bug).
- **Python `struct`'s native `@` format is not a C-layout mirror**, so a C-ABI record hand-marshalled with it (`pack` + `from_buffer_copy`) can be right on one platform and silently wrong on another: `@` pads interior fields but not the tail to the struct's max alignment (`calcsize("@ic")` is 5 where C lays out 8). `prediction_kernel.py` derives each format from `_fields_` and at import compares the struct size **and every field offset** against ctypes' real `sizeof`/`.offset`, falling back to field-by-field writes — the offset check catches same-size layouts with a field moved. Copy that pattern instead of writing a format out. (PR #6111)
- **A standalone `import config` probe dies with `ImportError: cannot import name 'APPS_SCHEMA' from 'config'`** — `config.py` imports `THIS_VERSION` from `predbat` while `predbat` imports `APPS_SCHEMA` from `config`, so `config` imported first builds against a half-built module. The suite imports `predbat` first and never sees it; in an ad-hoc probe `import predbat` first (the mutated `APPS_SCHEMA` is then the same dict object the test module imported). (PR #6114)
- **New kernel context arrays need `ContextStore` copies.** `pk_context_create` copies per-step arrays because the ctypes buffers are freed; a missing `ContextStore` vector/`assign`/`.data()` dangles silently, giving wrong values, not a crash.
- **Kernel and Python can choose equal-scoring but different plans.** The kernel ignores the levels pass's `step=30` fast mode; `enable_fast_mode_levels: False` does not disable it, as `optimise_levels_pass` sets `fast_mode` per region. The kernel also returns its scalar results already rounded to 4dp (PR #6112), so differences above 4dp between the engines are expected, not a parity bug.
- **Export instructions are `(mode, target, power)` tuples since the split, with a permanent legacy decode of bare numbers** (`export_target_of()` of a bare value is `int(limit)`, None for freeze/idle; sentinels: exactly 99.0 freeze, ≥100 idle). Unit tests usually feed bare floats, so a regression confined to the tuple path passes the suite — pin both forms. (GH#5997)
- **`--test <name>` resolves through `TEST_REGISTRY`, not file names** (`dynamic_load_car` is in `test_dynamic_load.py`); a wrong name gives a green run with zero new assertions (GH#5407). The fourth tuple field is the slow flag. **The suite aborts at the first failure** — a raising test aborts the run (the registry loop has no try/except) and some module runners return at their first failing `test_*`, so one FAIL proves nothing about later tests; rename them to `xtest_` one at a time (PR #5641).
- **CI got slow: read the step timings before the tests.** `gh run view <id> --json jobs` gives per-step times and the log's `PASSED in` lines rank the tests. In Nov 2026, 4m20s of one 14.5 min job was pip compiling numpy from source (`python-version: 3.x` had moved to a Python the pinned numpy had no wheel for), and check-yaml spent 48 s on the `coverage/cases` dumps. A YAML parse or dump runs at ~1 s per MB even with libyaml, so look for one repeated in a loop (`read_debug_yaml`, `create_debug_yaml`, `load_scenarios`). `inspect.stack()` reads source for every frame; walk `sys._getframe()` instead.
- **A test that reaches a vendor API passes anyway, and can take minutes.** Fake credentials get a fast 401 the component handles; when the call fails without a reply the component retries with real sleeps (`deye_api` went 1.8 s → 28 s, `ge_cloud` ran for minutes). `tests/network_guard.py` fails any test making a non-loopback DNS lookup or connect, naming the code line and the test line; its event-loop `getaddrinfo` hook gets past aiohttp's executor thread, which loses the stack.
- **Skips can count as passes.** `run_nordpool_test()` returns False (pass) on a download failure (the fixture is committed, PR #5799), and CI plus `coverage/setup.csh` install only `requirements.txt`, so `if have_<pkg>:` gates run only their skip path (GH#5715).
- **Tests that fail only in one dev container** — check the interpreter and `jq` first. Sigenergy's leak assertions filter `asyncio.all_tasks()`, and before Python 3.12 `asyncio.wait_for` leaves a wrapper task pending for the whole scenario, so four cancellation tests fail on 3.11. The owner-gate tests pipe the workflow's `--jq` filters through the real `jq` binary, and 1.6 rejects a variable named `$label` (`syntax error, unexpected label`) where 1.7+ accepts it, failing all 14. main's devcontainer pins Python 3.12 and jq 1.7.1 since PR #6090. (GH#6089)
- **A test that starts a real web/aiohttp component must stop it on the failure path too.** `Components.start("web")` and only stopping it after the assertion leaves the server thread running, `unit_test.py` never exits, and the runner sits to its timeout (exit 143) — which reads as a hang, not a failure. Stop the component in a `finally`. (PR #6104, seen in its red run)
- **A passing test proves nothing when the fixture encodes the bug.** Seen: flat-rate fixtures, identical inverters, zero-iteration loops, `_mk_get_ctx`'s `json_body or {}`; a log-grep "not called" check is vacuous if the method is a silent stub, so use a calls counter (GH#5718). `TestHAInterface.get_state` returns `""`, not `default`, for a missing attribute (PR #5131); window asserts must check `start < end` (PR #4943); for address-reuse guards assert the object is pinned (`gc.get_referrers()`), as `tests/test_secrets.py` does (GH#5171).
- **Stub, double and constructor shapes.** `Execute.__new__` stubs lack base methods (GH#4965). `ComponentBase.__init__` aliases the live shared `base.args`; prefer `Cls.__new__` plus explicit `base`/`log`/`prefix`/`args` (PR #5211). A MagicMock `self.base` passes `getattr(base, hook, None) is not None`, so a new host hook needs `base.<hook> = None` in those doubles (PR #5819). A mock that skips `ComponentBase.__init__` must set `self.base` (None is enough) once the component reports discovery, or `report_discovery()`'s `getattr(self.base, "components", None)` raises AttributeError, swallowed into an every-cycle "failed to report discovery" warn that poisons a last-log-line assertion (PR #5936).
- **`self.base.set_read_only` is `True` until the first `update_pred()`**; read `get_arg("set_read_only")`. The charger mixin and wallbox were fixed in PRs #5793/#5798; `gecloud.py` and `gateway.py` still read the attribute first.
- **`run_execute_test()` scenarios inherit fleet state from the previous scenario.** `total_inverters = len(my_predbat.inverters)` is whatever the last scenario left (mixed-fleet tests silently assume 2), the `reserve=` kwarg is fleet-total kWh divided by that count, and `assert_soc_target` can pass through the reserve-driven reset-to-100 fallthrough rather than the target split — work out the member count, the per-inverter reserve and which branch writes the target; per-inverter split targets are only asserted in the `check=True` rig. (PR #5906)
- **Car-slot dicts handed to Predbat are mutated in place; the deep copy in `calculate_yesterday()` is a backup, not a shield.** It deep-copies at entry and replaces the list at the end, so during the reconstruction external owners still saw their dicts written; the in-place writers are `yesterday_reconstruct_car_slots()` (with `car_energy_reported_load` on) and `dynamic_load_car_check()`. The random-scenario harness shared slot dicts between runs until PR #5946 added the per-slot copy.
- **`test_prune_dead_slots` stubs `run_prediction_metric`**, so it never checks that the simulator itself scores a dead slot the same as off — a real-simulator probe needs `calculate_plan(recompute=True)` on a fresh template-loaded instance first (`self.prediction` does not exist, and `manual_all_times` is a read-only property).
- **A component billing test run against the real `my_predbat` must pin `plan_random_delay = 0`.** `coverage/apps.yaml` sets 15, and any non-zero value makes `BillingReader` arm a random 0–30 minute hold-back and read in the background, so `queries` is empty synchronously and `sensor.predbat_billing` appears late with no failure until the assertion. Copy the pin (with its `finally` restore) from `test_octopus_run_publishes_billing`. (GH#6024)
- **`reset_inverter()` (`tests/test_infra.py`) moves the test clock to noon** — set `midnight_utc`/`minutes_now` *after* calling it, or a time-of-day test silently runs at 11:00–13:00.
- If PR #5953 lands as drafted, car-slot consumption splits in two — `in_car_slot()` (point membership, first match wins) for ungrouped cars and `car_slot_average()` (overlap average, summing all overlapping slots) for cars in `shared_power_groups` — so a car-slot semantics change must land in both Python sites plus the C++ kernel, and `test_kernel_parity` would not exercise the shared-power path.

### Clocks and time

- **`midnight_utc` and `now_utc` are local time**, in `ComponentBase` and `now_utc_exact` too. Use `.astimezone(timezone.utc)` before a `Z` suffix or an API window, and test with a BST date (GH#5572, GH#5693). `time_abs_str()` prints local time (GH#5036).
- **Build test dates from Predbat's clock**: anchor to `my_predbat.midnight_utc` and pin both clocks (PR #4877, PR #4998). Storage-cache expiry is the exception (real clock). `ComponentBase.midnight_utc` is a property re-reading `base.now_utc`, so a component fixture built with `__new__` plus a MagicMock base can replace the clock after construction (PR #5843 review).
- **The quick suite fails 00:00–01:00 local in summer on main** (2026-11-05): the teslemetry weekday test raises and aborts the run, and `test_solax.py`'s month test fails with an empty detail (grep `**** ERROR:`). Check the clock first. A test that hardcodes a calendar date turns the suite red from that date whatever the code does: `test_web_pv_calibration_chart` expected `Next scan 2026-11-17 00:00` and failed from 17 Nov 2026 (seen 00:10 GMT, the page said 03:00). Fix the fixture or the assertion, not the feature.
- **`minutes_now = 0` hides time-of-day bugs.** History-index code needs a test at non-zero `minutes_now` (GH#4732). A pin-guard test is vacuous when the pin equals the residue (`FIXTURE_MINUTES_NOW`).
- **`timedelta.seconds` wraps into [0, 86399].** Use `abs((a - b).total_seconds())`; the button-press site was fixed in PR #5697 (GH#5694). Sites whose cache cleanup caps age below 24 h are fine.
- **Naive-tz sweeps after `strptime_aware()`.** It raises on missing tzinfo, so a `%z` site's naive handling is dead, and a bare-statement `.replace(tzinfo=...)` is a no-op. Watch for orphaned F401 imports (GH#5695).
- **CI's `python-version: 3.x` resolves to different CPythons per runner**; check `Successfully set up CPython` in the job log (PR #5653). The AST guard `offset_strptime_calls()` misses attribute and `BinOp` formats (2026-11-05).
- **`HAHistory` lags up to 2 minutes, and smoothing back-fills the gap**, so moving a marker to now loses the tail; count only the uncounted delta (`car_manual_soc_track()`, PR #5752).

### Reading the code

- **`self.base.args` holds Predbat's own dummy entity ids.** `create_entity()` ids pass `is_entity_id()`; use `user_configured_entity()` (PR #4745). Since PR #5126 Inverter objects persist and `refresh_config()` re-reads config every cycle (GH#5099).
- **`inverter_source_active()` is fleet-wide**, and `rest_data` has gone (since #4864). `create_missing_arg()` pads with `None`.
- **`re:` arg values are full-matched `^...$`** (`resolve_arg_re()`, GH#5677); when the pattern has capture groups the value is replaced by group 1 — why templates wrap patterns as `re:( ... )`. On a list or dict arg the outer call's `matched` comes back `True` unconditionally (failed items become `None` + a warn), so indexing `[0]` on a list arg is a vacuous match check in tests. (GH#5931, verified 2026-11-10)
- **A template `re:` slug group must absorb the whole device name** — `[a-z0-9]` excludes `_`, so `(_[a-z0-9]{2}[a-z0-9]{1,6})?` in `templates/solis_local.yaml` cannot match `sensor.solis_s6_eh1p_...`: the optional group is skipped and the required text `_household_load_today_energy` does not follow `solis`. Symptom is the `unable to match ... now will disable` warn plus `load_today` disabled and no plan. PR #6088 fixes it (#6087 closed unmerged); nothing loads every template, the guards are specific (`test_docs_time_window`, `test_templates_ship_octopus_free_session`). (#5881/#6088)
- **Sign conventions.** `grid_power` is negative on import (`grid_power_invert` exists for meters that disagree); `battery_power` is positive while discharging. Find out which convention a sign report assumes (GH#4797).
- **Throwaway event loops in component events.** `select_event`/`switch_event` presses run under `asyncio.run` on a fresh loop, which breaks a persistent `aiohttp.ClientSession` or `asyncio.Lock`; hand the work over with `run_coroutine_threadsafe` (fixed for Hanchu in PR #5684).
- **Two loops over one slot.** A `TypeError` against `None` deep in the plan often means two loops over one slot drifted apart (PR #4943).

### Reviewing PRs

- **A clean auto-merge can still be a semantic conflict.** Run the full `run_pre_commit` (PR #4645).
- **Check base staleness first.** The fix may already be on main, and resolving a test conflict can delete main's test (PR #4756).
- **Read a PR's scaffolding against `origin/main`, not the PR's own base.** A PR cut from an old base can show `components.py` entries as class objects with top-level imports, apparently contradicting CLAUDE.md's lazy-import rule; main holds `"module.ClassName"` strings resolved by `load_component_class()` (a class object there raises AttributeError), pinned for every entry by the quick-suite `every_component_class_imports` test. Check `git merge-base origin/main HEAD` and the commit count before reading anything a PR does to `COMPONENT_LIST` or `config.py`. (PR #6034)
- **A new test file that imports `pytest` is doubly dead.** The only runner is the `TEST_REGISTRY` loop in the unit-test module, which imports every registered test module at startup and calls `func(my_predbat)`. `pytest` is not in `requirements.txt` and not in the coverage venv, so registering such a file breaks the **entire** suite at import time, and its bare `test_*` functions would never be called anyway. Expect the peer convention: a `run_<feature>_tests(my_predbat=None)` wrapper, plain asserts plus `unittest.mock`, and a registry entry. (PR #6034)
- **Stacked-PR squashes.** A `(#M)` squash suffix on PR N's head commit means its diff spans both PRs (PR #4186). A stacked PR — one whose base is another PR's branch — also shows state MERGED the moment the squash lands on that base branch, with a `mergeCommit` oid nowhere in main's history and nothing on the default branch; check `git merge-base --is-ancestor <mergeCommit> origin/main` before trusting "merged", and review the consuming PR's diff as the whole stack. (PRs #5591/#5363, 2026-11-10)
- **A review's `commit_id` (REST `commit.oid`) is the head at submission and never updates.** To judge whether an approval covers the current head, compare it to the PR's head: REST `/pulls/<n>/reviews` (fields `user.login`/`state`/`commit_id`) suffices without GraphQL, for which some triage permission modes deny `gh api graphql`. A later CHANGES_REQUESTED/DISMISSED by the same author supersedes an earlier APPROVED, so filter `state == "APPROVED"` with `commit.oid == headRefOid`; bot reviews post as state COMMENTED and satisfy no approval gate. (PR #5942, 2026-11-02)
- **Fork PRs can carry pasted truncation banners.** Grep the head tree for `truncated output` and `Total output lines`, confirming with `grep`, not Read, which adds its own banners (PR #5766).
- **CI runs the quick suite in the `pre-commit` job**, so "tests didn't run locally" does not mean untested; check the touched modules' slow flags (PR #5346). That job builds the kernel and runs the suite with `PREDBAT_KERNEL_REQUIRED=1`, so CI's `--quick` does exercise the kernel path (the seven slow-tagged tests are its only blind spot: `balance_sim_matrix`, `replay_roundtrip_day`, `plan_preclip`, `annual_integration`, `load_ml`, `ml_training_perf`, `gecloud_api_budget`) — a *local* green `--quick` is kernel coverage only if the kernel actually built and loaded, so check for the kernel load line, not just a green result. (PR #6109)
- **Docstring coverage (interrogate) and flake8 are enforced nowhere** (re-checked 2026-11-10) — CLAUDE.md's Code Quality section does say "100% coverage required (interrogate)", which is what misleads reviewers: missing docstrings, including in test files, are not an enforceable finding. (PR #5810)
- **GitNexus is indexed from main.** On a PR branch read `detect_changes()` as "which files", not "which symbols" (PR #5143).
- **Re-running `/pr-review` on an unchanged head duplicates the review.** Post a follow-up with `comments: []` instead (PR #5645).

### GitHub and tooling

- **`gh issue list --search` without `--repo` searches all of GitHub.** Always pass `--repo springfall2008/batpred`, and distrust an empty result: fetch the exact title, typos included (GH#4705, GH#4973), and search bare `#N in:body` and the reporter's own issues (GH#5420). Even with `--repo`, an OR'd multi-word query has returned other projects' issues (#6117; mechanism unexplained, suspected to be the OR parsing), so search one plain keyword at a time and sanity-check every title against batpred's subject before treating it as a hit.
- **`gh api` permission rules match literal prefixes.** Put flags after the endpoint. Events come back oldest-first, ascending within a page, so `gh api --paginate repos/<owner>/<repo>/issues/<n>/events` piped to a filter and `tail -n 1` is the most recent — the owner-gate workflow reads the last actor of a label exactly that way. The `comments: 0` in a review-creation response is unreliable (PR #5759, PR #5143). `jq` on `--json comments` needs `--jq '.comments | length'`; plain `length` counts the wrapper's keys (GH#5349).
- **A shell `grep -E '\s'` sweep returns zero matches on macOS** — BSD `grep`'s ERE has no `\s`/`\S` (GNU extensions) and fails to match rather than erroring, so a bogus pattern looks exactly like a clean tree (main had 20 hits; `[[:space:]]` found them). Spell whitespace as `[[:space:]]` under `grep -E`, or run the Python `re` pattern through `python3 -c`, and treat a zero-match `\s` scan as unverified rather than as proof. (PR #6107, 2026-11-10)
- **Triage permission-mode routes.** Read a branch doc with `git fetch` plus `git show <branch>:<path>` (GH#5291); for another repo use WebFetch after checking its default branch (GH#5417). Plain `git` from the repo directory only: `-C` and `cd` outside the working dirs are refused as well. **When `git fetch` itself is denied, verify the tip over HTTP** — `WebFetch https://api.github.com/repos/<owner>/<repo>/commits/main` returns the real remote sha without `gh`, so compare it with local `git log`/`git describe --tags` and report the sync as done-by-verification; a locally cached `origin/main` still serves range checks.
- **Kraken (EDF/E.ON) issues have no component label.** Do not guess `Octopus`.
- **Merge box shows `owner-gate` "Expected — Waiting for status to be reported" though the API says it passed.** The gate posts an `owner-approval` **commit status** (PR #6008), which belongs to no check suite, and its job is named `owner gate evaluator` so its own tick cannot satisfy the requirement; a `GITHUB_TOKEN` check run lands in the *oldest* suite, which the merge box never reads (`mergeStateStatus` still `BLOCKED`). Read the verdict from `/commits/<sha>/statuses`; an admin merge or a new head commit clears a stuck PR. The required `pre-commit` context is the `code-quality` workflow's job (which runs the owner-gate tests as a hook), not a workflow of that name nor the TEST_REGISTRY suite. Every `labeled` event fires the workflow including the bot's own, so a bot-labelled PR carries extra runs and a pending `owner-approval` until the owner approves — expected. (PR #5940, PR #6008)
- **`/commits/<sha>/check-runs` defaults to `filter=latest`, hiding duplicate runs of one check name** — pass `filter=all` (optionally `&check_name=`) before concluding a commit carries one run. Check runs live on the sha, not the PR: a force-pushed-away head returns none from `pulls/<n>/commits`, so locate it via a review's `commit_id` or `actions/runs?head_sha=<sha>`. **Repo rulesets are readable without admin**: `gh api repos/springfall2008/batpred/rulesets` (then `/rulesets/<id>`) answers the actual required checks and branch policy with the triage-bot token — use it before trusting a PR or issue description of the gating requirements. (PR #6004, PR #5978)

## What belongs here, and what does not

The journal is for what a future triage run would otherwise have to rediscover. Test every entry with one question: would it save time on a **different** issue?

- **Keep: techniques and traps.** How to replay a dump (`--redo`), test-order pollution, stale kernel binaries, the macOS local-network block. These apply to every investigation.
- **Keep, tightly: durable facts about a device or API.** One line, no story. "GivEnergy stores rates as a whole percent of capacity, rounded down" is about the hardware, not about the issue that found it.
- **Keep, short and dated: findings that explain a class of report.** "Car not charging because X" is useful when the same symptom comes back. Give the issue or PR number and the date, say how it was verified, and word it as "look here first", so the reader confirms it against the code.
- **Drop: per-issue narrative.** What was tried, what the fix was, why the alternatives were rejected. That belongs in the PR and the issue, where it stays tied to the code it describes. In the journal it goes stale as the code moves.
- **Drop: file paths and line numbers.** They drift with every merge, and a citation pointing at unrelated code misleads more than no citation. The area heading already names the module, so point at a function, a config item or a log line instead: those survive a refactor, and a reader can grep for them. Naming a file is fine when the file is the subject rather than a location: `apps.yaml`, a template, a test to run, or "`execute.py` has no AlphaESS case".

Write each entry in the same shape: the **symptom** (the log line verbatim, or what the reporter sees), the **fact or mechanism** behind it, and **where to start looking** (a function or config item). Then add the issue or PR number, and the date if it is a bug.

Entries go stale, so retire them:

- When the code an entry describes has changed, correct or delete the entry. Do not leave it marked as stale.
- Once a fix for a bug entry has shipped, cut it down to what a reader holding an older log needs ("fixed in PR #N") and drop the story. After about six weeks, delete it unless the mechanism is still a trap.
- Prefer sharpening an existing entry over adding a second one.

Keep it small. Every triage, review and journal-update run reads this file end to end, and at 730KB it cost them most of their turns. One fact per bullet, a few hundred characters at most. If an area's notes grow past about 3KB, consolidate them rather than adding more.

## Adding to this file

When an investigation turns up something that passes the test above, add a bullet under the right heading: the area under "Per-integration notes", or the topic under "Symptom → first place to look". Keep it short, name a function or config item rather than a file or line, and cite the issue number so the next reader can check the original.

If you are running under the triage bot you cannot edit this file directly — the clone is `reset --hard` before every flow, so the edit would not survive. Write the finding as a single markdown file in the queue directory named in your system prompt instead; the `/journal-update` flow folds the queue in once a day, re-checking each candidate against current `main` first, and opens a PR for a maintainer to merge.

Whichever route you take, the bar is the same and it is not "interesting": record what you **verified**, say how you verified it, and keep anything you merely suspect explicitly marked as suspected. A wrong entry here is worse than a missing one — every later run trusts this file, so a confident mistake ends up in a comment posted to a real reporter. Correcting or deleting a stale entry counts as much as adding one.
