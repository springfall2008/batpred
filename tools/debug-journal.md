# Debug journal

Notes distilled from maintainer debugging sessions and triage-bot runs on this repo (June–November 2026), for whoever is triaging an issue next.

Every entry is an observation from a past investigation, not a statement about current main. The code moves. Use these as "look here first", confirm against the working tree before you put anything in a comment, and say what you actually confirmed rather than what this file says.

Compacted 2026-11-05 from 730KB of per-issue detail, and consolidated again on 2026-11-23. The story behind an entry is in the issue or PR it cites, and in the last uncompacted version: `git show ea6ba38d:tools/debug-journal.md`.

## Replay the reporter's debug file

`predbat_debug.yaml` is a full state dump the harness replays against the current tree:

```bash
cd coverage
csh ./run_all --debug_file <scratch>/predbat_debug.yaml > <scratch>/replay.log 2>&1
csh ./run_all --debug_file <scratch>/predbat_debug.yaml --redo > <scratch>/replay-redo.log 2>&1
```

- `run_all` is a **csh script with no shebang**, so a bare `./run_all` under bash or `sh` dies with `OSError: [Errno 8] Exec format error`; invoke it as `csh ./run_all`. It needs `coverage/` as the working directory.
- Grep the log first for the non-default config block (`- <item> = <value> (default <value>)`). Output: `coverage/plan_orig.html`, `plan_final.json`, `<yaml>.actual.json`; all overwritten per run. The two "Wrote plan ... metric" figures can differ hugely (seen -79.86 vs -20.07) — read the per-slot rows.
- Without `--redo` you replay the dump's own rates, load model and Octopus slots. A dump with `debug_enable` off — the normal setting — carries empty `pv_forecast_minute_step`/`load_minutes_step`, so `KeyError: 0` there is a needs-`--redo` tell, not an old-dump one (GH#5860, GH#4766). A v8.x dump stores the same four dicts empty but keeps the series they derive from.
- A replay cannot reproduce live ML-forecast choices, so a marginal ~10p mismatch is inconclusive (GH#5213); grep the reporter's log for `Best export window` / `Best charge window`.
- Bot tooling: `tools/triage_test.sh <test>`, `tools/triage_replay.py`, and a temporary `TEST_REGISTRY` entry for `run_single_debug(..., redo=True)`, which also re-derives `set_rate_thresholds()`/`rate_scan_window()` (GH#5221).
- `Replay input:` lines (PR #5427) rebuild a cycle's inputs from the log alone, formats pinned in `tests/test_log_replay_inputs.py`; the forward replay parser (`tests/replay_forward.py`, PR #5363) makes them a contract, unknown lines skipped silently. A repeated identical line means the value changed, or (PR #5591) the first run of a new day. PR #6243 (open, not on main as of 2026-11-26) would add `Replay input: battery temperature forecast changed`, which bypasses `log_replay_changed()` and can repeat many times within a day, so on a build that has it the rule gains an exception; on main the rule holds.
- Reading a dump (GH#5509): rates and windows use absolute minutes of the dump day, `predict_*_best` minutes from now, `*_today` minutes-ago (index 0 = now). `export_window_best[].target` is not the `export_limits_best[]` level; decode with `export_mode_of()`/`export_target_of()`.
- **Forward replay** (`--replay_log predbat.log`, PR #5363): steps through the log's later runs, re-planning where live did (`--override name=value` for what-ifs). Needs a log running past the yaml and a yaml from before a restart or `apps.yaml` change; concatenate rotated logs oldest first. Most reporters take the yaml at the end of the log, leaving nothing to replay (GH#6150): ask for a History-view snapshot from the start instead. `triage_replay.py` checks this (exit 3). Exact mode takes the logged SoC; `--replay_simulate` steps the battery; `--replay_chart` draws it.

Loader failures before Predbat code runs:

- `could not determine a constructor for the tag '!secret'`: `DebugYamlLoader` has no `!secret` constructor (GH#5748); sed captured args to dummies in a copy.
- numpy dtype `SystemError` (GH#5205): fixed in PR #5892. `found unhashable key` from `io_slot_log_gate` (GH#5569): fixed in PR #5575.
- Without `apps/predbat` on `sys.path` a load dies at the first `!!python/object` tag. A newer dump on an older tree fails `No module named 'control_monitor'` (GH#5719); null `control_monitor:`/`control_ledger:` in a copy. Both have been out of dumps since they joined `DEBUG_EXCLUDE_LIST`.
- `DebugYamlLoader` is a safe loader: it rebuilds only `DEBUG_YAML_OBJECT_CLASSES` (`MinuteArray`, the two control objects for older dumps), numeric arrays and tuples. `... object/apply:X` means a new call-style value: add a numeric-only constructor, never a generic one. `Warn: ... load as plain dicts: X` means a new `!!python/object` class: add it, or `DEBUG_EXCLUDE_LIST` it if no replay reads it. `CSafeLoader` parses as fast as the old unsafe loader (0.91 s on 5 MB).

Normal lines, not the bug: `Prediction kernel stale binary ... - using Python engine` (plan still correct) and `Config item ... is below the minimum ... - clamping to ...`.

## Debug yaml can contain real secrets

Read dumps locally and never quote a raw block publicly unchecked.

- Pre-v8.55.0 dumps can carry `args_from_apps_yaml` with resolved secrets (GH#4765); masked at source since PR #4910, so no reason to tell a current reporter to rotate.
- `mask_secret_args()`/`is_secret_key()` match `_key`/`password`/`secret`/`token` in top-level keys. `annual.py`'s `scrub_secrets()` is recursive and masks differently (GH#4770).
- Discovery identifiers are published readable by design since PR #5924: the Redactor is an email scrubber only, so "my MPAN/serial/account id appears in the dump" is working as designed — point at `docs/discovery-catalogue.md`. Credentials are withheld by field NAME only, so a credential under a non-credential-named key reaches the dump verbatim. `catalogue_raw()` feeds only the web `?raw=1` view.
- `debug_history_enable` defaults True and snapshots ~3-hourly into `predbat_debug_history.tgz`, independent of `switch.predbat_debug_enable`. Retention is ~45 h (count `debug_history_count` 15, age `debug_history_interval` 3 h); an evidence-request deadline is capture time + ~45 h.
- The History view's snapshot download is `/debug_history_download?id=` on Predbat's own web server, so "I can't get files out of the Docker container" has a browser answer. For "what did Predbat command during the window", ask for HA recorder history of the exact window, not the newest snapshot's ledger — the ledger keeps the latest confirmed value per entity, so window-start writes hide. (GH#5852)
- Logs are redacted at write time (`LogRedaction`, `log_secrets.py`). `!secret` resolves only via the private `SecretYamlLoader`; bare `yaml.load(...)` hits are ruamel.
- Issue line numbers may resolve against a PR branch, not main. If `gh api .../pulls/<n>/comments` is denied, use `gh pr view --json`.

## Check configuration before code

Pull the non-default list first: `combine_export_slots`, `metric_min_improvement_export`/`_plan`, `best_soc_keep`, `metric_battery_value_scaling`, `metric_battery_value_export_scaling`, `metric_battery_cycle`, `metric_cloud_enable`, `load_scaling*`. "Configuration" is a legitimate outcome.

- Replay one setting change at a time and compare decisions, not the metric (an emptier final battery always looks cheaper). `best_soc_keep: 0.0` and `metric_battery_value_export_scaling: 0.8` are defaults.
- Read `optimise_all_windows()` end to end before calling a pass dead. The commented-out swap call is not the live one, which runs last (GH#4478).
- Near-parity export tariffs (GH#4840): leftover SoC is credited at `battery_value_rate()` (replacement cost), a ~1% margin, so `metric_battery_value_scaling` below ~0.987 flips exports. `metric_cloud_enable: False` predicts zero import.
- `battery_value_rate()`'s four inputs are built at different fetch stages (PR #5872): `rate_max_base` (raw tariff), `rate_export_max_forward`/`rate_export_min_base` (post-replicate, pre-session, pre-override), `rate_min_forward` (post-replicate + IOG overlay, pre-session — built in `fetch_sensor_data()`); `rate_export_min` stays session-inclusive by design. Code installing a rate table outside fetch (a test `reset_rates()`, a replay harness) must reset `rate_min_forward` itself; replaying an OLD dump restores its session-inclusive `rate_min_forward` and lacks `rate_export_min_base` — run `--redo`.
- **A term added to the replacement cost must go into `battery_value_rate()`'s cap too.** It computes `rate_min = (rate_min_raw + term) / inverter_loss / battery_loss + metric_battery_cycle`, then clamps with `max(min(rate_min, rate_max * inverter_loss * battery_loss − metric_battery_cycle), 0)` — a cap derived from `rate_max` alone. On a flat or narrow-spread tariff the pre-cap value exceeds the cap with *or* without the term, so both land on the same number and the setting is inert in `compute_metric`, the `value_per_kwh` sensor, `marginal.py` and the savings report alike. Test such a setting flat *and* spread. (PR #6209 review, read-only)
- Charge-to-export "loss" (GH#5069): naive arithmetic omits the end SoC credit and displaced peak house load.
- Non-GBP tariffs (GH#3683): `metric_min_improvement*` gates compared unconverted against the minor unit, so plans churned. Fixed by apps.yaml `currency_scale` (PR #6156): `apply_currency_scale()` multiplies the min/max of every money item by it; it only raises a cap; <1, `nan` or `inf` is ignored with a warn. Pick money items by exact unit — the `snapshots` unit on `debug_history_count` contains a `p`. `currency_scale` itself is always present: `reset()` calls `apply_currency_scale()`, which assigns it before its `scale == 1` early return, so a `getattr(self, "currency_scale", 1.0)` in a currency path is a silent off-switch — a dropped attribute makes a calibrated install round and compare at scale 1 with no error. `Prediction` copies it from its `base`, so keep the copy in step too. (PR #6221 review)
- Money-losing plans: grep `Previous plan best metric is ... and new plan best metric is ...`. Positive deltas under `metric_min_improvement_plan` mean retention (GH#5616); negative deltas every cycle mean lock-in on stale windows, which lowering the gate cannot help (`should_replace_plan()`, GH#5686).
- Levels-pass exports that paid only in the PV10/PV90 blend (GH#3376/#5633, GH#5969): fixed in PR #5977 (`export_gate_metric()`). Per-5-minute charging came in PR #5874.
- `best_soc_keep` is only a soft `metric_keep` penalty, never a window or reserve (GH#4961). `manual_soc_keep` and alert keeps force `keep_minute_scaling >= 10` weighted by import rate, so were inert in 0p windows (GH#5162); fixed in PR #6140 (`KEEP_TARGET_MIN_RATE` floors the penalty's rate in both engines). Only `set_reserve_enable` plus `reserve` is a hard floor.
- A "Predbat didn't charge before an Axle/saving-session event" report is usually config. Check `rate_low_threshold` set manually (0 = auto), `combine_charge_slots` on, `set_export_freeze_only` on (#3994 open). Then the arithmetic (GH#5901): event revenue is bounded by discharge power × event length, so a pre-event top-up only adds post-event buffer worth about `battery_value_rate()` minus the refill price; an *additive* event boost (Axle, PR #4520) can never move a min-rate scan. The only hook is Axle's `binary_sensor.<prefix>_axle_event`.
- `HoldChrg` (within 1% of the limit, `set_discharge_during_charge` default True) is not `FrzChrg` (`is_freeze_charge()`).
- No charge-start hysteresis (GH#2513): the hold band needs `inv_target_soc_percent < 100.0`, so a 100% target is re-commanded every cycle.

`get_arg()`/validation traps:

- `key:` (null) defeats the default for direct callers (component args fixed since PR #5188). A quoted `'1'`/`'y'` coerces to False.
- Float-default truncation (`solcast_poll_hours: 4.8` read as 4, GH#4925) fixed in PR #4938.
- An enable-gated CONFIG_ITEM still returns its declared default while gated off. Unknown apps.yaml keys are ignored silently (GH#4999, open); `allowed:` is enforced only for string and integer types. Sensor-typed items reject numeric scalars (GH#2172).
- A literal `0` in a `sensor_list` item passes silently despite `"zero": False` in its `APPS_SCHEMA` entry: `validate_config()` enforces `zero` only in the `integer_list` branch, and `get_arg()` defaults only on `None`, so the 0 reaches the code as a real maximum (`inverter_limit_export: [0]`, `inverter_limit_charge: [0]`, `battery_rate_max: [0]`). Treat a 0 maximum as unset at the consumer. (PR #6247, code-read)
- **`TypeError: ... unhashable type: 'list'` from a history read** — a per-inverter list read without `index=` reaches `get_history_wrapper()` as an entity id, and HA history uses it as a dict key; `battery_temperature_history` is not a CONFIG_ITEM, so nothing coerces it. Fixed for it in the #6222 stack (per-inverter read, and the list is averaged rather than summed across sensors). Search such a traceback for readers of list-valued keys, not for the key. A list-valued *non-additive* key passed through `minute_data_import_export()` is summed by `accumulate=` (meant for additive totals), so a two-sensor temperature list reads ~2x into the plan. (GH#6222)
- `get_arg()` consults `get_ha_config()` **before** `self.args`, and a value from that path comes back raw: `resolve_arg()`'s entity-id resolution and `required_unit` conversion run only on the args path.
- `config_index` items are mutated on the shared `CONFIG_ITEMS` dicts: `load_user_config()` seeds `default` from `args` and `expose_config()` writes `item["value"]`, which survives across calls. A test re-running `load_user_config()` must reset `value` and restore `default` (`test_fetch_config_options` Test 16). `reset()` deep-copies `CONFIG_ITEMS`, so a helper that mutates `base.CONFIG_ITEMS` before calling it has every edit discarded while its `base.args` edits survive — mutate the instance list after `reset()`. (PR #6098, PR #6221 review)
- A disabled item's retained `value` is inert: `get_ha_config()` re-checks `user_config_item_enabled()` and returns `None` (the caller's default) whatever `value` holds, so a hidden money setting cannot still drive the planner.

## Test-order pollution (GH#5079)

- Since PR #5102 each registry test gets its own `create_predbat()`. Module- and class-level state can still leak (`PLOT_ENABLED`, `LogRedaction`'s lock).
- From `coverage/`: `./run_shuffle --hunt --quick` bisects to a (culprit, victim) repro. Also `--bisect <seed>`, `--campaign N`, `./run_all --shuffle`.
- Victims cluster in `model`/`kernel_parity`. `run_pre_commit` runs the quick suite only after the hooks pass, so a log ending at the hooks is not a green suite.

## The shared clock is rewound for ~0.8s every hour

`calculate_yesterday()` sets `midnight_utc` back a day and `minutes_now = 0` on the shared `PredBat`, unlocked, while other threads read it live.

- Off-thread readers are hit: manual overrides (GH#4900, fixed with `manual_time_origin()`) and component PV buckets (GH#4804). `ComponentBase` derives its clock from `now_utc`; `PredBat` mixins such as `Octopus` still read the fake.
- Code inside the fake must pass the real `minutes_now` to history indexing (GH#5004).
- Suspected, unverified: `decode_octopus_slot()`, `dispatch_billed_off_peak()` and zero-kWh slot synthesis misread it (GH#4946); History only.
- On a "shifted by one day" report, check this first.

### Fox (`fox.py`)

- Cloud errno 42015/44096 = setting unsupported by the device (`FOX_SETTINGS_UNSUPPORTED_ERRNO`); it is marked unavailable and never polled or written again. Since PR #5840 those lines log at Info; a Warn form in an attached log dates it earlier.
- `soc_max` 4x too big when `batteryList` holds four `bmu` entries with one serial (AIO ESS, EVO 10-5-H): fixed in PR #5629. Unverified: whether `batteryDesignCapacity` totals a multi-pack stack.
- Fox device/detail `capacity` is an integer field, so fractional-kW models read low (`H1-3.7-E-G2-WL` read 3 kW, GH#5938): until PR #6081 only ".5"-suffixed deviceTypes were corrected. Both `-inverter_capacity` and `-battery_rate_max` funnel through `capacity_watts()` — the rate is min-capped with the truncated capacity and stored back destructively — and with `fox_automatic` on, apps.yaml's `inverter_limit`/`battery_rate_max` are re-bound to those sensors. A dump's `sensor.predbat_fox_<sn>_info` attributes prove the truncation.
- `fox_automatic: true` re-`set_arg`s `soc_max` every cycle and it is not in `CONFIG_API_OVERRIDE`; escape hatch `fox_automatic: false`.
- With the Mode Scheduler deleted, `compute_schedule()` shows the charge window from the legacy `forceChargeTime` read, which Predbat cannot clear (`set_battery_charging_time()` has no production callers; GH#4939).
- A Fox Cloud `didn't complete got X` is a genuine failure, but the cloud verify read is slow: old value at 3s, new one after ~18s.
- Reserve never reads back from the device (GH#5821, open), so "Current reserve is X%, already at target" is Predbat echoing its own write. Fox accepts `minSocOnGrid: 100` yet still discharges: declared ranges are acceptance, not enforcement.
- Device MaxSoc is published but never bound to the planner (GH#5395, open); `automatic_config()` binds only `soc_max`/`reserve`/`battery_min_soc`/`export_limit`.
- FoxESS HA/modbus path (`FoxESS`, not `FoxCloud`): the stock template binds `reserve:` to `number.foxess_min_soc_on_grid`; at 100%, `min_soc_on_grid` stops grid-connected discharge. `FoxESS` is `has_idle_time: False`, so `idle time is ...` programs nothing (GH#4961).
- Hold drain-block (GH#5704): `execute.py`'s hold-above-target branch called `adjust_charge_immediate(..., freeze=True)` on non-planner holds, so `charge_freeze_service` selected `"Back-up"`, which supplies no house load and pinned the battery. Fixed above the reserve in PR #5998.
- Live telemetry is refreshed by an **age gate, not a timer**: `_needs_refresh("device_values", ...)` against `self.realtime_refresh_minutes`, on the component's fixed 60 s loop. `FOX_REFRESH_REALTIME` (5) is the default and `fox_poll_seconds` (60–1800, `fox_poll_minutes()`) sets it since PR #6139. A failed poll does not stamp `data_age`, so it retries next tick. On "Fox data is up to 10 minutes stale", add the two ages: up to one interval old when read, then up to another plan interval old when the cycle consumes it. (GH#6138)
- Test trap: `MockFoxAPIWithRequests` and its subclasses override `__init__` and never call `initialize()`, so any attribute `initialize()` sets is missing in every run()-based test, reported only as `ERROR: Fox API test failed with exception:` with an empty message. Seed new attributes in `MockFoxAPIWithRequests.__init__`. Stashing a source file the test imports a new symbol from fails on `ImportError`, which proves nothing.
- Tests: `./run_all --test fox_api --test fox_oauth`

### Solis (`solis.py`)

- CID 636 (`SOLIS_CID_STORAGE_MODE`, 43110) is a bit mask. On "4B and above" firmware (`is_tou_v2_mode()`: CID 6798 reads 43605) per-slot registers (43707) alone drive timed charging and TOU bit 1 is refused, so CID 636 verify warnings are that refused bit, not a failed write (GH#4707). Do not infer V1/V2 from one read-back (GH#4774). V2 writes the mode with slot 1, V1 at the window boundary (`claim_window_mode_assertion()`). A CID 636 report with no `setting storage mode to` lines came from the HA select handler.
- **TOU V2 keeps only one of a slot's charge and discharge enables on**: writing one turns the other off. `automatic_config()` binds both Predbat's charge and export controls to slot 1 and never uses slots 2–6, and `execute.py` arms the next window up to `set_window_minutes` ahead, so a charge followed by an export flips them every five minutes — plan and published entities correct throughout. `read_and_write_cid()` verifies only the CID it wrote, so a dropped partner enable is invisible. Fixed in PR #6213 (`slot_direction_to_defer()` holds one direction back; only Pass 2 of `write_time_windows_if_changed()` writes the enables). Re-decoding the registers in the in-window re-read would adopt the inverter's broken state; the conflict must be resolved on the write path. Workaround on older builds: `inverter_set_charge_before: false`. Whether the exclusion is per slot index or one shared register is unresolved. (#6210)
- PV-only detection: `_reports_no_battery()` and `SOLIS_GRID_TIED_MACHINE_PATTERN` (`^S\d+-GR\dP`); Cloud alternates `batteryType` `'0'`/`'0.0'`, so match by value (`_reads_zero()`).
- Discovery beats apps.yaml (`overwrite=True`, grep `auto-discovery wins`) for `charge_limit`, `export_limit`, `battery_rate_max`, `battery_scaling`; only opt-out `solis_automatic: false`.
- Slot current cap (`slot_current_limits()`): CID 7224/7226 as read, else `SOLIS_SLOT_CURRENT_DEFAULT_AMPS` (60), lowered only by `--probe-ceiling` (GH#5068); the planner does not see the clamp, so set `inverter_limit_discharge`. `write_time_windows_if_changed()` defaults a never-read slot current to the cap, so no write is attempted — seed `cached_values` in fixtures. The slot-current entity republishes the clamped cache at live voltage (`didn't complete got 3094.0` every cycle) and CID 5965's slot-SOC readback tracks live SOC (GH#4184); grep `CID 5967 ... is set to` for what reached the inverter.
- Parallel pair (GH#5556): the master's V2 slot current governs the group while 7224/7226 are per-inverter — fixed in PR #5909 (the master's slot current is written for the whole group, `solis_parallel_slaves`).
- API: `B0115` (datalogger offline) and `R0000` (200/day allowance gone) are never retried; `automatic_config()` retries every cycle; `_with_retry()` catches only `SolisAPIError`. Unclassified outage codes (`B0072`, `B0673`) fall through and get no datalogger cooldown; B0673 carries B0600's message text, so classify by code.
- Still live (GH#5093, open): `SolisAPI.run()` folds all inverters into one `poll_success`, so one unreachable unit holds startup in backoff (to 128 min); list working SNs in `solis_inverter_sn`. Still live (GH#5190, open): `int()`/`float()` accept `_`, so `"1234567890_00"` passes `parse_cid_int()` and `get_arg()` coercion.
- Holds (PR #5265): `reserve` is CID 157, a floor only while CID 636 bit 4 (`SOLIS_BIT_BACKUP_MODE`) is set, so the bit is always set. Non-slot events wait for the next `run()`, beyond the 2 s verify. Older-log signatures: `export limit 0.48kW` (CID 499 100x small); `poll failed for <SN>: '<SN>'` (`KeyError` repr); `battery_scaling read as 0.0` every cycle, plan unaffected.
- `H M` types (`GS_fb00`, most cloud subtypes) rewrite time entities every cycle by design (#1529): first suspect for "hammers my Solis with writes". Test trap: `number_event_handler()` takes the SN from `parts[0]`, so use underscore-free mock SNs.
- `charge_discharge_time_windows[sn]` is startup-decoded once and plan-driven afterwards; slot entities go stale if the startup decode fails. When adding a `seconds % 300`/`% 3600`-gated block inside `run()`, check the pre-existing `run(first=False)` tests at 300/600/3600.
- Demo / read-only handover: `Warn: Solis handover unconfirmed` latches while `set_read_only` is on and clears only through `run_cycle()`'s control section. Per-step budget is 60 s without a completed step, 300 s per inverter, each written CID able to pay the 5 s verify settle; `Schedule cleanup rejected for CID ...` is a refused write; `was not confirmed` and `cancelled before confirmation` mean timed out. A Demo entry costs ~8+4N API requests (N slots) of ~200/day.
- First question on a hold-enforcement report: which route is the install on — the FB00 entity path, Predbat's Solis Cloud component, or a third-party select (Pho3niX90 `work_mode`: meaning-equivalent options, so supporting it needs a code-side name map, not config). A user-side HA automation keyed to `predbat.status` transitions can defeat any hold; landed `backup_soc` writes with the physical mode still Self-Use mean landed writes ≠ enforced hold. (GH#5852)
- `has_reserve_soc: false` types (all Ginlong custom types; `templates/solis_local.yaml` ships `solis_rc` since PR #5881): a user-wired `reserve:` is display-only — read once into `reserve_percent_current`, then replaced with a Predbat dummy, so `adjust_reserve()` lands on the dummy. Reserve functions are disabled fleet-wide and the plan's floor is `reserve_min = max(set_reserve_min, battery_min_soc)`.
- solis_local (Pho3niX90 solis_modbus) **battery polarity**: the plain `Battery Power` (33149/33150) is an unsigned magnitude — the sign lives in direction register 33135 — while `Battery Power Net` is signed (discharge positive). Map `battery_power` to `battery_power_net` and do **not** set `battery_power_invert`; `Grid Power Net` uses an import/export flag pair. Main's template still maps plain `_battery_power` (PR #6088 open). (#6088, read from the integration source)
- Third-party Pho3niX90 `solis_modbus` shares register 43110 between `select.*_storage_mode` and `switch.*_allow_grid_to_charge_the_battery`, and the select write clears conflicting mode bits — write the mode select **before** turning the switch on. Storage-mode values: Self-Use 1, Self-Use+Reserve 17, Feed-in Priority 64, Feed-in Priority+Reserve 80, Off-Grid 4, Peak Shaving 2048; RC force is 43135 with no hold option. Option names can be driven verbatim from a service template, so a freeze report on a service-driven Solis is template wiring (the code-side name map is the FB00 `energy_control_switch` route only). (PR #6124)
- Tests: `./run_all --test solis`

### Solis Modbus (`GS`, `GS_fb00` in `inverter.py`)

- The Energy Storage Control Switch (43110, `energy_control_switch`) is written by `alt_charge_discharge_enable()`, gated on `has_solis_energy_control`; `GS` reaches it via `mimic_target_soc()` (35/33).
- `GS_fb00` (PR #5258): `write_solis_energy_control()` runs from `adjust_charge_immediate()` (49 charge/idle, 17 freeze/hold) or `adjust_export_immediate()` (64 freeze export, 49 export); a third writer would flip the switch twice a cycle.
- With `energy_control_switch` unset, `write_solis_energy_control()` writes nothing and `warn_missing` fires only on a real charge cycle, so freeze/hold cycles degrade silently while reserve writes report success; a separate work-mode select is not a valid target — Predbat writes the FB00 option names verbatim (GH#5834).
- Bit 4 (Battery Reserve) makes `backup_mode_soc` (43024) a discharge floor. A SolisCloud session leaves the switch at 1 outside a slot. FB00 plugin names differ (`SOLAX_SOLIS_MODES_FB00`: Self-Use is 33).
- `set_current_from_power()` re-asserts `timed_*_current` on every rate call; `inv_charge_discharge_with_rate` zeroes only the power register. Open: #3914, #3868 (HV battery amp conversion).
- On GS a hold is **mimic-owned**: every hold path reaches hardware only through `mimic_target_soc()`, and several writers re-assert the full current over the 0 A hold — "bursts of full-rate charging during Hold/Freeze charging". ### Solcast (`solcast.py`)

- `max_kwh` is 9999 on the Solcast direct and HA-sensor paths (set only for Forecast.Solar/Open-Meteo), so "Raw forecast exceeds the array ceiling" never fires for Solcast (GH#4730, open).
- **P90 (and P10) roughly doubles every fetch on the HA-solcast integration, resetting when the integration republishes, P50 sane throughout** — the HA state cache holds attribute containers by reference and `get_state(..., attribute=...)` hands back that same object, so `pv_calibration()`'s write-back rescaled the band it had already scaled. Fixed in PR #6055 by copying the entries in `fetch_pv_forecast()`; P50 never compounded because its calibrated value goes to a separate key. Rule: copy a `get_state()` attribute container before handing it to code that mutates it. #6049's first triage blamed the integration's dampening — wrong.
- A PV log cannot settle what was fetched: the `Replay input: PV forecast changed` rows log `pv_forecast_minute/10/90`, the **post-calibration planner series**. A ~30-minute step pattern is Predbat's own read cadence (`SolarAPI.run()` re-fetches every `plan_interval_minutes`, default 30, and when data is >60 min old). `detailedForecast` is **kW per slot**, not kWh: per-slot values sum to 2× the sensor's kWh day total on 30-minute slots (4× on 15-minute).
- `fetch_pv_forecast()` order: Forecast.Solar with `forecast_solar_open_meteo_first` → Forecast.Solar (backup on empty data only) → `open_meteo_forecast` → Solcast direct → HA sensors. So `open_meteo_forecast` means Solcast is never used, and `solcast_api_key` beats `pv_forecast_*` sensors.
- Solcast direct has no fallback (GH#5545, open): a failed call returns the stale cache, so data is never empty and the plan ages; a backup must key off `solcast_last_success_timestamp`.
- `sensor.<prefix>_pv_forecast_h0` state is calibrated; raw is the `now` attribute. Since PR #5121 calibration reads `..._pv_forecast_h0_uncalibrated`. `history_attribute(attributes=True)` drops points lacking the key unless `fallback_to_state=True`.
- `sensor.<prefix>_pv_forecast_raw` has one publisher, always with `relative_time`; a missing attribute or entity means "no forecast source configured". Since PR #6014 the warn fires only for a present-but-unparseable value. (GH#6013)
- Open-Meteo applies ensemble P10/P90 as ratios to the deterministic P50, so a re-issued forecast can push `pv_estimate90` implausibly high, bounded only by `1.2 x kWp` (PR #5347).
- **PV10/PV90 on a band-supplying provider are not independently calibrated.** For Solcast direct/HA and Open-Meteo's ensemble, `fetch_pv_forecast()` sets `calibrate_band = not create_pv10 and has_band`, and `pv_calibration(calibrate_band=True)` scales each minute's P10/P90 by `used_minute / raw_minute` — the *same factor as P50*. So a central ratio learned from a cloudy week drags the whole band down and it can never widen for a sunny day. Only the band-less path (`create_pv10`, Forecast.Solar) builds the band from `best_day_scaling`/`worst_day_scaling`; on a band-supplying provider those two are read only by the metrics gauges. Guards: P10 ≤ P50, P90 ≥ P50, P90 clamped to the array ceiling (1.2 × kWp, never below the observed peak). (GH#6204)
- Dull-day calibration inflated by per-minute `dp2()` rounding: fixed in PR #5802. On "small values misbehaving", grep `dp2(`/`dp4(` in accumulation loops first.
- **Calibration is a 28-day evidence store, not a 7-day window** (`pv_calibration.py`, PRs #6231/#6233): each day keeps the per-slot uncalibrated forecast and actual (clipping imputed) plus the day's peak; `fit_pv_calibration()` derives a day factor and a half-hour shape, each shrunk toward 1 by its own day-to-day noise (`pv_calibration_shrink`/`_slot`, 0.2) with a 3.5-day half-life. A 0-PV day is excluded; fewer than `PV_CALIBRATION_MIN_DAYS` (3) gives `Not enough valid days of evidence for calibration`; an older log's `Not enough valid (non-down) days` dates it to pre-#6231. The evidence is stored under `pv_calibration_evidence`, scanned daily (retried hourly), saved with a 60-day expiry plus a daily resave; a failed read is treated as empty only after failed loads spanning `PV_CALIBRATION_LOAD_WAIT_MINUTES`. Clearing the stored evidence does **not** reset what calibration has learned — `pv_calibration_scan()` is a re-derivation from the uncalibrated forecast and `pv_today` history, so it lands back on the same answer; a change that alters the forecast's timing needs a minimum-evidence date (or simply ages out), not a wipe. (PR #6237)
- The P10/P90 band and observed peak still come from the last 7 days (`PV_CALIBRATION_BAND_DAYS`). Tests: `pv_calibration`, `pv_calibration_clipping`, `pv_calibration_scan`, `pv_calibration_update`, `pv_calibration_day_scaling`.
- Open-Meteo has no `horizon` parameter; Predbat has only monthly `shading_factors`.
- **An Open-Meteo PV forecast ~30 minutes late — low in the morning, high in the afternoon, daily totals right** — every radiation variable including `global_tilted_irradiance` is the **mean over the preceding hour** (a 12:00 stamp is 11:00–12:00); `_instant` variants exist and are not requested, while `temperature_2m`/`wind_speed_10m` are instants. `gti_hourly_to_period_kwh()` trapezoid-integrated adjacent pairs until PR #6237 keyed one period per sample at the hour start; Forecast.Solar and Solcast follow their own conventions and must not be aligned to it. Consequence: the dict `pv_forecast()` returns inside the solar component's fetch carries ~60 **negative** minute keys when local time is UTC (in BST the 00:00 UTC sample is minute 0 locally, so none), so new code there that walks the whole dict or takes `min(keys)` picks up yesterday's hour. They never reach the plan: `pack_and_store_forecast()` publishes over `range(0, ...)` and `Fetch.fetch_pv_forecast()` rebuilds `base.pv_forecast_minute` over `range(0, max_minute + 1)`, so a scan of the published series or the dump finds none. (PR #6237, merged 2026-11-21)
- Test traps: the solar mock matches the first key that is a URL substring (`api.open-meteo.com` is inside `ensemble-api...`); patch `solcast.history_attribute_to_minute_data`; `now_utc_exact` is wall-clock while `minutes_now`/`midnight_utc` are frozen.

### Hanchu Cloud (`hanchu.py`, `hanchu_const.py`)

- Added in PR #5305, largely unverified on hardware; #5664/#5665/#5667/#5668 are from one live-hardware reporter, so search them first.
- Power limits are **two separate layers**, and a "Predbat won't write more than 5000 W though my unit is 10 kW" report usually confuses them. (a) The planner's `battery_rate_max`/`inverter_limit`: user override, then the `HANCHU_MODELS` rating for `devModel` (codes are not in size order), then the `ranges_for()` ceiling. (b) The write clamp on `CHG_PWR_LMT`/`DSCHG_PWR_LMT`: max(the cloud menu's range, the highest value seen held), capped by the model rating — the rating never raises it, and there is **no apps.yaml override for this layer** (#6044, decision pending). A 10 kW unit whose menu says 0–5000 is written at most 5000 W until seen holding more.
- `CHG_PWR_LMT` limits grid charging only, so freeze export is never requested. A hold caps `DTU_AC_CHG_SOC_LMT` at the current SoC.
- Floors and caps: `CHG_BAT_SOC_LMT` ≥ 50 (read, never written), `DTU_AC_CHG_SOC_LMT` ≥ 20, `DSCHG_BAT_SOC_LMT` ≤ 45, so a hold below 50% or a discharge target above 45% cannot be set. A hold is a 0 W charge slot.

- Predbat commits a window in stages, pressing the write button after each; presses are debounced since PR #6077 (`hanchu_write_debounce`, 10 s), and the rates arrive after the loop with no press, so any schedule change while a write is pending restarts the wait. Look for two `iotSet`s a minute or more apart at a window start. (GH#6074)
- **A hold stops at ~target+1 or at the clamped grid-charge target+1** — core's reserve hold floors at target+1; Hanchu's `_discharging_to_target()` judges against the **clamped** `DTU_AC_CHG_SOC_LMT` (floor 20) plus the 1% margin, so a 10% target holds at 21% — deliberate (#6127, pinned by `test_hanchu_control`). (GH#6133)
- HC-HY-SL-*-G2 is missing from the `devModel` table, so it always takes the fallback.
- Read-only is checked where a write is *queued*, not where it is sent: `_reconcile_control()` gates on `_is_read_only()`, but `_debounced_write()` → `apply_schedule()` does not, while `apply_schedule()` does re-check `control_enable`. So a debounced write armed before read-only fires `hanchu_write_debounce` (10 s) later with read-only on. `hanchu_min_write_interval` defaults 60 s. Start at `_debounced_write`/`_is_read_only`. (PR #6216 review)

Tells: held entries in `Octopus slots changed` carry a `%z` stamp and no kWh; the row is `held: True`/`AT_HOME` with `amount` rising every cycle by (5 min × charge-point kW)/60. `octopus_slots_held` names the held half hours and `octopus_slots_held_saved` carries them across a restart. **The release gates** (`octopus_held_withdrawn()`, first in v9.7.8): needs `octopus_intelligent_dynamic` on plus a definitive not-charging read, and nothing logs when gated out. No `car_charging_now` sensor reads None (blocked); a load-inference misread such as the house battery's own import latches "seen charged" permanently; and the car-config `charging_now [False, False]` prints `bool(state)`. (GH#5884, GH#5957, GH#5962, GH#6130)
- **The withdrawal strip** (`octopus_strip_withdrawn_feed_rates()`): a minute at/after now outside 23:30–05:30 loses the feed's discount (reset to `rate_max_base`) once its half hour was seen covered by a dispatch (`octopus_feed_covered`, Storage-persisted) and no dispatch covers it now. Nothing is stripped while any car reads charging, under the window billing rule, or (dynamic Off) in the half hour in progress. Strips reset to `rate_max_base`, not the half hour's own rate, so for a few cycles a genuinely cheap window can read at peak. (GH#5663/#5984)
- **A car slot priced wrong for a newly added dispatch source** — which sources are billed at the tariff rather than a dispatch rate is encoded twice: `dispatch_billed_off_peak()` early-returns False for `bump-charge`, `BOOST` and charger-schedule, while `load_octopus_slots()` derives its own `tariff_rate_slot` flag independently. (GH#6110)
- **Do not read `Octopus Intelligent: car charging in its dispatch, preferring battery charge in the run to ...` as evidence the car charged** — it prints whenever the car is in a dispatch that was not cancelled. Build the timeline from `car_charging_now` history. (GH#6110)

### History fetch / memory (`ha.py`)

- History is fetched in `HISTORY_CHUNK_DAYS` chunks with boundary dedup; the chunking also multiplies REST calls enough to trip the startup API-error counter (see *Startup*).
- `HAInterface.get_history()` takes the db path only under `db_enable`+`db_primary`; until 2026-11-09 it ignored `from_time` there. Since PR #6071 an empty read is cached with `history_checked` and rechecked every 30 minutes less a 15-minute overlap; a failed read caches nothing. Anything calling `get_history_wrapper()` without `tracked=False` joins the 2-minute refresh for good.
- **`Found N load_today datapoints going back 2 days` on a recorder holding 10, with the depth resetting on every restart** — HA answers a bounded old window with `[]`, not an error, and `HAInterface.get_history()`'s chunk loop appends whatever each window returns (`return [history] if history else None`) with no check that it reached the requested start, so a read that falls short is cached by the consumer as complete and the 2-minute refresh only reads forward. The surviving span is whatever Home Assistant's bounded-window horizon leaves, and it moves between reports (one site on v9.10.0 at 3-day chunks read 2 days, then 4, and 7 with the constant set to 0), so it cannot be used to infer the chunk size. Two tells hold: the age comes from the first record returned, and the datapoint count is the padded array size, which hides the truncation. The chunk size is the module constant `HISTORY_CHUNK_DAYS = 3` in `ha.py`, not a config item (a `chunk_days:` key in apps.yaml is ignored silently); setting it to 0 in code and restarting restored full depth. Hits every `minute_data_load` consumer, Load ML included. Test trap: `history_chunking`'s mock always returns rows. (GH#6240, live on main 2026-11-25)
- The largest memory peak is ML load-predictor training, not the plan.
- Since PR #5837 `EntityHistory.prune()` keeps the last pre-cutoff record re-stamped at the cutoff, so a rarely-changing sensor's cached oldest record is an artificially-stamped anchor; suspected, unverified: a later merge can keep it contradicting a refetched record.
- Tests: `./run_all --test history_chunking`

### Minute data (`utils.py`)

- `minute_data()`'s gap-fill writes `newest_state` beyond the data, which for `backwards=False` is the earliest sample's value, so deltas after the fill show a phantom step. Convert deltas per sensor before summing.
- **With `to_key=None` (what `minute_data_import_export()` passes), `minute_data(..., backwards=True)` returns an entry for every minute of the window**, not just those with data: it pads 0..(newest sample − 1) with `newest_state`, pads older minutes with the oldest sample, then gap-fills. So a history of only `unavailable`/`unknown` records yields an **all-zero dict**, not an empty one; so does a history whose only record is older than the window. Only a genuinely empty result comes back `{}`. Anything keyed on a *value* of 0 must accept that 0 also means "no usable sample". (PR #6203 review, read-only)
- **A daily counter that resets at local midnight reads no reset on a DST-shifted date** — the reset test uses the history stamp's own clock (`stamp.time() < 00:06 or > 23:58`) and HA stamps are UTC, so under BST a local-midnight reset lands at ~23:00 UTC. A drop under 1 kWh then takes the small-dip path and `clean_incrementing_reverse()` flattens the day's early increments. (GH#6083)
- `get_from_incrementing()` adds 24×60 to a negative index instead of returning nothing, so a plan-axis key taken below 0 reads a plausible value from another day or the far end of the forecast. Guard where `minute - minutes_now` or a change-day start can go negative — the load forecast's tail is guarded since #6084. `fetch.py`, `load_ml_component.py` and `predheat.py` each carry the same wrap. (GH#5760)
- Tests: `./run_all --test minute_data`

### Battery capacity estimation (`inverter.py` `find_battery_size()`)

- The estimator applies `battery_loss × inverter_loss` to every sample, right only for an AC-side `battery_power`; DC-side it under-reads ~4% at defaults (GH#5831, open). Suspected, unverified: GivTCP's `battery_power` is DC-side.
- The 0.65–1.20 plausibility band anchors on `nominal_capacity`, which `refresh_config()` re-reads from the `soc_max` arg every cycle, so an integration that binds a wrong capacity there rejects every real charge (`capacity_too_high`) and the size never self-corrects. The fallback inside `battery_size_tracking()` is cycle-local. Sunsynk fixed this in PR #6007 by binding `soc_max_fallback`; DEYE still binds `soc_max` from its own capacity, so a mistyped Deye capacity still pins the band.
- `sensor.<prefix>_soc_max_calculated` is not always a measurement: it publishes the 7-day trimmed mean only with at least one non-None day, otherwise the `nominal_capacity` attribute (or `unknown`), and `battery_size_tracking()` reads it back only with a measurement or a nominal. On an install whose `soc_max` has since been unset, a restart could read the old configured size back as the "measured" mean. Since PR #6018 the unconfigured branch no longer writes the estimate into `soc_max`, and a day that found nothing retries hourly.
- The 80–100%-of-nominal clamp means `battery_scaling_auto` tracks only degradation below `battery_scaling`.

### Charge/discharge rate grid (`battery_rate_grid.py`, `battery_curve.py`, `inverter.py`)

- The plan's charge/discharge ceiling is a learned **rate grid**: SoC percent (101 columns) × battery temperature rows, looked up per minute by `rate_grid_curve()`/`rate_curves()` and applied in prediction, execute, output and the Curves page. A rate tapering near ~93% SoC is expected. (#6212)
- The manual `battery_charge_power_curve`/`_discharge_power_curve` and `battery_temperature_*_curve` make the base grid, fallback and prior. With `battery_rate_grid_auto` the learned grid is laid over it only once evidence covers `BATTERY_RATE_GRID_MIN_CELLS` (20) over `BATTERY_RATE_GRID_MIN_DAYS` (3) days; with it off the evidence is still gathered for the Curves page. (#6189)
- **"Battery temperature has no effect on the plan"** — the forecast reaches the plan only through `rate_curves()` → `rate_grid_curve()`, which quantises it with `grid_temperature_index()`, so a whole-degree forecast gives the identical curve: compare the grids, not the forecast values. An **exact 0 reading counts as "missing"** (it takes the grid's `zero_row`/`zero_cap`, not the 0 °C row, so 0.0 and 0.4 land on different rows), and beyond the grid's range it clamps at `BATTERY_RATE_GRID_TEMP_MIN`/`_MAX`. (PR #6243, code-read)
- Was a bug (fixed in PR #6247, 2026-11-21): the discharge grid is learned from forced exports, which run at `inverter_limit_export`, but the scan measured them against the discharge rating — a cap well below it learned nothing, and one just under it recorded a false taper that then capped house-load discharge in the plan. Export-limited minutes now record as no battery limit, told apart by `grid_power`. Durable trap: a grid value is a fraction of the rate the *consumer* asks against, so producer and consumer must agree on the maximum.
- Evidence comes from history runs of at least `BATTERY_RATE_GRID_RUN_MINUTES` (15) at the written full rate (every inverter ≥95% of its own maximum), ramp ends dropped, cut into 5-minute segments, kept per day for 365 days with a 90-day half-life, rescanned daily. A failed store read and an empty store both look like None: the store is treated as empty only after failed loads spanning 10 minutes, and is saved with a ~395-day expiry so a backend's 72 h default cannot drop it. (#6225)
- **"Efficiency/loss should differ per inverter"** — `inverter_loss`, `battery_loss` and `battery_loss_discharge` are read globally (no `index=`) in the fetch config pass, while `inverter_limit*` and `inverter_battery_rate_min` are per inverter, so a per-inverter loss is a real gap. `inverter_loss` is already direction-aware (multiplied on charge, divided on discharge) and `inverter_loss_ac` is 1.0 on a non-hybrid, so only the *power* dependence is missing. Battery losses are DC-side efficiencies, so new `battery_dc_*` keys would double-count. A curve already fits the ABI (`PK_CURVE_WIDTH` 103-row tables); the obstacle is that power-dependent efficiency is implicit and needs an iteration in the kernel. (GH#6224)
- The learners run on inverter 0 but read the **whole fleet's** history (`curve_fleet()`), because the plan models one summed battery. A `0`/blank entry in a per-inverter list is the documented site-total idiom, not a missing setting: truthiness cannot tell it from an absent entry (`resolve_arg` turns an out-of-range index into `None`), so use `is_entity_id()`/`counted_in_site_total()` (fixed in #6227). When another inverter lacks a setting or history, learning falls back to inverter 0 alone, except under a site total, where it warns and refuses. (GH#6226, #6229)
- `Info: ... Cannot find battery discharge rate grid evidence, export_limit ... is below the discharge rate and there is no grid_power history to tell which exports it limited` — wire `grid_power` or accept the manual curve.
- `battery_temperature_charge_curve`/`_discharge_curve` are apps.yaml-only keys checked by `validate_curve()` in `fetch.py`, not CONFIG_ITEMS; `battery_charge_power_curve`/`_discharge_power_curve` and `battery_rate_grid_*` are CONFIG_ITEMS. (GH#5630)
- Tests: `./run_all --test battery_rate_grid --test battery_rate_grid_scan --test battery_rate_grid_update --test battery_curve_keys`

- Climate Scheduler (#6042) reads `climate_scheduler/get_schedule` (`schedule_mode` `all_days`/`5/2`/`individual`, node `time`/`temp`/`hvac_mode`) and `get_settings`, whose keys are exactly `"workdays"` and `"use_workday_integration"`. `DEFAULT_WORKDAYS` is Mon–Fri. HA's `workday/check_date` takes `check_date` (not `date`) and returns `{<entity id>: {"workday": bool}}`.
- Predheat works in °C internally: entity temperatures are converted in from their unit since PR #5958 and results published in the user's unit, so a °F entity running the forecast away while energy stays 0 is a pre-#5958 log. An entity with no unit is read in HA's unit. (GH#5153)
- Thermostat bands: `hysteresis` (0.5 °C) is how far **below** target heating turns **on**, `hysteresis_off` (0.1 °C) how far **above** it turns off. The COP key is `heating_cop`, with `heat_cop` still supported, default 0.9.
- Two routes to the fallback target (21.5 °C): an unset `heating_energy` meter pinned `minute_data_age` to 0 (PR #5867); `EntityHistory.prune_history()` dropped the state-in-force record, so an `unavailable` blip floored age to 0 for 24 h (PR #5837).
- Traps: `run_simulation(save="best")` publishes HA entities, so a parameter sweep overwrites the sensors; Predheat reads `datetime.now(local_tz)`, so build history mocks against wall-clock time.

### Load ML (`load_ml_component.py`, `load_predictor.py`)

- The 2-hourly retrain is a curriculum of passes, a 16–40 minute CPU spike every 2 h (GH#3896, GH#5213). `threads` reaches only the C++ kernel and nothing caps BLAS threads.
- `load_ml_retrain_interval_hours` (PR #5433; default 2, max 48) is age-based. Past `ml_max_model_age_hours = 48`, `is_valid()` returns `"stale"` and ML predictions fall back to empty.
- `load_ml_enable`, `load_ml_source` and the retrain interval are component/apps.yaml args, not CONFIG_ITEMS.
- `is_valid()` can say "active" for a never-trained model, and an aborted curriculum leaves fresh stamps that suppress the staleness retrain (GH#5075; fix in open PR #5112). Since PR #6319 a deferred initial training records a success, so a fresh install no longer reports "component errors: ML Load Forecaster".
- `PREDICT_HORIZON` is 48 h (576 steps) and the plan's load beyond it is exactly 0, as `load_forecast_only` skips the historical forecast (GH#5336, open); "over 48h" in `Generated N predictions` is hardcoded text.
- Each fine-tune can move the published 48 h total by double digits (GH#5561, open): bracket `Training successful` with the adjacent `Generated N predictions (total X kWh ...)` totals. The ML forecast replaces the load forecast with no blend.
- Load exclusion knobs (`car_charging_energy`, `iboost_energy_subtract`, future `heat_pump_energy`) reach ML-source users only if the data prep subtracts the same: car already did, iBoost since PR #5829. Saved rows are restored verbatim, so a data-prep change reaches only fresh minutes until old rows age out.
- "The LoadML trace shows large spikes and deep flat sections" has two mechanisms: rate history from the `rates` sensor's `results` attribute backfill (fixed by PR #6241, `pad=False`) and long-range rollout error meeting ReLU death in `_normalize_features()` (fixed by `FEATURE_Z_LIMIT`, ±5σ in `bound_normalised()` and both `WindowedFeatures` row paths, `MODEL_VERSION` 11). Discriminator: `pattern_mae_kwh` vs `rollout_mae_kwh` on the `load_ml_stats` sensor (PR #4678). On an older saved history the flat region starts exactly at *yesterday 00:00 relative to when the file was saved* — that is the backfill, not a recorder gap. (#6147, #6208, #6259)
- **Rate history still one flat value for weeks after the `pad=False` fix, or a corrected fetch that changed no rate stats** — `pad=False` only stops the oldest-value backfill *below* the oldest record; absent rate minutes still reach the model as **0.0**, not NaN (`dict_to_array`/`array_to_dict` persist NaN, but `_create_dataset` zero-initialises every channel and skips empty chunks). The channel merge is a repair path (`merged.update(new)`, new wins), so a fetch only replaces rows the recorder still holds — older rows need the history npz deleted. (PR #6241)
- **A LoadML forecast flat at one value (or jumping several-fold) around a saving session or Axle event, on an old model** — inspect the saved weights before the inputs: in #6147/#6208/#6259's models only 69%/27%/2% of the 256 second-layer units fired on any of 576 validation windows, and clipping their inputs revived none. Retraining from scratch on the same history gave 52–98%, so only a retrain clears it — why `MODEL_VERSION` was bumped. Replaying those histories: a +100p future spike moved single steps by up to 16× without the limit and under 4× with it; two training runs per case could not tell the accuracy apart, so robustness, not accuracy, is the measured gain. Trap for offline experiments: `_initialize_weights()` calls `np.random.seed(42)`, so every run is identical unless that call is redirected. (GH#6147, GH#6208, GH#6259)
- **The LoadML forecast stays at the household's long-run level through a cold snap** — by construction: `predict()` blends the autoregressive rollout with a per-weekday daily pattern down to `blend_floor = 0.5` at the 48-hour horizon, and a multi-month mean cannot move inside a snap. Training is one step ahead with teacher-forced validation, so a good `val_mae` measures persistence on the same regime. Check the temperature source feeds the *forward* channels: Open-Meteo's `past_days=28` returns ~7 days ahead as negative keys. (GH#6157)
- Replaying a LoadML npz pair offline: `ml_model.npz` holds no object arrays and **float64 weights** — cast nothing. `ml_history.npz` keeps only positive, 5-minute-aligned keys, so per-minute temp/rate keys collide into `minute//5` buckets. Rebuild `{i*5: value}` dicts; set `model_initialized` (or `predict()` returns `{}`) and the metadata means/stds. Future channels use **two key formats**: the temperature sensor's results attribute is quoted ISO with `+00:00`, while `predbat.rates`/`rates_export` are unquoted `...+0000`. Self-check by matching `pattern_mae`, `prev_energy` and `max_dow` against the `Starting autoregressive` line; the published 48 h total may still differ (31.5 vs 36.8 kWh in #6208) because future exogenous channels are absent — say so rather than presenting the gap as a finding. `Forward temperature/rate forecast ran out` fires only when a step is missing from temp **and both** rate channels. (GH#6157)
- **LoadML saved history drifts later in the day with age (forecasts gain implausible overnight blocks, worse on older rows)** — `_fetch_load_data` reads the clock repeatedly across its own span, then `_merge_fetch_data` reads it again (`load_minutes_now_time`, then `last_data_fetch`, the anchor the next shift is measured against; `_merge_channel` takes no clock), and the component is on its own thread, so a main-thread `update_time()` can replace `base.now_utc` mid-fetch; keys come out one step small, which means the sample appears *later* in the day (~9–10 min/day). Only the fetch window is rewritten, so older rows keep the error. Diagnose by indexing the file from its `saved_utc` and taking a **circular** production-weighted mean of the PV channel (a linear mean wraps past midnight); the temperature channel agrees independently. Test trap: the run test moves the mock clock only *between* runs. (GH#6238)
- Tests: `./run_all --test ml_training_perf`

### Savings & metrics (`output.py`, `predbat.py`)

- `savings_total_predbat` accumulates the unadjusted `saving`, while `savings_yesterday_predbat` publishes `saving_adjusted`; they can disagree in sign (GH#3894). The battery-value adjustment bills the day-end SoC level against the baseline, not the day's change.

- **A new per-kWh *planning* price belongs in `compute_metric()`, and nowhere else in the kernel.** `run_prediction()` returns `import_kwh_battery` separately from `import_kwh_house`, and both reach `compute_metric()`, where `metric_self_sufficiency` prices their sum. The C++ kernel returns raw `cost` and `battery_cycle` and never the metric, so a new metric term needs **no** `PREDICTION_PARITY`/`PK_PARITY_REVISION` bump — but a simulation accounting change does. `import_kwh_battery` is an upper bound, not "energy delivered to the battery": it accumulates every grid import in a step where a charge window is *open*, house load and already-full windows included. A price term has a second home: the charge-window `average` used to band windows (`sort_window_by_price_combined`) adds `metric_battery_cycle` and `metric_self_sufficiency`, as does the plan table's "Import (w/loss)", so a term added only to `compute_metric()` leaves the banding and display disagreeing with the decision. A new `p/kWh` `input_number` gets `currency_scale` free. Deriving a round-trip cost from the loss settings is not equivalent to a measured one (defaults give ~13% where a reporter measured 9%). (GH#6207)

### Component health (`components.py`, `component_base.py`)

- `count_errors` is a lifetime counter. `api_started` means `run()` returned truthy once. `is_alive()` is the real health check (60-minute staleness). Device-writing methods are listed by `write_methods()` via the `@writes` marker; overriding a marked method without re-marking it silently unmarks it (PR #5920).
- `record_status()` writes raw text as the HA state, and HA rejects states over 255 characters. A test of `update_status()` sees only the last `record_status()` message.
- Each component has its own thread, so blocking compute stalls only that component and `run_timeout` never fires. Slow shutdown: find the `run()` that cannot return, load_ml first (PR #5112 open). `Components.start()` waits up to 10 minutes per component, serially, so restart delay ÷ 10 minutes = dead-component count (GH#5580).
- A `run()` exception skips the rest of that cycle and retries on backoff, so report what was skipped, not a "crash" (GH#5584). `json.JSONDecodeError` slips past `aiohttp.ClientError` handlers. On timeout, `start()` cancels the task without setting `api_stop`, and the next tick may start a second run.
- Since PR #5963 each component owns a clock (`monotonic()`/`wall_time()`): elapsed-time windows are stamped on it; anything leaving the component stays on the wall clock. A stamp initialised to 0 needs an explicit zero-guard.
- `align_minute: True` runs the loop at minute boundary +1 s. `run()`'s `seconds` steps in whole minutes, so interval checks must be relative deltas. Sigenergy, Solax and Teslemetry set it (PR #5976).
- A component whose fetch fails **gracefully** never triggers backoff, so a one-shot `if first: automatic_config()` against empty data is a permanent silent miss (Octopus: KT-CT-1199 → None → previous data → `tariffs == {}` → `run()` returns True). Octopus's is fixed (PR #6080); other components are unaudited. (GH#5994)
- A hardware fault is invisible outside the component's own log unless it calls `self.base.record_status()` (`solax.py` calls it nowhere; `gateway.py`'s error path is the precedent) — and the `had_errors` branch in `update_pred()` skips `record_status()` entirely (GH#5996).
- An every-cycle `failed to report discovery for the catalogue: <AttributeError>`: the guard covers `KeyError`/`IndexError`/`TypeError`/`ValueError`, but a read of the data container *outside* that try raises AttributeError uncaught, and `refresh_discovery()` swallows it (GH#5936).
- Stamping liveness on cache-only cycles hides a dead component, so override `is_alive()` (enphase, Kraken; GH#5582).
- A component whose thread is still running after all log Stopped keeps the process alive; `test_component_shutdown` covers it.

### Run loop (`predbat.py`)

- The HA-interface guard is duplicated in `update_time_loop()`/`run_time_loop()`. `test_time_loop_guard.py` tests only `ha_interface is None`.

### HA websocket socketLoop (`ha.py`, `hass.py`)

- Event handlers run on the socketLoop, so a handler awaiting a queued WS call deadlocks for 2 minutes. `run_in_executor()` returns inside a `with` block and blocks its loop. Never-sent signature: an all-None `Service call ... failed or timed out` after exactly 2:00, with no `Service call timeout for request id` line (GH#3460, open).

### Carbon intensity (`carbon.py`, `fetch.py`)

- The API publishes up to ~48h ahead, often far less, and returns `{}` with HTTP 200 past the horizon; `prediction.py` scores uncovered minutes as zero carbon, so `best_carbon` swings. Matters only when `metric_carbon` is non-zero.
- **The carbon forecast runs short between polls, by design** — `fetch_carbon_data()` skips while its data is under 4 hours old while the component visits every 15 minutes. Two warns, so read which fired: a fetch reaching under `CARBON_FETCH_SHORT_HOURS` (47) is a genuine shortfall and warns once per fetch; the per-cycle `Carbon intensity forecast only covers X hours of the N hour plan` is only a `Warn:` below `CARBON_WARN_COVERAGE_HOURS` (24). (#5964)
- **Every carbon column in the plan is 0 while `sensor.<prefix>_carbon_intensity` carries a full forecast** — the plan-side read is gated on `carbon_enable and ("carbon_intensity" in self.args)`, and setting `carbon_postcode` starts the component regardless: only `carbon_automatic: true` (default **false**) wires the arg. (GH#5986)
- Tests: `./run_all --test carbon`

### Storage (`storage.py`)

- Expiry is checked against the real clock, so an expiry built from Predbat's `now_utc` is born expired under replay or tests.
- `Storage.save()` signals failure by returning `False`, not by raising — a `try/except`-wrapped write that ignores the return treats failure as success. Grep `run_async(storage.save(` for callers that must be reliable; `save_plan()` still ignores it.
- **`Storage: Error: Failed to write ... [Errno 36] File name too long`** — the backends compose `<module>_<identifier>` and never length-limit it, so a long URL exceeds 255 bytes and the `.meta` sidecar fails too. Fixed caller-side only (`SolarAPI.solar_cache_key()` hashes to sha256[:16], PR #6165); a trailing md5 of `"{}"` in an old filename is the pre-fix tell.
- Tests: `./run_all --test plan_persistence`

### DB manager / DB engine (`db_manager.py`, `db_engine.py`)

- Opt-in paths. `set_state_db()`'s `utcoffset().seconds // 3600` is wrong for negative or half-hour offsets (GH#5693; PR #5698 open). `db_engine` lowercases ids on read only; the read-back key is `last_updated` with a trailing `Z`.
- **A command that raises in the DB thread posts no IPC result**, so `send_via_ipc()` waits the whole `IPC_TIMEOUT` (60 s) and returns `None`: `Error: No response received for command 'get_history'` with a 60-second hang, every cycle. Any new DB command must make its engine call unable to raise (PR #6062).

### Manual override selects (`userinterface.py`)

- Option lists are built in three places (`manual_times()`, `manual_rates()`, `api_select_update()`); change all three.
- Elapsed slots are pruned every cycle, so past cheap rates re-price at base (GH#5517, open). `get_override_time_from_string()` rolls forward only bare `HH:MM`, so a same-weekday earlier `"Thu 07:00"` decodes to the past and drops (GH#5832, open).
- The manual-API allowlist (`CONFIG_API_OVERRIDE`) and `docs/manual-api.md`'s list drift, and the allowlist is the whole gate — grep both in a PR touching either (GH#5839).

### Marginal rate sensors (`marginal.py`)

- Plan-relative predictions (+1/2/4/8 kWh injected), refreshed only on plan publish. With a base minimum ≤ 0, cheap never turns on (GH#5826, open). `marginal_plan_cost()` duplicates `compute_metric`'s battery_value term, so edit both.

### Manual rates (`fetch.py` `basic_rates()`/`rate_replicate()`)

- A rule ending `:59:59` leaves the window's last minute at 0p; end rules at the next rule's start. Unmatched minutes take `metric_future_rate_offset_*`. Test `day_of_week` rules beyond tomorrow.

### Manual load adjust (`fetch.py` `step_data_history()`)

- `manual_load_adjust` is additive, floored at zero, and marked `±` in the plan HTML (GH#5176). Free-event load gets baked into history (GH#4942, open).

### Status health (`output.py`, `predbat.py`)

- A false "(unhealthy)" on Python ≤3.10: `last_updated` is written with `%z` (no colon), which `is_running()`'s `fromisoformat()` rejects before 3.11 (GH#5181, open). Fix the writer to `.isoformat()`.

### Futurerate / AgilePredict (`futurerate.py`, `fetch.py`)

- `rate_replicate(use_future=True)` fills live import/export, so the `*_base` tables, compare recognition and the IOG strip value include forecast fills (PR #5738).
- AgilePredict: `GET https://prices.fly.dev/api/{REGION}/?days=N&high_low=false` (N ≤ 14; `&export=true` for export) returns half-hour `{date_time, agile_pred}` entries from the current half hour; mixed timezones across DST; cached ~180 min. The post-April-2026 discount is applied **before** the unit-rate cap, and the cap is 95.23p (5% VAT makes it 100p). (PR #6100)

## Symptom → first place to look

What a report or log shows, and where to start. Where a symptom belongs to one integration, the bullet points at that area's notes above.

### Startup, config and apps.yaml

- **`You have not set load_today or load_forecast in apps.yaml` then `Exception raised ValueError` every cycle** — since PR #6101 the cycle is skipped without a traceback while no load source is set. Cloud components set `load_today` at runtime, so during their startup delay check the Components panel. (GH#5092)
- **`timer_tick caught exception`, "stopped planning"** — an exception escaped `update_pred()`; find the raiser from the payload. `ReadTimeout` is not a `ConnectionError`, a hole in any `except ConnectionError` (PR #5801). (GH#5743)
- **`Too many API errors, stopping`, "stopped but running", `Cannot initialise Home Assistant Interface` (empty message), or silence after a restart** — this was the `fatal_error` latch: consecutive REST failures with no decay, stopped at 10, reachable from one startup history fetch (`HISTORY_CHUNK_DAYS` 3, the 30-day fetch exactly 10 calls). **Fixed in PR #5449:** an outage timer (`HA_OUTAGE_LIMIT_SECONDS`, 15 min); any contact ends it, REST and websocket keep separate timers, `initialize()` retries with backoff but fails at once on a 401/403 `ha_key`, and Supervisor calls no longer count. "Stopped after 10 errors" on a current log dates it earlier. Two amplifiers survive: `wait_api_started()` never checks `fatal_error`, and the standalone fatal watcher starts only after `initialize()`. No-interface repeats follow the 0/120/360 s ladder (GH#5886). (GH#5354, GH#5744, GH#5806)
- **predbat.log shows only `Loading secrets from ...` / `Loading apps.yaml` every ~20 s, never `Startup`** — apps.yaml failed to parse, usually an unknown tag (only `!secret` is registered). Since PR #5642 the parse error is logged with the offending tag. (GH#5530)
- **`Invalid value None in element predheat.heat_energy$external`, no `Predheat:` lines** — `predheat:` must sit inside `pred_bat:`; bundled sub-apps read via `self.args.get(domain, {})`. (GH#5002)
- **A config item above its maximum stays capped, or a slider accepts a value the engine reverts** — a `CONFIG_ITEMS`/`APPS_SCHEMA` `max` clamps every source including apps.yaml (GH#5070). Entities advertise min/max but do not clamp writes; the Warn-clamp runs only at startup, after a config write and on the 8-hour refresh. Every restore path applies `value` only. The clamp also catches items the engine writes back via `expose_config()`, so their max must cover the physical range: `next_volume_temp` (fixed in PR #6173), `car_charging_manual_soc_kwh` (100 kWh), `iboost_today` (30), `holiday_days_left` (28) — fix the range, not the clamp. (GH#5995/#6000)
- **"Predbat reports a GivEnergy error but I use Solis / Fox / GE Cloud"** — `inverter_type` is `GE` until component auto-config sets it; self-heals. (GH#4990)
- **`Inverter N unable to read charge window time - no source is configured` every cycle** — deliberate with no `charge_start_time` and `inverter_source_active()` False (GH#5804). Read the dump's `inv_charge_time_format`: `HH:MM:SS` on a non-GivEnergy setup means the template's `inverter:` block never applied (flattened to `pred_bat:` level). The same raise is legitimate on a real type with `has_charge_enable_time` and no source. (GH#5804, GH#6113)
- **`apps.yaml has N errors` naming a `*_today` "not a valid type float", or `Warn: Validation of apps.yaml found ...` while it runs normally** — validation is warn-and-continue and reads live states, so an `unavailable` accumulator fails a few times a day. An unquoted all-digit value is the usual benign case; quote it. A *list* where the schema says `string` passes item by item. (PR #6104 review)
- **`Validation ... is not a list, but requires N entries based on num_inverters` plus `Return bad int value [<list>]`** — the `entries: num_inverters` check disagreed with a reader lacking `index=`. PR #5651 added `single_value_ok` for `inverter_battery_rate_min` and `inverter_reserve_max`. (GH#5369)
- **`Validation ... element <entity> which cannot be modified` while everything works** — the writable-domain allowlist in `validate_config()` has drifted from the write paths (`input_select`, `input_boolean`), so a helper domain the validator forgot is a false positive. (GH#5885)
- **An inverter drops out of the plan after an upgrade on a mixed fleet** — start at the vendor `automatic_config()`'s `set_arg_auto(..., overwrite=True)` writes (grep `auto-discovery wins`). Workaround: `givtcp_automatic: False`. (GH#5029, GH#5209)
- **An apps.yaml entry for a daily total is ignored or reverts under `<integration>_automatic`** — the totals are discovery-bound and `set_arg_auto(overwrite=False)` is adopted unevenly: GivTCP for the four plus `export_limit`, Sigenergy for `export_limit`/`battery_min_soc`, Hanchu for the four; GE Cloud binds several with plain `set_arg`; Solis default-overwrites (only `load_today`/`pv_today` escape, via `solis_cloud_pv_load_ignore`). Read the component's `automatic_config()` first.
- **"Predbat entities that won't go away" / a "[Disabled] ..." entity after turning a feature off** — enable-gated config entities are never removed; disabling keeps the entity with its last state and a `[Disabled]` prefix. Feature outputs such as `iboost_best` publish regardless of the enable switch. (GH#5922)
- **`Watched event: <entity> = {...} will trigger re-plan` repeating each refresh** — `watch_event()` sets `plan_valid = False` unconditionally, so an `event.*` entity fires on every refire. Fingerprint attributes for event entities and state for everything else. (GH#6105)

### Plan: charging and holding

- **Plan shows Freeze/Hold charging through the evening peak ahead of an Axle or saving event** — the hold level is usually `best_soc_keep`, not the event: compare the charge window's target and the plan's final SoC with `best_soc_keep / soc_max`. The event only supplies the pre-event import windows (`find_event_pre_charge()` → `find_low_rate_windows()`, merged by `combine_charge_slots`) and makes the keep bind; the keep sets the level. Check `best_soc_min` and `load_scaling` too. A weather-alert keep is the #3200 variant. (GH#3188)
- **Battery charges, freezes or discharges when it shouldn't** — rule the plan out first. A planned freeze is a charge window whose limit equals the reserve %; on an all-loss tariff holding full is correct (GH#4890). An alert keep (default 100) is a *floor the optimiser defends*, not a hold (GH#3200). Every minute outside a charge/export window is ECO in `predict()` — only EV slots and iBoost hold the battery, so "why discharge during cheap hours" is a model gap (GH#5122).
- **The plan drops the SoC to the reserve in one row — "55% → 10% in 20 minutes", an impossible discharge rate — with `Battery has 0.0 hours left` every cycle** — the drawn power is capped; what is wrong is how much SoC a drawn kWh costs. `fetch_config_options()` stores `1 - setting` as the *efficiency* in `self.battery_loss`/`_discharge`/`self.inverter_loss` (and `fetch_sensor_data_cars()` for `car_charging_loss`), so typing the efficiency (0.97) instead of the loss (0.03) models a 3%-efficient battery. The `Calculate Best options` line prints the *loss* (`battery_loss_discharge (97%)`), so it agrees with the reporter — read it as `1 - efficiency`. At 1.0 (the entity max) the efficiency is 0 and the prediction divides by zero. Nothing clamps or warns on main (2026-11-25); PR #6235 would. Note the same three names under `dummy_inverter:` are efficiencies (0.96 default) — the opposite convention. (GH#6235)
- **Battery pinned at 100% while the house imports at peak** — `Completed run status Demand`, zero register writes and a flat SoC mean something outside Predbat refused the discharge; check the integration's reserve/min-SoC binding. (GH#4961)
- **`Hold charging target X%-Y%` while importing at peak** — the high-price gate (`best_price_charge_level`) guards only windows whose limit is still 0. Without `set_reserve_hold`+`set_reserve_enable` (or `inv_has_timed_pause`) "Hold charging" is an armed-window fallback; `not yet in charge freeze, holding target SoC at 100%` is a deliberate pre-window write. The suffix is SoC–target. (GH#2716)
- **`HoldChrg -> N%` while the slot charges higher, or a "Planned Charge" row whose SoC never rises** — a row's target is the predicted end SoC when the window cannot reach its limit, and `HoldChrg` shows only when the modelled SoC stays at/above the limit over the whole window; otherwise it falls back to "Planned Charge" with its rising arrow. Check the dump's `best_charge_limit` against `status_detail`. (GH#4445, GH#5889, GH#5902)
- **`set_reserve_min` 100 and it never charges — `Filtered charge windows []`** — the charge scan needs levels strictly above the reserve, so a reserve ≥ `soc_max` leaves only "off". (GH#4766)
- **First cheap window charges to 0% / the target lands later than the cheap band** — a metric tie: the SoC scan adopts on a non-strict `<=`, and with `metric_battery_cycle` at 0 a charged kWh scores as its stored credit. (GH#5069)
- **Overnight charge stops at "just enough", starts late and stops short** — pruned pv10/pv90 hedge slots, fixed in PRs #5721/#5735 (`Prune dead`/`Prune kept hedge`/`Prune trade-off` per slot). The "stops short when a free session sits later" case is by design. (GH#5719)
- **The plan won't adopt a clearly better replan** — `should_replace_plan()` compares pre-clip snapshots and a retained incumbent keeps a stale one. (GH#4736, GH#5261)
- **`Will not recompute the plan, it is 5.0 minutes old and max age is 10 minutes` at a tariff boundary** — the gate is `plan_age_minutes + RUN_EVERY > calculate_plan_every` with a strict `>`, and both stamps sit on the 5-minute grid, so at the default 10 the run after a recompute never replans; a rate rollover is not a trigger. Workaround `calculate_plan_every: 5`. (GH#6102)
- **The battery keeps charging at a higher tariff inside one window although the row shows a hold after the rise** — nothing splits a window at a rate change: `clip_charge_slots()` raises a charge's limit to full so adjacent windows merge, and `discard_unused_charge_slots()` merges same-limit neighbours with no price check unless `set_charge_low_power` is on. (GH#6108)
- **A near-tie flip adopts the cleaner plan and the branch has no cost check** — the fragmentation branch takes any `improvement >= 0` with fewer segments; `plan_fragmentation()` counts each night's charge window above the reserve. (GH#5991)
- **Charge and hold writes alternate every 5 minutes** — SoC flips 1% across the target: the hold gate `soc_percent >= inv_target_soc_percent` has no tolerance, and the `- 1.0` hysteresis nested inside it is dead. (GH#5083, open)
- **Low power charging does nothing, charges at full rate, shows "rate zero" on a dawn-split dark half, or changes rate several times** — by design: `find_charge_rate()` uses max rate when the window's average remaining PV forecast is at least `low_power_pv_threshold_w` (150 W), re-runs every cycle filtered by `rate_tolerances()`' 5%; a dark half showing "rate zero" is frozen at the reserve. Treat requests as enhancements. (GH#4577, GH#4975, GH#5241, GH#5536)
- **The low-power rate exists only inside the running-window branch.** `execute_plan()` calls `find_charge_rate()` in the in-window branch; outside a window no branch claims the rate, so `apply_rate_intent()` resets it to `battery_rate_max_charge` and a window armed before it starts opens at full rate (~60 s, ~0.1 kWh). The lead-in is `set_window_minutes`, from `plan_interval_minutes` (30), **not** `RUN_EVERY` (5); `inverter_set_charge_before: false` sets it to 0, and `create_predbat()` doubles run with 30. Traps: adding a branch to that pre-window `if/elif` chain silently drops the `else` — the IOG action-latency recording has exactly one writer there; the window enable is written *before* the rate within a cycle. (PRs #6211/#6190, GH#6190)
- **"Predbat won't charge when the battery is cold"** — `find_battery_temperature_cap()` treats curve values as fractions of `soc_max`; a `0.00` step is a genuine 0 kW cap, so with a charge-current-triggered BMS heater that is a causal loop. Without `battery_temperature_history` one temperature spans the horizon and `predict_battery_temperature()` repeats 24 h-old deltas, blind to heater runs; no heater concept exists. (GH#5919)
- **Every planned charge capped at a temperature curve's coldest step while the live battery reads warm** — `predict_battery_temperature()` anchors on `history[0]` and adds the 24-hours-ago delta per step, so the horizon is whatever the `battery_temperature_history` entity recorded: a sensor that records 0 (a GivTCP stack BMS sensor can, for days) predicts 0 °C, and one with no rows predicts the 20 °C default. Check the history entity really has non-zero rows. (GH#6193)
- **Two charge windows meet at 00:00 inside one cheap period** — `calc_dawn()`'s light latch resets at midnight; since PR #5709 `find_charge_window()` splits only at dawn. (GH#5205)
- **`calc_pv_light_dark()`/`calc_dawn()` answer "before dawn", not "is it dark now"** — within each day the light flag is a one-way latch: everything from the first forecast bucket at or above 150 W to midnight reads light, including after sunset. Deliberate (#4557/#4699), and there is no dusk detector. The dict is empty with no PV forecast, which reads as "never dark". (GH#6181)
- **Turning `debug_enable` on changes the plan** — deliberate: `kernel_supported()` refuses under `debug_enable`, and Python honours the coarse `enable_fast_mode_levels` step. (GH#5408, GH#4453)
- **Control SOC only: status `Demand` during the inverter's own charge window, or an AC-coupled inverter charges to 100%** — `isCharging` used to be set only inside `execute.py`'s `set_charge_window` block, so a charge the inverter ran itself counted as no charge; fixed 2026-11-06. (GH#5991, GH#5987)
- **"Why does the plan use these charge windows" in Monitor / Control SOC only** — with `set_charge_window` off, `calculate_plan()` clones `self.charge_window`, which the executor fills from the first enabled inverter's own windows, so the tariff's never appear; a mixed fleet follows only that first inverter. (PR #6001)
- **`best_keep {}kWh` in a plan log is a penalty, not a planned level** — `metric_keep` prices the deficit below `best_soc_keep` at the minute's import rate × weight × duration. (GH#5987)
- **Predbat exceeded the site's import ceiling** — the planner has no import clamp; `import_limit` is only a discovery rating. Draft PR #5486 open. (GH#5490)

### Plan: exporting

- **Exports happen at the wrong time** — `plan.py`'s export pass order, `combine_export_slots`, `metric_min_improvement_export`. **"Random" exports that lose money on a flat tariff** — see GH#4840 above.
- **A plan that never exports in the tariff's cheapest export band** — the automatic threshold in `set_rate_thresholds()` is `rate_export_min + 0.5` whenever the cheapest export pays less than the cheapest import (the common shape), and the scan only admits minutes at or above it, so a slot at the tariff's own minimum can never be a candidate. A rescan in `fetch_sensor_data()` then overwrites `rate_export_cost_threshold` with the lowest average it admitted (the higher band), so the dump and published sensor show a ratcheted value the scan did not use. The other branch (`rate_export_min > rate_min`, equal max/min, or an alert) takes `rate_export_min - 0.1` and admits everything. Adding candidates is the only route into the plan: `calculate_plan()` clones `high_export_rates`, and `clip_export_slots()` can only narrow or raise enabled windows. `high_export_rates` also drives the published sensors and plan shading, so clipping-driven slots belong in a separate candidate list. Probe-verified: 20p/90p export against flat 23.8p import gives 20.5p and no window before noon. (GH#6214)
- **`Best export window @ 0p` on a non-zero export tariff** — a stale discharge window read back from the inverter (`average = 0`), used verbatim under `calculate_best_export: false`. A `discharge_rate` + reserve write after a charge window is the routine restore. (GH#5036)
- **"Predbat writes my inverter's minimum SoC as the forced-export cut-off instead of the target it planned"** — by design: `adjust_force_export()` writes `discharge_target_soc = int(reserve_percent)` ("always set to the minimum reserve", so it tracks the reserve in both directions), and only the 5-minute loop enforces the plan's target. On Fox Cloud the reserve is visible in the schedule itself, as `fdSoc` on the `ForceDischarge` group. GH#3101 proposed writing the planned target and was closed as "not the right approach" — a maintainer decision, not a gap. (GH#6248)
- **"Charging and exporting in the same slot"** — two windows in one 30-minute row; `output.py` splits the State cell deliberately. (GH#4987)
- **Loss-making forced export kept plan after plan; `Prune kept hedge export slot`** — fixed in PR #5977. Prune pairs read (without slot) vs (with slot), lower is better; `export_threshold_penalty` is charged per plan interval of export still to come (PR #5874). The dead-slot branch still drops on nominal-identical-plus-no-SoC-move alone. (GH#5969)
- **An evening export drains to the same level whatever the load risk** — the pv10 scenario used to score target exports at `best_soc_min`; since PR #5736 it floors them at the nominal run's end SoC. And since PR #5874 the export gate charges `metric_min_improvement_export` per interval of export still to come, scaled by power, against the export-off baseline — so every extra 5 minutes of a deeper start must earn its own share. (GH#5860, re-checked on main)
- **An export window is in the plan but moves nothing** — limits 99.3/99.5/99.7 mean "Hold exporting" in both engines, and 99.0 is the freeze sentinel (GH#4914). A freeze-export window zeroes an overlapping charge candidate. Change both engines together (`test_kernel_parity.py`).
- **A `FrzExp` slot / 99.0 in a zero-PV period is not a fault** — freeze export computes identically to Demand at PV 0; the label is cosmetic. Dead freezes are removed by `prune_dead_plan_slots`. (GH#4124)
- **A dump's `rate_export_cost_threshold` is rewritten from the plan's own level**, so it is not the operating threshold (GH#5221). On a pre-v9.3.7 log, every ordinary export window vanishing while an event was in the horizon was that threshold latching at 99 (fixed in PR #5163).
- **Predbat plans exports the site may not make** — on Teslemetry see `update_battery_export_permitted()`; elsewhere `export_limit: 0` and `battery_rate_max_discharge: 0` both mis-model it. (GH#5710)
- **Do not compare the plan table's two "(w/loss)" columns** — Import-(w/loss) = raw / `battery_loss` / `inverter_loss` + `metric_battery_cycle`; Export-(w/loss) = raw × `battery_loss_discharge` × `inverter_loss` − `metric_battery_cycle`. "Export w/loss 32 < Import w/loss 40, so holding wins" compares sell vs re-buy. The loss chains cancel when both paths discharge, so the raw export-vs-import spread is the trade for the displaced part. When export < import the optimiser trims rather than forbids (the `Export windows filtered [... @ N%]` percent is a SoC floor, not a price). (GH#5999)
- **The export icon says off while the battery exports** — `isExporting` is not set by the demand-freeze block; read the status text. PR #5131 open. (GH#5125)
- **"Predbat planned an export inside a free / 0p import session"** — start at `load_free_slot()` and `load_scaling_free`, not the export gate. A free session only scales the in-session load by one multiplier (slider capped at 2.0), and nothing suppresses an export window inside a 0p import window: windows are scanned from `rate_export` alone, with the import table reaching the scan only as `alt_rates` to *split* a window. The only export-on-charge guard is `calculate_export_oncharge` (default off), and it drops an export only where it **overlaps** a charge window still carrying a limit. Charging at 0p and exporting at 20p is genuine free money, so the optimiser is right to want it; the only thing that should stop it is house load eating the discharge — an export that never reaches the grid is `load_yesterday` too low, not double counting. Family: #3325, #5122, #2687, #4942/#5887; they point at modelling free-event load as its own series. (GH#6202)
- **"Battery charges to full before peak solar and then PV is clipped"** — an unwritten headroom preference: Predbat schedules only *grid* charge windows, so the SoC rise through PV hours is the inverter putting DC surplus into the battery. Its only clipping levers are the export plan (`freeze` holds the battery while PV goes to grid, `target` discharges to a level), and nothing prices headroom against *forecast* PV above the cap — that ask is GH#4865 (with #1206; #5460 is a dup). Do not promise zero clipping when `export_limit` equals `inverter_limit`. **The clipped total is modelled for every scenario but never returned**: `run_prediction()` accumulates it but the return tuple has no clipped field, and `predict_clipped_best` is written only under `enable_save_stats` in a `save`/debug run — a clipping-aware metric needs the total added at both ends and on the batch path. `kernel_supported()` refuses `save` runs, so saved-plan clipping figures always come from Python. (GH#6193, GH#6205)
- **"Stop exporting below Xp" is a margin gate, not a price floor** — `metric_min_improvement_export` requires a window to beat *not* doing it by that many pence per interval. Partial power exists via `set_export_low_power` and `LOW_EXPORT_POWER_LEVELS` (0.7/0.5/0.3); what is missing is a price-linked rule to pick the rung. (GH#6172)
- **Exports at the peak then imports all evening ("never sells above my buy price")** — sell is weighed against the refill price, not the concurrent import price; `best_soc_keep` handles the tail and `best_soc_min` binds only in export windows. Answer with `export_peak × (1 − discharge_loss) − import_peak`: negative → suspect the fixed #5566 mechanism; positive → the plan is behaving as designed, so answer with the levers (`best_soc_keep`, `best_soc_keep_weight`, `metric_battery_cycle`). (GH#5509, GH#5566, GH#5579, GH#5866)

### Car charging and Intelligent dispatch

- **IOG: the battery charges at the back of a long, equally cheap dispatch, or the limit flaps tick to tick** — placement is metric-neutral. Since PR #5635 `io_confirmed_credit_update()` adds a small score-only early credit in a confirmed run, and since PR #5896 PV10's dispatch-gone hedge is skipped for those minutes in both engines. - **IOG: "Hold for car" with Self-Use and the house battery not charging in an early cheap slot** — check the version: before PR #5635 the planner scored charging inside a live dispatch the same as waiting for the fixed off-peak window. - **IOG: the battery charges cheaply for the first minutes of a dispatch that started the moment it was published** — `octopus_surplus_from()` withholds only from the next half hour. Umbrella #4516 open. (GH#5424)
- **Plan won't use Intelligent dispatch windows, and `pv_metric10_weight` alone toggles it** — PV10's `dispatch_gone` rule prices `io_adjusted` minutes after the first 30 at `max(rate_max, import)`. Gate the kernel's `io_flag` too or `test_kernel_parity` fails. (GH#5540)
- **Predbat charged the car at peak rate** — before PR #5251 `car_charging_plan_smart` defaulted false. A saving-session reward on the import rate can drop that hour from `low_rates`. (GH#2716)
- **A short dispatch, the car never charged in it, and the battery charged through it at day rate** — short dispatches structurally cannot reach a dynamic-load cancel verdict: load-path evidence needs the whole PREDICT_STEP window inside the dispatch, and once the verdict cycle falls at/after the dispatch end the expired dispatch drops out. (GH#5914)
- **Repeating `Warn: Out of range index N within item car_charging_planned`** — fewer charger entries than `num_cars`; keep a fix car-arg-scoped. PR #4928 open. (GH#5783)

EDF/Kraken's `..._intelligent_dispatching` is on only while the provider dispatches, and EDF dispatches in ~10-minute bursts, so each burst arms the hold. The hold lasts as long as the sensor is on (no timer), is discharge-only, and on an inverter without `inv_has_timed_pause` is deferred while charging. The only lever is `car_charging_from_battery: on`. (GH#6150)
- **EDF/Kraken smart-plan data collapses mid-session** — the merged smart slot to the ready time can vanish while the car is still charging, taking the evening rate overlay with it. Same family as #5686. (GH#6150)
- **Battery idle ("Hold for car") while the car charges from grid** — expected; since PR #5470 a charging inverter is left alone. (GH#4572, GH#5419)

- **`Regular expression ... unable to match ... now will disable` on `octopus_ready_time` + `octopus_charge_limit` with Ohme** — configuration, not a bug: the Octopus integration creates no charge-target entity for an Ohme device, so Predbat disabling them is correct. ### Inverter control and writes

- **Export start time rewritten to "now" every cycle of a running export** — the overlap guard after `Include original export start` counted an empty charge window, or one starting as the export ends, as an overlap. Fixed in PR #6005.
- **Inverter setting not applied** — follow `execute.py` into the component's reconcile loop, and check `read_only`.
- **A parallel master/slave pair gets every control written twice** — nothing suppresses writes to a non-first unit, and the two helpers differ: numeric writes read back and skip, while `write_and_poll_option` writes even when the entity matches. Silencing the slave alone halves the delivered power (#5556): either one virtual inverter (Sunsynk) or suppress the slave *and* write the group total to the master (the Solis `solis_parallel_slaves` pattern). (GH#6169)
- **"Predbat writes my timed entities although apps.yaml sets `set_charge_window: false`"** — that key and `set_discharge_window` are dead config (in neither `CONFIG_ITEMS` nor `APPS_SCHEMA`). Runtime gates come only from the mode select. The `*_service` paths are gated on `set_soc_enable`, so **Control SOC only leaves the inverter's own windows alone and still drives a service-controlled one** — except `reset_inverter()`, which writes both sides. `has_time_window` is likewise unread. (#6069, docs PR #6073)
- **A mapped time entity is written 00:00–00:00 with no window planned** — on `has_charge_enable_time: false`, `scheduled_charge_enable` defaults to **on**, so `disable_charge_window()` calls `adjust_charge_window(midnight, midnight)`; the discharge twin is `adjust_force_export(False)`'s midnight disable. On a real register-backed entity it closes a standing window (a SolaX mode-8 site loses house supply). (#6073)
- **Battery charges to 100% at start, on a mode change or on `set_read_only`** — `reset_inverter()` writes `adjust_battery_target(100.0, False)`, a real order where that register is a floor, on any `reset_inverter: True` change including startup, even in Read-Only.
- **`Note: Inverter does not support charge/discharge freeze - disabled` despite the flag** — capability flags are `INVERTER_DEF` values in the `inverter:` block (a custom type copies `GE`); `has_service_api` does not exist and `has_rest_api` is never read. None of these keys is in `APPS_SCHEMA` or read by `get_arg()`, so the same flag at `pred_bat:` level is ignored — `templates/tesla_powerwall.yaml` ships that inert `charge_control_immediate` (PR #6114 open would warn). (GH#1406, GH#5066, GH#5203, GH#6113)
- **`No entity_id for scheduled_charge_enable ... to write` / `No entity_id for inverter_mode`** — presence flags with no bound entity; custom types inherit GE's `has_charge_enable_time: True` / `has_ge_inverter_mode`. (GH#5539)
- **Reserve ratchets up and never returns (`Increasing set_reserve_min from X% ...`)** — a one-way raise in `refresh_config()`; bound to a live entity it read back Predbat's own reserve write, and a hold writes the current SoC (8%→97% in one night). Fixed in PR #6137: a `battery_min_soc` naming any inverter's reserve entity is treated as unset — but an already-raised value must be lowered by hand. (GH#4013, GH#5232) **"Predbat always sets the reserve to target + 1"** is the hold-on-reserve path. (GH#5660)
- **Hundreds of `Trying to write N to X didn't complete got M` overnight** — idle cycles rewrite rates to max and `write_and_poll_value()` has no failure dedup, so a refused register repeats every cycle. SolarEdge `Connection to inverter ID N failed` is the HA integration. (GH#5073, GH#5324)
- **Every charge/export window runs ~N minutes late** — the inverter's clock; compensate with `inverter_clock_skew_*`. `check_clock_skew()` warns hourly at ≥5 minutes. (GH#4927)
- **GivEnergy-mode discharge times appear in the portal only once the window starts** — `adjust_force_export()` nulls start/end when `inv_has_ge_inverter_mode and not force_export`. The 30 s `Sleeping (workaround)` settle runs inside `adjust_inverter_mode(changed_start_end=...)`, so on a `*_service` install it also delays `discharge_start_service` by 30 s and can delay full rate ~10 minutes; it fires only when the window times were rewritten, never on a bare enable flip, and the charge path never reaches it. Draft PR #6337 would make it the `inverter:` option `discharge_window_service_write_delay` (default 30, 0 skips). (GH#2649, GH#4180)
- **Charge or discharge rate pinned far below the hardware's** — check the component's auto-config rate binding first (GE Cloud, Fox, Solis: their notes); compare `battery_rate_max_raw`/`soc_max` in the dump with the nameplate. The only raise lever is `battery_rate_max_scaling[_discharge]`; `inverter_limit_override` is another cap, never a raise, and it also caps **export** (`refresh_config()` mins it into both directions, then `inverter_limit_export` defaults to the capped discharge), and the per-direction manual-API overrides are read before it (GH#6170). CONFIG_API_OVERRIDE does not reach a component's `set_arg` binding. (GH#4908, GH#4919, GH#4940, GH#5938)
- **Low power computes the right rate but a service-driven inverter still charges at full power, or `{power}` is one cycle behind** — with `output_charge_control: "power"` there is no dummy `charge_rate`, so `{power}` was `battery_rate_max_raw`. Since PR #5149 the rates are written by `apply_rate_intent()` after the per-inverter loop, while the immediate calls built `{power}` before it. **Fixed in PR #5373:** where a service sends `{power}` (`services_send_power()`), calls are queued and made after `apply_rate_intent()`; a "power" inverter with no rate entity holds the rate Predbat last set (per direction, 5% deadband, any move to/from 0 is a change). (GH#5182, GH#5252, GH#3311)
- **Monitor mode is not read-only** — the mode select sets only the windows/SoC flags; `set_read_only` is a separate switch, so with `set_freeze_export_during_demand` a plan-free Monitor mode still writes a pause-charge plus rate-0. A control-mode pause is also not released by switching to Monitor. (GH#5856)
- **Inverter service calls stopped, or re-sent every cycle** — `Calling service` with no effect is an HA rejection; `Skipped service ... as it was previously called` is dedup keyed by domain alone, so two inverters on one domain re-call. A rejected call is dropped and reissued; an accepted call that died downstream was recorded as done. The hash is recorded only after every template call was accepted, keys the last accepted call per domain, is computed from `data`, and a freeze call passes `target_soc` = the live SoC, so every 1% tick makes a new hash. Grep the template for `repeat:`/`always:`. (PR #6124; GH#5021, GH#5627, GH#5888, open)
- **Solar Assistant: charge windows planned but ignored / drained through (SA Growatt SPH)** — the work-mode select is the operative control and SA firmware clears the TOU slot registers 0.4–0.9 s after a mode write, so slots alone control nothing. SA republishes cleared slots as `00:00`/`23:59` with enable off, and the read path accepts that pair as a live full-day window (`start == end` is the only disable test). A fix must re-send/verify the mode, not the slots. (GH#5951)
- **Solis: no charge or export since a pod restart, `Failed to verify CID 636` (2 lower), errors naming `cid 103`** — a timed-out CID 6798 read left a TOU V2 inverter treated as V1; fixed in PR #5864. **Sigenergy: MQTT `published` but commands do nothing** — run `sigenergy.py --command-test --command-mode idle`.

### Rates, costs and savings

- **`cost_today` steps up after each half hour of an Intelligent car charge and falls back later** — `today_cost()` re-prices a running dispatch before `completedDispatches` lists it; `octopus_held_update()` bridges it. (GH#5520)
- **The half hour under a running Intelligent dispatch stays at the peak rate while the car charges** — `started_dispatches` is read but never priced; the `Dispatch timeline car N @ ...` line proves whether the entity listed it. (GH#5773)
- **Rates read zero, or `No Octopus data in sensor ... attribute 'rates'`** — `fetch_octopus_rates()` reads only `rates`/`raw_today`/`prices` (plus `raw_tomorrow` for non-Octopus entities). Keys: `rate`, `value_inc_vat`, `start`/`end` (×100), `value`, `price`/`from`/`till`. (GH#5676)
- With a saving session or Axle event in the forecast, `rate_max`/`rate_average` stay event-boosted by design; `rate_minmax_excluding_saving()` keeps the low-rate classification clear of them. (GH#5050)
- **"Plan has continual charge slots to 100% through the peak" on a tariff whose export max beats the import max** — with `rate_low_threshold: 0`, `set_rate_thresholds()` widens the import threshold to `rate_max + 0.1` when the export max beats the import max (also with alerts or manual keeps): the `Low import rate windows` filter becomes a no-op and buy-at-any-price/sell-at-the-peak is what the optimiser rationally plans. Fingerprint: `Rate thresholds ... import <rate_max+0.1>` with every slot in the low list. Workarounds: a non-zero `rate_low_threshold`, `set_export_freeze`, or more keep/`metric_battery_cycle`. (GH#5990)
- **Today's cost over-costs every car-charging slot by roughly car kWh × rate** — with `car_energy_reported_load` off, `car_outside_clamp_energy()` already prices the car from `car_charging_energy` at each minute's rate, so a smart-meter `import_today` that also sees the car counts it twice. (GH#6149)
- **Guidance for one setting lives in three places** — the docs page, a comment in `automatic_config()`, and the template/regex. A behaviour change that flips which setup users should choose must be grepped in all three.
- **Import cost far above the bill on a 3-phase site with per-phase sensors** — `minute_data_import_export()`/`minute_data_load()` sum phases instead of netting, double counting cross-phase offsets (plan unaffected). (GH#5746, GH#4856)
- **`cost_yesterday` uses today's rates for yesterday on a dynamic tariff** — `rate_replicate()` back-fills negative minutes with today's same-time rate; the live plan is unaffected. (GH#5194, open)
- **`cost_yesterday` / savings show the wrong day after a clock change** — fixed in PR #6084. (GH#5760)
- **An old History day still shows "(import, export not billed yet)"** — billing stops re-reading a local day once it is `BILLING_SETTLE_DAYS` (5) old, however incomplete. `_parse_node()` also drops a half hour whose bucket kWh do not sum to the metered kWh. With an export meter, a row whose import leg is billed and export leg is not is flagged `billing_pending_export`. (GH#6009/#5926)
- **The Billed/Diff columns and Happy-Hour marks vanish on `plan_interval_minutes: 15`** — `attach_billing()` returns before adding any billing field when the interval is not a multiple of 30, with no warning, and the docs tell 15-minute users to set exactly that. (PR #6116 review)
- **History's Billed column shows a car-dispatch evening at Home Standard Rate, but the app shows EV Low Rate** — Kraken first publishes it under `Home Standard Rate`, then re-rates the same half-hours a day or so later. A complete day is now read again once per local day until it settles at `BILLING_SETTLE_DAYS`, so a late re-price shows the next day. Predbat's own cost is unaffected — check `predbat.rates` and `cost_today_car` first. (GH#6252/#6274, PR #6275)
- **"I can only override one plan slot at a time"** — by design. Batch with `rates_import_override`/`rates_export_override` or the manual API. (GH#5289)

- **The Energy dashboard refuses a Predbat daily energy sensor** — HA accepts only `state_class` `total` or `total_increasing`; Predbat's counters reset at midnight, which `total_increasing` reads as a new meter cycle and `total` without `last_reset` counts as negative. - **`The unit of sensor.X (None) cannot be converted to the unit of previously compiled statistics (°C)`** — a numeric state with no unit meeting compiled metadata that has one. No current Predbat path produces it. (GH#6093)
- **A live window stops mid-slot after `Dynamic load last period 9.60kW, status high`** — `load_last_period` came from a coarse counter; since PR #5851 "high" must be confirmed by `load_power` (fail-open). (GH#5851)

## Traps when investigating

### Versions, logs and attachments

- **Version drift.** Compare the log's version with `git tag --contains <sha>` (fetch tags first); many reports are fixed on main, and `v9.0.1` is `v8.55.1`. Treat "worked on 9.x, broke on 9.y" as a version question: `git show vX:<file>` before accepting a regression (GH#5390).
- **A tester's `AttributeError: ... has no attribute ...` after copying PR files over a release** — a partial copy leaves a new file calling a method only another PR file adds. `git grep` the exact source line against the PR's old SHAs and its head; `git diff --stat <release-tag> origin/main -- <files>` shows which files can be copied alone. (PR #6165)
- **An HA notification quoting `Source: custom_components/<integration>/...:<line>` pins a third-party release**: fetch that file at each upstream tag and match the line number. On #6059 line 3026 matched solax-modbus `2026.10.02` while main was at 3064.
- **Tracebacks showing `/config/hass.py`** — the add-on flattens `apps/predbat/*` into `/config`, so line numbers match the released tag, not main. The download is gated on `/config/apps.yaml` being absent, so reinstalling does not refresh stale runtime files. (GH#5869) A `bad marshal data` at aiohttp import is corrupt bytecode in the locally built container, before any Predbat code.
- **A `predbat.log` spans versions and restarts.** Count restarts by `Loading apps.yaml` → `Predbat: Startup predbat`. A restart without `Predbat terminating` was an outside kill; the wrapper's line is `Shutdown, sleeping 20 seconds before restarting` (GH#5886).
- **`Best charge window` is the prefilled incumbent, not the optimised plan**, which is in the later `Raw/Filtered charge windows` lines. In a repeated pair in one tick the later line is the recompute.
- **Prove an attached dump is the reporter's own** (compare `soc_kw` and serials at its capture minute with their log); once proven it beats the issue prose. Numbered logs are overlapping snapshots, not rotation order; two attached dumps can be byte-identical. A new attachment URL can 404 for 10+ minutes; the HA Companion webview ignores `Content-Disposition: attachment`.
- **Evidence on Google Drive cannot be fetched by tooling** (npz files): ask for a GitHub-hosted attachment. **A screenshot when `curl` is denied**: WebFetch the `user-attachments/assets/<id>` URL (GitHub 302s to a signed URL expiring in ~5 min), WebFetch *that*, then Read the saved `tool-results` file — the Read is what renders it. `user-attachments/files/<id>` downloads with plain `curl -L`.
- **HA entity-history CSV exports cannot prove write provenance** — context ids are unreliable. Attribute by value + timestamp against `predbat.log`'s `Wrote X to Y successfully`/`Calling service` lines. (GH#5951)
- **Routine `Warn:` lines are the cause only if their timing matches.** HA core's `Referenced entities ... are missing` is **not** a startup race: Predbat's entities are state-only, so every control write logs it and the write lands through Predbat's own `call_service` event. Fixed for Predbat-published controls in PR #6230 (see *HA write/verify*); on an older log it is log noise. (GH#5420 was closed on an unsound theory.)
- **Log severity is read by two consumers** — the console prints a quiet line only when the prefix starts with error/warn/info, while `classify_log_line()` is substring, so "warn"/"error" anywhere lands in the web Warnings tab. De-noise a repeating warn by switching it to Info (PR #5841).
- **A quoted "Predbat did not react until ..." timestamp is usually the latest repeat of a per-cycle line.** `Car N is charging now outside its plan`, `Current SoC X% is less than Target SoC Y`, `operation_mode = ...` and `Completed run status` re-log every cycle. Grep for **every** occurrence and anchor on the first.
- **Hardware behaviour needs the hardware.** A unit test shows what the code does, not what the inverter did.
- **A flat SoC is not necessarily a stall.** One percent can be ~10 minutes at 2 kW on a large pack.
- **Check that the report's premise exists.** Reports have cited AI-invented settings (GH#4918), features only on unmerged PRs (GH#4917), history `git log -S` disproves (GH#5022) and false "expert gated" claims (GH#5237). Grep `config.py`/`APPS_SCHEMA`, read each item's `enable:`, and check a proposal's symbols are on main.

### Replays and debug dumps

- **Copy `manifest.yaml` into a new worktree before running anything.** It is gitignored and *generated* from the release file list — a new module needs no entry, and a working-tree copy is whatever release was last downloaded. Without it `check_install()` downloads the release over tracked files and exits. Recover: `git checkout -- .`, `git clean -fd apps/predbat`. **A/B across versions by checking out the old tag in place** (`git worktree add` is denied under triage permissions).
- **Replay-probe pitfalls.** The window list holds both days in one minute-of-day frame, so filter `1140 <= start < 1440`. `Prediction.__init__` copies SoC, rates and ~200 other attributes from `base`, so set them first or rebuild it.
- **A dump's `now_utc:` can carry a YAML anchor**, so `now_utc` and `plan_last_updated` alias (`&id002`/`*id002`). Allow an optional `&idNNN` after `key:` in text regexes, or parse with `yaml.safe_load`; never infer "not a dump" from a regex miss — check for `debug_schema_version`/`CONFIG_ITEMS`.
- **A log stamp and a dump's `now_utc` are different clocks** — logs carry the host's naive local wall clock, while `now_utc` is aware in Predbat's configured `timezone`. Compare the `minutes now` each run line records, or apply the offset.
- **`pv_forecast_minute`/`10`/`90` are keyed by absolute minute of day; `..._step` by minutes from now.** A replay helper indexing the raw dict with `range(start - minutes_now, ...)` samples a different time of day, and `.get(minute, 0.0)` hides it.
- **A dump-restored inverter does *not* lack attributes added since the dump was written** — `read_debug_yaml()` deep-copies the live `self.inverters[0]` and overlays only the dump's keys, so anything added since keeps its `_init_attribute_defaults()` value. PredBat itself is freshly constructed and overlaid, never pruned. So a `getattr(obj, "<setting>", default)` justified by "an old dump has no such attribute" is dead code and hides typos — initialising in `__init__`/`reset()` is enough (the maintainer rules forbid the defensive form). (GH#6194, verified 2026-11-22)
- `charge_rate_now`/`discharge_rate_now` exist only after the first `update_status()` and are floored to `battery_rate_min` immediately after, so capture the raw read first — a nonzero `inverter_battery_rate_min` defeats the balancer's `== 0` held-gate (GH#5927).
- **`self.predict_soc` after a trial run holds the nominal scenario**; its keys stop at `forecast_minutes − 5`. **Simulated SoC RMS cannot tune battery settings**: a changed loss or rate changes the plan too.
- **Ad-hoc replay under the triage permission mode.** Env-var prefixes break the allowlist: add a temporary probe to `run_debug_cases()`, gated on a marker file, and revert it. Plan pass lines go to `coverage/predbat.log`.
- **Golden plans move with load scaling.** Regenerate `coverage/cases/*.expected.json` via `./run_random`; `debug_cases` stops at the first failure. Only the four window/limit arrays are compared, so a PR that adds plan-JSON fields needs no regeneration.
- **A forward replay drifts from live** on logs without `Replay input:` lines, and where live re-planned twice in one run. Multi-inverter SoC is the sum of each inverter's SoC line.
- **`Will recompute the plan as it is invalid` is logged on every recompute**; only `Recompute, previous plan is invalid...` means it was. The 8-hourly config refresh adds an extra run.
- **The dump's rate tables sit back-to-back with no separator**: a line-range read across an unanchored end mixes tables — grep the exact bounds of each `^rate_` key.
- **The per-candidate export metric table needs no instrumentation.** A `TEST_REGISTRY` entry calling `run_single_debug(..., debug=True, redo=True)` puts `Try optimising export window(s) N` lines (each with a window→[metric, cost] map) in `coverage/predbat.log`. **On a money-losing-plan ticket read the dump's `plan_preclip` first.** `--redo` overwrites edits of `high_export_rates`; replay no-export by flipping `calculate_best_export`/`set_export_window` and emptying `export_window:`.
- **A dump carries two config sources; only one is live.** The flat sorted args below the rate tables is what a replay reads — edit those; the CONFIG_ITEMS `value:` fields feed only the "changed items" printout. `predbat.plan_html` inside `dashboard_values` carries the projected plan table, whose Totals column settles "does the model think this wins" without a replay.
- An attached `apps_live_masked.yaml.txt` is the `/debug_apps_live` dump — `self.args` as that run resolved them — so it shows which entity each arg really bound to.

### Tests and the C++ kernel

- **Do not rebuild the kernel binaries while triaging**: they are committed and CI-built. A `scan_soc_range` count of 0 over a full plan means the kernel served it. After a `.cpp` edit delete the local `prediction_kernel_lib.so`. The verify script is `apps/predbat/verify_kernel_binary.py`, and `pk_parity_revision()` against `KERNEL_PARITY_REVISION` makes a stale `.so` fall back loudly.
- **Python `struct`'s native `@` format is not a C-layout mirror** — it pads interior fields but not the tail (`calcsize("@ic")` is 5 where C lays out 8). `prediction_kernel.py` derives each format from `_fields_` and compares struct size **and every field offset** against ctypes, falling back to field-by-field writes. Copy that pattern. (PR #6111)
- **A standalone `import config` probe dies with `cannot import name 'APPS_SCHEMA'`** — `config` and `predbat` import each other. In an ad-hoc probe `import predbat` first.
- **New kernel context arrays need `ContextStore` copies** (the ctypes buffers are freed); a missing copy dangles silently, giving wrong values, not a crash.
- **An `HAInterface.call_service()` change reads green while nothing tests it** — `create_predbat()` wires `TestHAInterface`, a standalone simulation (plain class, implements `call_service` itself), so the component and inverter tests never run the real method; only the `hainterface_*` tests bind the real `HAInterface` to `tests/test_hainterface_common.MockBase`, whose attribute list must cover everything the method reads. Fix the double rather than adding `getattr(self.base, ...)` guards. (PR #6230 review)
- **An `inverter:` block in a test mutates the shared `INVERTER_DEF` row** — a custom type gets a copy of GE, a built-in type has its row mutated in place, so a key one test sets survives into the next `Inverter()` of that type. Use a unique custom type name, `INVERTER_DEF.pop()` it in a `finally` (as `test_custom_inverter_def_drops_rate_step` does), and never put an `inverter:` block on type `GE`. (PR #6337 review)
- **Kernel and Python can choose equal-scoring but different plans.** The kernel ignores the levels pass's `step=30` fast mode and returns scalars pre-rounded to 4dp, so differences above 4dp are expected.
- **Export instructions are `(mode, target, power)` tuples with a permanent legacy decode of bare numbers** (99.0 freeze, ≥100 idle). Unit tests usually feed bare floats, so pin both forms. (GH#5997)
- **`--test <name>` resolves through `TEST_REGISTRY`, not file names**; a wrong name gives a green run with zero assertions (GH#5407). **The suite aborts at the first failure**, so one FAIL proves nothing about later tests.
- **CI got slow: read the step timings before the tests.** `gh run view <id> --json jobs` gives per-step times. A YAML parse or dump runs at ~1 s per MB; look for one repeated in a loop. Walk `sys._getframe()` instead of `inspect.stack()`.
- **A test that reaches a vendor API passes anyway, and can take minutes** (real sleeps on retry). `tests/network_guard.py` fails any non-loopback DNS lookup or connect, naming both lines.
- **Skips can count as passes.** `run_nordpool_test()` returns False (pass) on a download failure, and CI installs only `requirements.txt`, so `if have_<pkg>:` gates run only their skip path.
- **Tests that fail only in one dev container** — check the interpreter and `jq` first. Sigenergy's `asyncio.all_tasks()` assertions need Python ≥3.12, and the owner-gate tests need jq ≥1.7 (main pins 3.12 and 1.7.1 since PR #6090).
- **A test that starts a real web component must stop it on the failure path too**, or `unit_test.py` never exits and the runner times out (exit 143). Stop it in a `finally`.
- **A passing test proves nothing when the fixture encodes the bug.** Seen: flat-rate fixtures, identical inverters, zero-iteration loops, `json_body or {}`; a log-grep "not called" check is vacuous if the method is a stub — use a calls counter. `TestHAInterface.get_state` returns `""`, not `default`, for a missing attribute; window asserts must check `start < end`; address-reuse guards assert the object is pinned (`gc.get_referrers()`).
- **Stub and double shapes.** `Execute.__new__` stubs lack base methods. Prefer `Cls.__new__` plus explicit `base`/`log`/`prefix`/`args` over `ComponentBase.__init__` (which aliases the live `base.args`). A MagicMock `self.base` passes `getattr(base, hook, None) is not None`, so set `base.<hook> = None`. A mock that skips `ComponentBase.__init__` must set `self.base` once it reports discovery, or the AttributeError is swallowed into a "failed to report discovery" warn (PR #5936).
- **`self.base.set_read_only` is `True` until the first `update_pred()`**; read `get_arg("set_read_only")`. The charger mixin and wallbox were fixed; `gecloud.py` and `gateway.py` still read the attribute first.
- **`run_execute_test()` scenarios inherit fleet state from the previous one.** `total_inverters` is whatever the last scenario left, and the `reserve=` kwarg is fleet-total kWh divided by that count. Work out the member count and which branch writes the target.
- **Car-slot dicts handed to Predbat are mutated in place; the deep copy in `calculate_yesterday()` is a backup, not a shield.** Writers: `yesterday_reconstruct_car_slots()` and `dynamic_load_car_check()`.
- **`test_prune_dead_slots` stubs `run_prediction_metric`**, so it never checks that the simulator scores a dead slot the same as off.
- **A component billing test against the real `my_predbat` must pin `plan_random_delay = 0`**, or `BillingReader` arms a random 0–30 minute hold-back and `queries` is empty. Copy the pin from `test_octopus_run_publishes_billing`. (GH#6024)
- **`reset_inverter()` (`tests/test_infra.py`) moves the test clock to noon** — set the clocks *after* calling it.
- If PR #5953 lands, car-slot consumption splits into `in_car_slot()` and `car_slot_average()`, so a semantics change must land in both Python sites plus the C++ kernel.

### Clocks and time

- **`midnight_utc` and `now_utc` are local time**, in `ComponentBase` and `now_utc_exact` too. Use `.astimezone(timezone.utc)` before a `Z` suffix or an API window, then test with a BST date (GH#5572, GH#5693). `time_abs_str()` prints local time.
- **A "the clock moved back" guard built on `now_utc` deltas can never fire on a DST change** — `now_utc` is an aware absolute instant, so `now_utc + timedelta(...)` compared against `now_utc` is DST-proof by construction and only catches a *host* clock jump (NTP sync, VM restore), whatever it is named. A changeover instead shows a wall-clock value (`minutes_now`) disagreeing with an elapsed one; the fix shape is the offset difference, `minutes_now - minutes_ago + (offset_then - offset_now)`, as the PV calibration scan does per minute. Applies to any poll/rescan interval stored as `now_utc + timedelta`. (PR #6233)
- **Build test dates from Predbat's clock**: anchor to `my_predbat.midnight_utc` and pin both clocks. Storage-cache expiry is the exception (real clock). `ComponentBase.midnight_utc` re-reads `base.now_utc`, so a `__new__` fixture with a MagicMock base can replace the clock after construction.
- **`multi_car_iog_load_slots_regression` fails in the first ~11 minutes after local midnight** — it expects minute 0 in `octopus_cap_idle`, but `octopus_cap_idle_load()` settles the record at `now_utc_real - OCTOPUS_CAP_LAG_MINUTES` (2 × `PREDICT_STEP` = 10) and takes whole minutes up to the floor, so minute 0 only enters once real now is past 00:11; the set came back `-720..-1`. Not a code bug: re-run later, or pin `now_utc_real` in the test. (verified 2026-11-24 at 00:10, which is when the nightly run hits it)
- **The quick suite fails 00:00–01:00 local in summer**: the teslemetry weekday test raises and aborts the run, and `test_solax.py`'s month test fails. A test that hardcodes a calendar date turns the suite red from that date whatever the code does. The mechanism is that `create_predbat()` pins `now_utc` to **noon of the real day** (`FIXTURE_MINUTES_NOW`), so a stub carrying absolute dates slides into the past on a known date and never recovers — retrying is pointless. Fix shape (PR #6245): pin `my_predbat.now_utc` in the test to a fixed instant just before the stub's boundary, keeping the pin's time of day equal to `FIXTURE_MINUTES_NOW`, and restore it in a `finally`. (GH#6244)
- **`minutes_now = 0` hides time-of-day bugs.** A pin-guard test is vacuous when the pin equals the residue.
- **`timedelta.seconds` wraps into [0, 86399].** Use `abs((a - b).total_seconds())` (button-press site fixed in PR #5697).
- **`strptime_aware()` raises on missing tzinfo**, so a `%z` site's naive handling is dead, and a bare `.replace(tzinfo=...)` is a no-op.
- **CI's `python-version: 3.x` resolves to different CPythons per runner**; check `Successfully set up CPython` in the job log.
- **`HAHistory` lags up to 2 minutes, and smoothing back-fills the gap**, so moving a marker to now loses the tail; count only the uncounted delta.

### Reading the code

- **`getattr(component, "x", default)` is justified only for an attribute set in a later periodic method.** `ComponentBase.__init__` calls the subclass's `initialize()` during construction, so anything set there always exists on a component the registry returns (as do `base.components`/`local_tz`/`prefix`); a page defaulting one of those hides only a typo. Initialise the genuinely lazy one to its "not run yet" value in `initialize()` instead. (PR #6231 review)
- **`self.base.args` holds Predbat's own dummy entity ids.** Use `user_configured_entity()` (PR #4745). Inverter objects persist and `refresh_config()` re-reads config every cycle.
- **`inverter_source_active()` is fleet-wide**, and `create_missing_arg()` pads with `None`.
- **`re:` arg values are full-matched `^...$`**; with capture groups the value is replaced by group 1 — why templates wrap patterns as `re:( ... )`. On a list or dict arg the outer `matched` comes back `True` unconditionally, so indexing `[0]` is a vacuous match check in tests. (GH#5931)
- **A template `re:` slug group must absorb the whole device name** — `[a-z0-9]` excludes `_`, so `(_[a-z0-9]{2}[a-z0-9]{1,6})?` in `templates/solis_local.yaml` cannot match `sensor.solis_s6_eh1p_...`. Symptom is `unable to match ... now will disable` plus `load_today` disabled. PR #6088 fixes it; nothing loads every template.
- **Sign conventions.** `grid_power` is negative on import; `battery_power` is positive while discharging. Find out which convention a sign report assumes.
- **Throwaway event loops in component events.** `select_event`/`switch_event` presses run under `asyncio.run` on a fresh loop, which breaks a persistent `aiohttp.ClientSession` or `asyncio.Lock`; use `run_coroutine_threadsafe`.
- **Two loops over one slot.** A `TypeError` against `None` deep in the plan often means two loops drifted apart.

### Docs

- **Docs yaml fences are unvalidated.** Extract each fence and `yaml.safe_load` it; mis-indented `variables:` keys parse silently. `git blame` the fence and suspect wide re-indent commits (GH#5479).
- **The kernel parity contract is hand-synced across three homes** — the `developing.md` kernel section, the `apps-yaml.md` notes and the `kernel_parity` docstring. Grep both pages for `bit-for-bit` and `1e-6` whenever the contract moves.
- **`docs/apps-yaml.md` documents each setting twice**: a key bullet and a `### <Display Name>` section. `### Inverter reserve maximum` still says "the default is 98" (PR #5644).
- **Docs lists of feed-in-first inverters drift from the code's opt-in set, with nothing failing when they do.** `INVERTER_DEF`'s `support_feedin_first` plus `test_support_feedin_first_is_opt_in` (seven types, including `GS_fb00`) are canonical; the apps-yaml and inverter-setup lists still name six and omit `GS_fb00`. Recount against the test before repeating the list. (PR #6200 review)
- **Some docs entities live in HA core.** `binary_sensor.predbat_running` is the Supervisor's per-add-on sensor, disabled by default.
- **Inverter templates.** An unknown `inverter_type` needs no code. `battery_min_soc` reaches the plan only through the reserve chain. With no freeze service, `freeze=True` falls back to `discharge_stop_service`. A `template:` sensor's entity id comes from `name:`. Check `mdi:` names against the SVG repo.

### Reviewing PRs

- **A clean auto-merge can still be a semantic conflict.** Run the full `run_pre_commit`.
- **Check base staleness first.** The fix may already be on main, and resolving a test conflict can delete main's test.
- **Read a PR's scaffolding against `origin/main`, not the PR's own base.** A PR cut from an old base can show `components.py` entries as class objects with top-level imports, apparently contradicting CLAUDE.md's lazy-import rule; main holds `"module.ClassName"` strings. Check `git merge-base origin/main HEAD` first. (PR #6034)
- **A new test file that imports `pytest` is doubly dead.** The `TEST_REGISTRY` loop imports every registered module at startup; `pytest` is not installed, so registering one breaks the **entire** suite, and its bare `test_*` functions would never run. Expect a `run_<feature>_tests(my_predbat=None)` wrapper and a registry entry.
- **Stacked-PR squashes.** A `(#M)` suffix means the diff spans both PRs. A stacked PR shows MERGED when the squash lands on its base, with a `mergeCommit` not in main; check `git merge-base --is-ancestor <mergeCommit> origin/main`.
- **A review's `commit_id` is the head at submission and never updates.** Compare it to `headRefOid`; a later CHANGES_REQUESTED/DISMISSED supersedes an earlier APPROVED. Bot reviews post as COMMENTED and satisfy no approval gate.
- **Fork PRs can carry pasted truncation banners.** Grep the head tree for `truncated output`, confirming with `grep`, not Read, which adds its own banners.
- **CI runs the quick suite in the `pre-commit` job** with `PREDBAT_KERNEL_REQUIRED=1`, so CI's `--quick` exercises the kernel; the seven slow-tagged tests are its only blind spot (`balance_sim_matrix`, `replay_roundtrip_day`, `plan_preclip`, `annual_integration`, `load_ml`, `ml_training_perf`, `gecloud_api_budget`). A local green `--quick` is kernel coverage only if the kernel actually built and loaded.
- **Docstring coverage (interrogate) and flake8 are enforced nowhere** — CLAUDE.md says "100% coverage required (interrogate)", which misleads reviewers. Missing docstrings are not an enforceable finding.
- **GitNexus is indexed from main.** On a PR branch read `detect_changes()` as "which files", not "which symbols".
- **Re-running `/pr-review` on an unchanged head duplicates the review.** Post a follow-up with `comments: []` instead.

### GitHub and tooling

- **`gh issue list --search` without `--repo` searches all of GitHub.** Always pass `--repo springfall2008/batpred`, and distrust an empty result: fetch the exact title, typos included, and search bare `#N in:body`. Even with `--repo`, an OR'd multi-word query has returned other projects' issues, so search one plain keyword at a time.
- **`gh api` permission rules match literal prefixes.** Put flags after the endpoint. Events come back oldest-first, so `--paginate ... | tail -n 1` is the most recent. `jq` on `--json comments` needs `--jq '.comments | length'`.
- **A shell `grep -E '\s'` sweep returns zero matches on macOS** — BSD ERE has no `\s`, so a bogus pattern looks like a clean tree. Spell whitespace as `[[:space:]]`, or run the Python `re` pattern through `python3 -c`, and treat a zero-match `\s` scan as unverified. (PR #6107)
- **Triage permission-mode routes.** Read a branch doc with `git fetch` plus `git show <branch>:<path>`; for another repo use WebFetch after checking its default branch. Plain `git` from the repo directory only: `-C` and `cd` outside the working dirs are refused. **When `git fetch` is denied, verify the tip over HTTP** — `WebFetch https://api.github.com/repos/<owner>/<repo>/commits/main` returns the real remote sha.
- **Kraken (EDF/E.ON) issues have no component label.** Do not guess `Octopus`.
- **Merge box shows `owner-gate` "Expected — Waiting" though the API says it passed.** The gate posts an `owner-approval` **commit status**, which belongs to no check suite, and its job is named `owner gate evaluator` so its own tick cannot satisfy it; a `GITHUB_TOKEN` check run lands in the *oldest* suite, which the merge box never reads. Read the verdict from `/commits/<sha>/statuses`; an admin merge or a new head clears a stuck PR. The required `pre-commit` context is the `code-quality` workflow's job. Every `labeled` event fires the workflow including the bot's own.
- **`/commits/<sha>/check-runs` defaults to `filter=latest`, hiding duplicate runs** — pass `filter=all`. Check runs live on the sha, not the PR; a force-pushed-away head returns none from `pulls/<n>/commits`, so locate it via a review's `commit_id`. **Repo rulesets are readable without admin**: `gh api repos/springfall2008/batpred/rulesets`.

## What belongs here, and what does not

The journal is for what a future triage run would otherwise have to rediscover. Test every entry with one question: would it save time on a **different** issue?

- **Keep: techniques and traps.** How to replay a dump (`--redo`), test-order pollution, stale kernel binaries. These apply to every investigation.
- **Keep, tightly: durable facts about a device or API.** One line, no story.
- **Keep, short and dated: findings that explain a class of report.** Give the issue or PR number and the date, say how it was verified, and word it as "look here first", so the reader confirms it against the code.
- **Drop: per-issue narrative.** What was tried, what the fix was, why alternatives were rejected — that belongs in the PR and the issue.
- **Drop: file paths and line numbers.** They drift with every merge. Point at a function, a config item or a log line instead. Naming a file is fine when the file is the subject (`apps.yaml`, a template, a test to run).

Write each entry in the same shape: the **symptom** (the log line verbatim, or what the reporter sees), the **fact or mechanism**, and **where to start looking**. Then add the issue or PR number, and the date if it is a bug.

Entries go stale, so retire them:

- When the code an entry describes has changed, correct or delete it. Do not leave it marked as stale.
- Once a fix has shipped, cut the entry down to what a reader holding an older log needs ("fixed in PR #N"). After about six weeks, delete it unless the mechanism is still a trap.
- Prefer sharpening an existing entry over adding a second one.

Keep it small. Every triage, review and journal-update run reads this file end to end, and at 730KB it cost them most of their turns. One fact per bullet, a few hundred characters at most. If an area's notes grow past about 3KB, consolidate them rather than adding more.

## Adding to this file

When an investigation turns up something that passes the test above, add a bullet under the right heading: the area under "Per-integration notes", or the topic under "Symptom → first place to look". Keep it short, name a function or config item rather than a file or line, and cite the issue number so the next reader can check the original.

If you are running under the triage bot you cannot edit this file directly — the clone is `reset --hard` before every flow. Write the finding as a single markdown file in the queue directory named in your system prompt instead; the `/journal-update` flow folds the queue in once a day, re-checking each candidate against current `main` first, and opens a PR for a maintainer to merge.

Whichever route you take, the bar is the same and it is not "interesting": record what you **verified**, say how you verified it, and keep anything you merely suspect explicitly marked as suspected. A wrong entry here is worse than a missing one — every later run trusts this file, so a confident mistake ends up in a comment posted to a real reporter. Correcting or deleting a stale entry counts as much as adding one.
