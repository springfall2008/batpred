# Debug journal

Notes distilled from maintainer debugging sessions and triage-bot runs on this repo (roughly June–September 2026), written for whoever is triaging an issue next.

Every entry is an observation from a past investigation, not a statement about current main. The code moves. Use these as "look here first", confirm against the working tree before you put anything in a comment, and say what you actually confirmed rather than what this file says.

## Replay the reporter's debug file

The most useful attachment on a bug report is `predbat_debug.yaml` — a full state dump the test harness can replay against current main:

```bash
cd coverage
./run_all --debug_file <scratch>/predbat_debug.yaml > <scratch>/replay.log 2>&1
```

What you get out of it:

- **Every config item the reporter has changed from default**, printed as `- <item> = <value> (default <value>)`. Grep the replay log for that block before reading their yaml — it is where most "the plan is wrong" reports get settled.
- A recalculated plan with a metric before and after, written to `plan_orig.html` and `plan_final.json` in `coverage/`. Both are gitignored, and `git clean -fd` clears them.
- `--redo` recomputes rates, load model and Octopus slots instead of reusing the ones in the dump. Without it you are replaying the exact state they had, which is normally what you want.

Committed examples of the same format live in `coverage/cases/*.yaml`; they run as golden regressions under `./run_all --test debug_cases`.

`--debug_file` **without** `--redo` can crash on an older dump with `KeyError: 0` at `prediction.py:769` (GH#4766) — retry with `--redo` before concluding the dump itself is unusable.

Two lines in that output are normal and are not the reporter's bug:

- `Prediction kernel stale binary ... - using Python engine` — the local C++ kernel is older than the Python side expects, so the pure-Python engine runs instead. The plan is still correct, just slower.
- `Config item ... is below the minimum ... - clamping to ...` — routine clamping of an out-of-range setting.

## Debug yaml can contain real secrets

A `predbat_debug.yaml` or debug-history snapshot attached to a bug report can carry live, unredacted credentials. Read it locally; never quote a raw block from one in a public comment without checking it first.

- **The `args_from_apps_yaml` leak is fixed — do not tell a reporter to rotate credentials on the strength of this entry.** For a while both dump paths special-cased only the field literally named `args`, so `self.args_from_apps_yaml` — a second full copy of apps.yaml taken before Predbat's own defaulting, added in PR #4500 — went out unmasked with every `!secret` already resolved, through `create_debug_yaml()`, every rolling debug-history snapshot, and the `get_state` agent/MCP tool. GH#4765 caught a real reporter that way: their debug yaml carried a plaintext `mcp_secret`. PR #4910 (`0c7747e4`) closed it at the source — `predbat.py:1865` is now `self.args_from_apps_yaml = mask_secret_args(self.args)`, so the copy cannot carry a secret however it is later dumped, and both dump paths mask it as well (`userinterface.py:775`, `agent_tools.py:1131`). A debug yaml from **before v8.55.0** can still carry live credentials, so the "read it locally, never quote a raw block" rule below stands regardless of version.
- The masker itself (`mask_secret_args()` / `is_secret_key()`, `utils.py:141-159`) matches `_key`/`password`/`secret`/`token` substrings on top-level keys. Narrower gaps flagged in GH#4757/#4770 (credential-like keys with none of those substrings) and GH#4768 (the MCP `get_apps` tool returning `args` unmasked) have since been closed — confirmed fixed on `main`.
- `debug_history_enable` defaults **True** and captures a snapshot roughly every 3 hours **independently of `switch.predbat_debug_enable`** (`predbat.py:807-820`) — a user who has never turned debug on still has credentials sitting in the rotating `predbat_debug_history.tgz` buffer.
- `annual.py:60`'s `scrub_secrets()` is a properly recursive masker; its docstring's claim to mirror `create_debug_yaml()`'s behaviour is itself wrong (GH#4770) — they mask differently, and `create_debug_yaml()` is the leakier of the two.

## Check configuration before code

"The plan is wrong" has repeatedly turned out to be settings rather than a defect:

- **GH#4222** (odd freeze-export windows) — traced to the reporter's own `combine_export_slots: True` plus a high `metric_min_improvement_export`, not a code regression. A stale local test file also produced a false kernel regression partway through that investigation.
- **GH#4478** (exports scheduled late) — there *was* a real ordering bug (`optimise_swap_export` ran before the later plan passes, fixed in PR #4513), but the user-visible difference was dominated by `best_soc_keep: 4.0` in their config. The commented-out swap call left at the old position in `optimise_all_windows()` can make a reader think the pass is dead - it is not: the live call runs deliberately **last**, after the plan and solar passes that add the near-term exports the swap exists to push back. Read `optimise_all_windows()` end to end before claiming any pass "runs during planning"; symbol presence in `plan.py` is not evidence either way.
- **GH#4840** ("random" exports at peak rate on a flat 12p export tariff) — `metric_battery_value_scaling: 0.9` against the 1.0 default. `compute_metric()` credits leftover SoC at `battery_value_rate()`, which is the *replacement* cost of a stored kWh (cheapest future import grossed up by charge losses). Exporting is profitable to the planner exactly when `export × inverter_loss × battery_loss_discharge` beats that credit, so the protective margin is only `(export realised) / (replacement cost)` — on 10.54p import against 12p export that is `11.174 / 11.319`, i.e. **1.28%**. Any scaling below ~0.987 flips every export decision on a near-parity tariff, and the trade genuinely loses ~0.2p/kWh. Two things made this hard to see: the reporter had also turned off `metric_cloud_enable` (default **True**), so the planner assumed perfectly smooth PV and predicted *zero* grid import for 48h — restoring that default alone also removed the export; and the modelled 48h cost looks ~52p *better* with the export, because the plan simply ends with 4.7kWh less in the battery. Note the slider's step was 0.1 until the PR for #4840 reduced it to 0.01, so the smallest possible nudge below the default used to overshoot the flip point by 7.8x - and 0.02 was not enough either, since 0.98 is still below 0.9872.

- **Three different "keep" mechanisms** get conflated in reports, and only two of them can hold a battery up. `best_soc_keep` is *soft*: purely a cost-model penalty added when predicted `soc <= best_soc_keep` (the `metric_keep +=` line in `prediction.py`), scaled by `best_soc_keep_weight` and ramped in over the first four hours of the horizon. It never creates a charge window and never raises the reserve, so an automation setting it to 3 kWh cannot pin a full 8.64 kWh battery at 100% (GH#4961). `manual_soc_keep` (the web-UI `manual_soc` override) and weather-alert keeps are *hard-ish*: both merge into `all_active_keep`, which forces `keep_minute_scaling` to at least 10.0 - a 10x-import-rate penalty that effectively forbids discharging below the keep percent. `set_reserve_enable` with a high `reserve` is the only true hard floor. Related, because it comes up in the same reports: `set_discharge_during_charge` **defaults True** (`config.py`), and even when it is on, `prediction.py` still pins the discharge rate to `battery_rate_min` while SoC sits within 1% of the window's charge limit. That at-target hold is what `HoldChrg` means, and it is not `FrzChrg` - `is_freeze_charge()` requires the limit's percent to equal `reserve_percent`.

So pull the non-default config list out of the replay first and look at `combine_export_slots`, `metric_min_improvement_export`, `best_soc_keep`, `metric_battery_value_scaling`, `metric_battery_value_export_scaling`, `metric_cloud_enable` and the `load_scaling*` family before concluding "code bug". Saying "this is configuration" is a legitimate triage outcome — that is what the `configuration` label is for.

A cheap way to settle these: replay the debug file once per suspect setting, changing one at a time, and compare the resulting force-export windows rather than the headline cost. The cost column moves for uninteresting reasons (a plan that ends with an emptier battery always looks cheaper), so **compare the plan's decisions, not its metric** — and check a suspect setting is actually non-default before building a theory on it (`best_soc_keep: 0.0` and `metric_battery_value_export_scaling: 0.8` both *are* the defaults, and have each cost a session's time).

Two `get_arg()` boolean traps affect every component boolean arg, and either alone can look like a feature silently not running (both pre-existing and generic, surfaced reviewing PR #4997):

- **An explicit empty value defeats the default.** `key:` with nothing after it is YAML null; `self.args.get(arg, default)` only applies the default when the key is *absent* (`userinterface.py:287`), and `validate_is_boolean()` (`predbat.py:1446`) passes `None` silently — so the component stores `None` and `not value` treats it as off. A default-True flag with `key:` in the yaml is off.
- **A quoted truthy string coerces to False.** `'1'` or `'y'` passes validation (anything `bool()`-able) but the coercion list `['on','true','yes','enabled','enable','connected']` (`userinterface.py:319`) turns it into `False`. Unquoted `1` parses as an int and stays truthy — the trap is specifically quoted strings.

Bool defaults are safe from the int-default truncation pattern (`userinterface.py:307` excludes bool from `int(float())`) — that one (GH#4925) bites component args with float defaults like `solcast_poll_hours: 4.8`. Check both paths first on any "flag silently off" report.

Unknown apps.yaml keys are **silently ignored** — `validate_config()` (`predbat.py:1459`) iterates over `APPS_SCHEMA` checking required-ness and type and never the reverse, so a typo'd or obsolete key produces no diagnostic at all. The nearest thing to a net is `unmatched_args` (`userinterface.py:auto_config`), which only captures args whose `re:` regex matched nothing (GH#4999 is the enhancement request for a warning). If that warning ever gets implemented, the allowlist cannot be `APPS_SCHEMA` alone: component yaml blocks (`octopus:`, `web:`, …) are validated via `COMPONENT_LIST` (`components.py:56`), Predbat injects derived args at runtime via `set_arg()` (so the check must read the startup snapshot `args_from_apps_yaml`, not live `self.args`), and dict-valued schema entries such as `predheat` have un-enumerated inner keys.

Related, sensor-typed config items **reject fixed numeric scalars** (GH#2172, probe-verified): 13 `APPS_SCHEMA` items (`car_charging_battery_size`, `pv_forecast_today`, `car_charging_soc`, ...) are typed `{"type": "sensor"}`, and the `sensor` branch of `validate_config()` wraps a scalar into a list only when it is a *string*, so `77.4` or `100` falls through to the generic `not of type 'sensor'` error while a one-element list (`- 77.4`) passes. Two strings to search on: with `entries` resolving to 1 it is `not of type 'sensor'`; above 1 the pre-dispatch length check fires first and reports `Invalid type, expected list`. Impact is status-only (`arg_errors` zeroes the `config_valid` sensor; the value itself reads fine). Do not fix it by loosening the validator — the obvious wrap-any-scalar patch was rejected on the issue because several sensor-typed items (`pv_forecast_today`, `car_charging_soc`) should never hold a fixed value; the maintainer's direction was to fix the documentation to the list form, and that has now landed for `car_charging_battery_size` (PR #5024, v9.0.2, docs only — the validator still rejects the scalar form, and `docs/car-charging.md` now says to use the list). Start here on any "validator says X should be a sensor but the docs show a fixed value" report.

## The shared clock is rewound for ~0.8s every hour

`calculate_yesterday()` winds `self.midnight_utc` back a day **and zeroes `minutes_now`** on the shared `PredBat` instance while it re-simulates yesterday — the fake is the `# Fake to yesterday state` block, the restore the `# Save state` block, both inside `calculate_yesterday()` (re-anchor on those comments rather than line numbers; the refs have drifted several times). That is roughly 0.8 seconds, once an hour, on an object that other threads read live — components run on genuine OS threads, the web server answers `/api/plan_data` every 5 seconds, and HA select changes arrive on the websocket thread. There is no lock anywhere in the codebase.

This has now produced three independent bugs, in **two different flavours** — off-thread readers *and* code inside the fake reading its own faked clock — so treat "reads the shared clock" as a class rather than a one-off:

- **Manual overrides ran a day late and never came back (GH#4900, fixed in PR #4906).** Manual charge/export/freeze/demand slots and manual rate overrides are stored as relative `"%a %H:%M"` labels and re-decoded, re-rendered and written back on every read. The decode read `midnight_utc` and the render read `midnight`; a caller landing inside the rewind decoded the labels a day late and **persisted** the result. The same borrowed clock also broke the 48-hour horizon check, silently dropping any slot more than 24 hours out. The fix is local: `manual_times()`/`manual_rates()` now take their origin from `manual_time_origin()`, derived from `now_utc`, which nothing fakes — the rewind itself is unchanged.
- **PV forecast buckets landed a day late (GH#4804).** `SolarAPI.publish_pv_stats()` reads the same attribute live (`solcast.py:696`). The reporter's log showed `today` at 0 with every later day matching the previous cycle's one-day-earlier value. Not separately fixed, and confirmed by reading rather than reproduced.
- **History car slots shifted (GH#5004, fixed in PR #5025, v9.0.2 - keep the mechanism for older logs).** First instance of the **same-thread** flavour: `calculate_yesterday()` itself reads its own faked attribute inconsistently across ~350 lines. It builds `yesterday_load_step` with `base_offset = 24*60 + real minutes_now` *before* faking `minutes_now = 0`, then calls `yesterday_reconstruct_car_slots()`, whose per-minute scan derived `minute_previous = self.minutes_now + 24*60 - minute` — which under the fake is `1440 - m`, so car energy recorded at yesterday clock T was attributed to axis minute T − minutes_now, and any session before minutes_now vanished entirely (`get_from_incrementing()` wraps a negative index by +1440 and reads the *previous* day instead of nothing, `fetch.py:757`). The fix passes the real minutes_now into `yesterday_reconstruct_car_slots()` as a parameter (`output.py`); it touches only that formula and its call site, so the octopus-half consumers below survive it. Affects the History display and yesterday savings only; the live plan path is indexed correctly. The old e2e test actively encoded the bug — it built its sensor fixture from the same faked `1440 - minute` formula, so it passed only because fixture and code shared the error; and its `step_data_history` mock swallows `base_offset` into `**kwargs` and returns a flat 0.1 kWh dict on every axis, so the load-side assertions are axis-invariant and a partial regression that fixes only one of the two clocks stays green — while every test in the file pins `car_energy_reported_load=True`, so the flag-off (charger outside the CT clamp) no-subtraction path has zero coverage. The deeper fix already exists in-repo: a yesterday-axis origin object built like `manual_time_origin()` (`userinterface.py:1484`) would retire the faked attribute; note `publish_html_plan`'s internal alignment arithmetic is load-bearing on the fake, so removing it without threading an origin would shift the whole History render — the *reverse* of GH#5004.
- **Three faked-clock consumers survive the sensor-half fix in the octopus half of the same function** (pre-existing on main; PR #5025's diff touches only the energy-sensor formula and its call site; all bounded by the `car_energy_reported_load` load-cap clamp; code-read, not reproduced live): (1) `decode_octopus_slot()` caps slot ends at `forecast_minutes + self.minutes_now` (`octopus.py:2939`), which inside the fake is `end_record + 0`, so a dispatch that ran *today* before now decodes to yesterday-axis minutes past 1440, the cap collapses `end` below `start`, `kwh` scales negative and the `kwh > 0` filter silently drops it — the today-so-far segment of the widened History axis gets neither a car slot nor its load subtraction; (2) the `dispatch_billed_off_peak()` completed-dispatch exemption from PR #4957 keys on `end_minutes <= self.minutes_now`, which can never fire on the yesterday axis, so a retroactively relabelled AWAY dispatch vanishes from yesterday's reconstruction (GH#4946 replayed); (3) the `kwh == 0 and start <= self.minutes_now < end` active-slot synthesis branch (`octopus.py:3146`) fires for any zero-kWh dispatch straddling yesterday midnight — bounded by the load cap and requiring an unverified data condition (an explicitly zeroed chargeKwh), so suspected, not confirmed.

So a "shifted by exactly one day" or "the value reverted / went stale for no reason" report is worth checking against this before anything else. Any new code that reads `midnight_utc`/`minutes_now` from outside `update_pred()`'s own thread needs `manual_time_origin()`'s treatment, not the shared attribute — and **anything inside the fake that indexes a history series must be handed the real `minutes_now`**, because those series are keyed from the real now.

| Solis (`solis.py`) | `SOLIS_CID_STORAGE_MODE = 636` is Modbus 43110, a bit mask. On firmware "4B and above" (what `is_tou_v2_mode()` detects: CID 6798 reads 43605) the timed charge/discharge enable moved to the per-slot registers — `SOLIS_CID_CHARGE_ENABLE_BASE`/`..._DISCHARGE_ENABLE_BASE`, Modbus 43707, six slots not three — and every mode value carrying TOU bit 1 (3/35/43/51/98) was dropped; 35 became 33, 98 became 96. Such an inverter answers a CID 636 write with code 0 and reads back without bit 1, so a log full of CID 636 verification warnings is a refused bit, not a failed write (GH#4707). `set_storage_mode_if_needed()` decides the bit from `is_tou_v2_mode()`: never asked for on V2, always asked for and retried on V1, where bit 1 still *is* the timed charge/discharge enable. Do not try to learn it from the read-back instead — GH#4710 did, and GH#4774 showed why that cannot work: on six inverters the same write of 179 verifies minutes before and minutes after the one that reads back 177, so a single post-write read is not evidence of a firmware property. Latching it was also silent rather than noisy: the verify read refreshes `cached_values`, so after a stripped write the cache held the stripped value, the suppressed computed value matched it, and `set_storage_mode_if_needed()` stopped writing CID 636 at all for the whole 8-hour verdict — across an overnight charge window. GH#4239's "only retained while a window is configured" is not the whole story — it was refused with slot 1 enabled and its window in force. `read_and_write_cid()` re-reads once after `verify_settle_seconds` before calling a mismatch a failure, because the immediate verify read is taken about half a second after the write. Do not "stop the failed verify poisoning the cache" — `write_cid()` caches the value it *requested* and the post-write `read_cid()` deliberately overwrites it with what the inverter actually reports, so the cache mirrors the inverter rather than Predbat's intent; skipping that update would leave the cache agreeing with the write that just failed, and change detection would then never retry it. The two control paths choose the storage mode differently and it matters: V1 picks from `in_charge_slot`/`in_discharge_slot`, which are clock tests, so CID 636 changes value and gets written the moment a window opens; V2 picks from `slot1_active`, which is only "slot 1 has a window configured", so the mode is written when the slot is *programmed* and nothing at all happens at the window boundary. On the GH#4774 night the last CID 636 write was 22 minutes before the window opened, and the comparison night that worked had one near the window - so `claim_window_mode_assertion()` now asserts the mode once per window on both paths. Slot registers are polled hourly, plus every 5 minutes while `is_inside_active_window()` is true, so drift during the window that matters is caught in the same cycle it happens. GH#4774 also left a useful negative result: that inverter grid-charged from 20% to 91% overnight with bit 1 clear throughout, confirming the per-slot enables alone drive timed charging on V2 — so a "charge window never started" report on V2 firmware is not a CID 636 problem and needs looking at elsewhere. ## Traps when investigating

- **Stale kernel binary.** The `prediction_kernel_lib_*.so` binaries are committed and CI has a job for them. The warning above means the checkout falls back to the Python engine, which is fine for triage. Never rebuild or commit binaries while triaging.
- **`minutes_now = 0` hides time-of-day bugs.** The load-forecast tests set `minutes_now = 0` in their shared
  setup, which made GH#4732's holiday off-by-one invisible for years: the faulty `tod <= minutes_now` was then
  true only for the midnight slot. Anything indexing history as `(minutes_now - tod) + d * 1440` needs a test at
  a non-zero `minutes_now`, and wall-clock-aligned fixture days (`test_holiday_mode.py`) rather than the
  minutes-ago bucketing in `test_load_forecast_history.py`, which only lines up when `minutes_now` is 0.
- **Golden plans move when load scaling changes.** Any change to `step_data_history`'s `scale_today` handling
  shifts both `coverage/cases/*.expected.json` (regenerate by copying the `*.actual.json` the run writes) and
  `coverage/cases/random_results.json` (regenerate with `./run_random`, then copy `random_results.json` over it).
  `debug_cases` stops at the first failing case, so a second case can start failing only after you fix the first.
  Before regenerating, confirm the shift is the intended one by temporarily restoring the old behaviour and
  checking the golden files pass again.
- **Build test dates from Predbat's clock, not the machine's.** Predbat runs on the timezone set in apps.yaml (Europe/London in the harness), not the host's, so a fixture built with `datetime.now()` is on a different date from the code under test for part of every day. `test_saving_session` and `test_alert_feed` failed exactly that way under `TZ=America/Los_Angeles` at 21:30 local - and the clearest case is instructive: `load_free_slot()` measures a slot against `midnight_utc`, so a window built for the machine's "today" starts before Predbat's day began and is dropped entirely. Anchor fixture dates to `my_predbat.midnight_utc` (`96e1073c`, PR #4877). Hardcoded future dates in test data have the same shelf-life problem and were pushed out to 2099 (`d850365b`). Newest instance: PR #4971's `multi_car_iog` tests force `now_utc` to 12:00 on the *machine's* UTC date while `midnight_utc` stays on the real clock, so between 23:00 UTC and midnight the forced slot falls behind local midnight and is dropped - observed as `multi_car_iog_load_slots_regression` and `multi_car_iog_model_limit_fetch_4967` both failing with "car 0 should have IOG slots, got none" at 00:06 local, on a clean docs-only tree (mechanism reasoned from the code, not reproduced at a passing hour) - **fixed in PR #4998** by pinning `midnight_utc` in those tests, keep the mechanism for the next test that pins only one of the two clocks.
- **`midnight_utc` is local midnight, and `now_utc` is local time.** Both names are wrong in the same direction and it has misled at least one review into hunting for a UTC-vs-local frame mismatch that does not exist. `update_time()` sets `now_utc_real = datetime.now(self.local_tz)` (`predbat.py:654`) - already local, not UTC - and `midnight_utc` is that value with the time zeroed (`predbat.py:655`), i.e. the local midnight of Predbat's configured timezone as a timezone-aware datetime. Anything comparing a slot against `midnight_utc` is therefore working in local wall-clock, which is usually what you want and never what the name says. Before concluding a rate or slot bug is a timezone frame error, check which of the two frames the code is actually in. Corollary for reading logs: `time_abs_str()` renders against `self.midnight`, so a line quoting a past/negative minute key prints in the local frame and will not line up with the UTC timestamps an integration's sensor publishes (GH#5036) — recompute the minutes from the sensor's own timestamps instead of keying evidence off the printed date.
- **Test ordering.** Some tests share a `PredBat` instance, which is exactly why `run_debug_cases` builds a fresh one per case. A test that fails in a full run but passes alone is usually pollution, not the reporter's bug — another reason to run only the targeted test. And the inverse asymmetry has a second cause (GH#5026): `create_predbat()` takes `minutes_now` from the **wall clock** (`update_time()`) and never resets it, so the one shared `my_predbat` built in `unit_test.py`'s `main()` inherits whatever the previous module's `reset_inverter()` left (`minutes_now = 12*60`, `test_infra.py`) while a standalone run gets the host's time of day — a test can pass in the suite and fail standalone in the evening with *no state pollution at all*. `prediction_batch` failed exactly this way: not misrouted, the ten-trial SoC-cost precondition (`test_batch_results_match_their_own_job`) just collapsed onto one value at seed 5's window/rate alignment. Equivalence-style subtests are `minutes_now`-insensitive; only precondition checks on seeded-scenario economics are sensitive. PR #5028 (merged, `9290055d`) pins the clock per-module (third per-module pin of this class — PR #5013 pinned dates, #4971's tests pinned midnight_utc) with `minutes_now` added to `SCENARIO_STATE_ATTRS`; if a fixture-level pin in `create_predbat` ever lands instead, it closes the class — but beware that a pin-guard test is **vacuous in suite configuration when the pin value equals the residue value** (suite ambient is already 720), so a future guard test must capture the pre-pin entry value, not just compare against the pin constant.
- **A textually clean auto-merge can still be a semantic conflict.** Merging `origin/main` into an old PR branch reported no conflicts while main's GivTCP refactor (#4864) had deleted `Inverter.rest_data`, which the PR both tested on and passed to the constructor - the merged tree crashed the first `Inverter()` construction in two test modules, only one of them the PR's own (PR #4645). For PR-cleanup work the full `run_pre_commit` suite is the detector, not the PR's own module. Corollary: `rest_data` is gone since #4864 and `inverter_source_active()` (`inverter.py`) is the replacement question for "is this inverter component/REST-backed" - anything written against `self.rest_data` predates the refactor. And when a test plants a components stub, construction-time calls run against whatever stub the *previous* test module left behind, so a new components-consulting call in `Inverter.__init__` needs a `getattr` guard on the registry surface, not a fake patched into one module.
- **Version drift.** Compare `git describe --tags` against the version in the first few lines of their log. A fair number of reports are already fixed on main, and that is a useful triage answer on its own. Two tag quirks: the `v9.0.1` and `v8.55.1` tags alias the **same commit** (`b8996659`), so "diff vs 8.55.1" is the right comparison for any v9.0.1 upgrade report from ≤v8.55.x; and PR #4991's moderate clock-skew warning postdated them both until v9.0.2 (`b8f3f956`, 2026-09-10) shipped it — a "no moderate warning" report is a pre-v9.0.2 version, not a broken feature.
- **Log noise.** `predbat.log` carries routine `Warn:` lines (config clamps, kernel status, unsupported settings). Don't quote a warning as the root cause unless it lines up with the time the reporter describes.
- **Hardware questions.** A unit test settles what the code does, not what an inverter did. Several findings here were only confirmed on live hardware. If the question is hardware behaviour, say the maintainer needs to confirm it rather than running a test to look thorough.
- **`gh issue list --search` without `--repo` searches all of GitHub.** Confident-looking hits can be from unrelated projects (GH#4705). Always pass `--repo springfall2008/batpred` on a duplicate search. An **empty** result deserves the same suspicion as a confident one, and usually the cause is the query rather than the machinery: a triage run reported `gh search issues` as dead on the runner because a search for GH#4961's title text returned nothing, when that issue's real title misspells "unreasonably" - the run had silently corrected the typo while retyping the title, and searching the spelling the reporter actually used finds it (GH#4973, re-probed). Fetch the issue's exact title rather than retyping it, and sanity-check an empty result with a distinctive token from a known issue before reporting no duplicates.
- **A flat SoC reading isn't necessarily a stuck charge.** `soc_kw` is derived from `soc_percent × soc_max / 100` (`inverter.py:1422-1428`); on a large pack, one percentage point is a meaningful chunk of energy — e.g. ~0.32 kWh on a 31.6 kWh pack, ~9.5 minutes flat at a 2 kW rate. Before treating a flat run as evidence of a stall, check whether its duration is fully explained by the pack's percent-to-kWh granularity at the charge/discharge rate in play (GH#4784).
- **The HA Companion app's embedded webview ignores `Content-Disposition: attachment`** and renders any download link inline instead, even when the server sends correct headers — confirmed for both the debug-snapshot and bulk-archive routes (GH#4720). A "download doesn't work" report from the Companion app specifically is a client limitation, not a server bug. The advice this bullet used to carry - that the snapshots sit as plain-text `.txt` YAML in `<config root>/cache/` - is now out of date twice over. PR #4743 (GH#4720) moved the periodic snapshots into `debug/` under their real capture name, and PR #4941 (GH#4932) renamed that to `predbat_debug_<id>.yaml.txt`, because **GitHub rejects a bare `.yaml` attachment** - which is the entire reason for the trailing `.txt` (`snapshot_filename()`, `debug_history.py:219`; `_legacy_snapshot_filename()` still resolves and prunes pre-upgrade `.yaml` files for the rest of their time in the ring). So a reporter can now attach a ring snapshot straight out of `debug/` with no renaming. `create_debug_yaml()`'s separate per-cycle dump is still written as a bare `debug/predbat_debug_HH_MM_SS.yaml` (`userinterface.py:761`) and does still have to be renamed before it can be attached. The bulk archive has the mirror-image constraint and must stay **compressed** end to end: browsers that unarchive downloads do it by extension, and a 15-snapshot history is 32 MB of yaml against 4.6 MB as a tarball - unpacked it breaks GitHub's 25 MB attachment limit *and* GitHub rejects bare `.tar` outright, while `.tgz` is accepted (PR #4898).
- **Two scans over one slot must agree on their range.** *(Both halves below were fixed in PR #4943; the mechanism is kept because it recurs and because an older log still shows it.)* `calculate_yesterday()` rebuilds each History slot with two walks over the same per-minute status list: one decides *whether* the slot rebuilds a charge/export window, the other decides *where* that window starts. When #4872 widened only the first to trust homogeneous slot edges, a state living solely in a trusted edge was counted but never given a start minute, so the window was appended as `{"start": None, "end": None}` and `in_charge_window()` raised `TypeError: '>=' not supported between instances of 'int' and 'NoneType'` — killing the whole `update_pred()` cycle, not just the History view (regression from PR #4872). A `TypeError` comparing against `None` deep in the plan is worth tracing back to a *pair* of loops that drifted apart. The same edit uncovered a second defect in those loops: the charge/export handoff ("whichever side starts second ends the one that started first") also fired when both sides started at the *same* minute, which is what Cross-charging is - so every cross-charging slot rebuilt a **zero-width** export window (`start == end`), invisible to `in_charge_window()` and worth nothing in the simulated cost. The export half of cross-charging was thus still missing from History long after #4466 "restored" it, because `_test_cross_charging_reconstructed_as_both_windows` only asserted the window list was non-empty. **A window assertion that does not check `start < end` proves nothing** - a list of zero-width windows passes it.

- **Two traps when adding a guard to an `Execute` entry point** (found writing the GH#4965 fix, merged as PR #4968). `test_control_ledger.py`'s `test_every_entry_point_opens_its_own_cycle` builds a bare `Execute.__new__(Execute)` stub (`test_control_ledger.py:1845`) and calls `quick_inverter_data_update()` on it directly, so any new base-class read added to that function fails the quick suite with `'Execute' object has no attribute 'get_arg'`. The stub now carries a `get_arg` lambda, but the shape is the trap: the same is true of every entry point tested this way. The second is worth more than the first - **the harness cannot reproduce the crash the issue describes**. Deleting `inverter_clock_skew_discharge_start` and calling the unguarded function does *not* raise, because that read (`inverter.py:1624`) sits behind `if "discharge_start_time" in self.base.args:` (`inverter.py:1563`), which the mock inverter never satisfies. Verified by stashing the fix and re-running `./run_all --test execute`: the regression test failed on its return-value assertion, not on the AttributeError branch it was written for. For this class of init-order bug, assert that the guard is present and returns early; an attribute-deletion reproduction passes silently whether or not the bug is fixed.
- **Check that a report's premise exists before verifying its logic.** Three reports in two weeks were built on configuration or history that is not there: GH#4918 quoted `tesla_tariff_sync`, `tesla_smart_plan` and `tesla_smart_plan_max_export`, none of which appear anywhere in the codebase or `APPS_SCHEMA` (an AI assistant invented them for the reporter); GH#4917 treated `trust_future_dynamic_iog_slots` as shipped when it exists only on the unmerged PR #4885 - on `main`, `rate_add_io_slots()` trusts every planned IOG slot unconditionally; and GH#5022 (an enhancement issue written by Claude under the reporter's account) claims #5015 "turned off `support_feedin_first` for FoxCloud", which `git log -S` disproves — the flag was set once by `3ed9151e` and never removed. Grep `config.py` / `APPS_SCHEMA` for every setting a report names, and check `git log` or `gh pr view` before accepting an "added for #NNNN" claim — including the background section of an issue you are about to implement.
- **`grid_power` is negative when importing.** That is the repo's convention: `docs/faq.md` states it, `web.py`'s power-flow code reads it that way, and `test_enphase_api.py` asserts it by name - `grid_power_invert` exists precisely for meters that do the opposite. The outlier is `predbat_metrics.py:101`'s Prometheus help string, which claims "positive for import". GH#4797 read that string as authoritative and concluded the web arrows and icons were inverted; measured against every other statement of the convention, they are not. Work out which side of that contradiction a sign report is arguing from before agreeing with it.
- **A passing test proves nothing when its fixture encodes the bug.** This has now happened often enough to be a check rather than a surprise: `web_power_flow` shares the sign assumption it would have to catch; the `iboost_smart` fixture uses a flat rate, so a rate-averaging bug cannot show; `test_balance_inverters` configures two *identical* inverters, so neither the capacity-blind SoC split nor the 3+ inverter partner ring is exercised; PR #4935 found a cap test whose slot started after the window it was capping against, so the loop under test ran zero iterations; and GH#4826's `write_failure` test mocks a response with no error code, leaving the classification branch untested. Read the fixture before quoting "the test passes" in a comment - and say what the test would have to look like to catch the reported behaviour.
- **One unexplained observation, recorded so a second sighting is recognised.** In GH#4900's log, at 00:00:27, the nightly tariff-compare scenario for `igo_fixed` - running under swapped flat 12.0p export rates - had its scenario plan accepted as the **live** plan (`using new plan` logged from inside the scenario). A recalculation 18 seconds later replaced it, so nothing was harmed that night. The code path was not identified within triage scope. If you see `using new plan` inside a compare scenario, this is the thing.

## Adding to this file

When an investigation turns up something a future triage run would have wanted to know — a config item that explains a class of report, an API quirk, a symptom that maps to a module — add a row. Keep it short, name the symbol rather than the line number, and cite the issue number so the next reader can check the original.

If you are running under the triage bot you cannot edit this file directly — the clone is `reset --hard` before every flow, so the edit would not survive. Write the finding as a single markdown file in the queue directory named in your system prompt instead; the `/journal-update` flow folds the queue in once a day, re-checking each candidate against current `main` first, and opens a PR for a maintainer to merge.

Whichever route you take, the bar is the same and it is not "interesting": record what you **verified**, say how you verified it, and keep anything you merely suspect explicitly marked as suspected. A wrong entry here is worse than a missing one — every later run trusts this file, so a confident mistake ends up in a comment posted to a real reporter. Correcting or deleting a stale entry counts as much as adding one.
